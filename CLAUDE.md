# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Godot 3rd-person endless-runner-style adventure game ("CrimeKickers"). The player walks an infinite procedurally generated field, switches between several characters, and is chased by hostile NPC crocodiles. The codebase is written to be read — scripts are heavily commented for teaching purposes, so match that density when editing existing files.

**Engine version:** The actual target is **Godot 4.5** (`project.godot` declares `config/features=("4.5", ...)` and CI uses `barichello/godot-ci:4.5`). README.md and QUICKSTART.md say 4.3 — they are stale; trust 4.5.

## Commands

The **game** has **no test suite, linter, or build script** — it is a pure Godot project driven from the editor and CI. (The multiplayer lobby in `server/` is a separate Go service with its own `go test` suite; see "Multiplayer lobby service" below.)

**Run `godot --headless --path . --import` once in a fresh clone before any of the headless checks above.** A never-opened checkout has an empty global class cache, so every `class_name` type (`MobileSensors`, `ToonShading`, `LobbyClient`, …) fails to resolve and the scripts using them **silently fail to attach** — the scene still boots, just missing pieces. `webrtc_addon_check.gd` documents the same trap; `minimap_selfcheck.gd` now detects it and fails loudly rather than passing vacuously (a scriptless `StartOverlay` means nothing paused because nothing loaded).

**Any headless harness that boots `main.tscn` must press PLAY SOLO before it measures anything.** `start_overlay.gd` takes `get_tree().paused = true` in its `_ready()` and re-asserts it every `_process`, so a `PAUSABLE` node — which is most of them — never takes a frame; and `SceneTree.create_timer()` defaults to `process_always = true`, so a wait elapses under that pause and the check runs against a world that never ran. Two ordering gotchas in `minimap_selfcheck._run()`: `_ready()` is **deferred** for a scene added from `_initialize()` (dismiss on that first frame and the overlay's `_ready()` re-pauses behind you — `await process_frame` first), and the dismissal must be re-tested (`if paused:`) because another node may hold its own pause. `mp_selfcheck.gd` boots no scene and `mp_e2e.gd`'s `MpManager` is `PROCESS_MODE_ALWAYS`, which is why neither noticed.

Editing is expected to happen in the Godot editor (`godot project.godot`); the editor reimports assets into the gitignored `.godot/` cache. Each `.gd` has a sibling `.gd.uid` — Godot manages these; don't hand-edit them. (Note: `scripts/windman_whole_body_animator.gd.uid` is orphaned — its `.gd` no longer exists.)

3D character/enemy models are **generated by Python**, not modeled by hand. Regenerate via `python3 scripts/generate_*.py` (depends on `trimesh` + `numpy`; `generate_windman_separate.py` also needs `shapely` + `scipy` for the extruded chest "W"); output goes to `assets/models/characters/`. The live Windman is the 11 separate parts in `windman_parts/` (regenerated by `generate_windman_separate.py`), assembled and animated by `scenes/characters/windman_updated.tscn` — **not** the monolithic `windman.glb` (used only by the orphan `windman_3d.tscn`).

## Architecture

### Node discovery is group-based, not reference-based
Systems never hold hard references to each other. The player adds itself to the `"player"` group; terrain and enemies locate it with `get_tree().get_first_node_in_group("player")` / `get_nodes_in_group(...)`. When adding a system that needs the player (or enemies), use groups rather than `$`-paths or exported references. Relevant groups: `player`, `crocodile`, `enemy` (used by `piglet_crocodile_ai.gd`), `enemies` (used by `enemy_controller.gd` — note the inconsistent pluralization between the two enemy scripts), and `mp` (the multiplayer manager, found by `mp_ui.gd`). **`"player"` means the LOCAL player and nothing else** — a remote multiplayer peer is a visual-only `RemoteAvatar` in **no** group, because terrain streaming, crocodile chase, the LOD manager, the danger vignette, fauna and weather all resolve "the player" through `get_first_node_in_group("player")` and would silently follow a hologram (see "Multiplayer (phases 3–4)" below).

### Everything in the world is spawned procedurally from the terrain
`scripts/endless_terrain.gd` (on the `EndlessTerrain` node in `main.tscn`) is the world engine:
- Maintains a `Dictionary` of active chunks keyed by `Vector2i` chunk coords; only recomputes when the player crosses a chunk boundary (`world_to_chunk`). `render_distance` (exported, default `5`) gives `(2*render_distance+1)²` active chunks.
- Generates each chunk's mesh, collision, decorative cubes, **and crocodile NPCs** in code — there is no hand-placed scenery. Object/crocodile positions are seeded deterministically from chunk coords **plus the per-run `run_seed`** via `hash(Vector3i(...))`, so a chunk always regenerates identically *within a run* while consecutive runs get fresh worlds (see "Gameplay loop" below).
- Spawned crocodiles are **parented to the chunk MeshInstance3D**, so they are freed automatically when the chunk unloads. Anything you spawn per-chunk should follow this parenting rule or it will leak.

**Terrain focus points — the one multiplayer thing the terrain knows about, and its boundary is absolute.** `set_focus_points(points: Array)` pins a `FOCUS_RING` (1) block of chunks — 3×3, i.e. at least 50 m of loaded ground in every direction — around each of up to `MAX_FOCUS_POINTS` (3) extra world positions, purely by **unioning them into `update_chunks`' `chunks_to_load` set**. **Focus points decide only WHICH CHUNKS STAY LOADED; they never touch what a chunk contains.** Every chunk's content is a pure function of its own coords + `run_seed` and generation order already cannot change it (see the time-slicing note below), so a chunk built because a teammate stands on it is byte-for-byte the chunk the local player would have built by walking there — nothing in generation reads a focus point, and nothing that does may ever be added. The caller is `crocodile_lod_manager.gd`, which already builds exactly this array from `MpManager.peer_positions()` (master-only by construction — that method answers `null` on a non-master), already runs on a throttled 9 Hz tick, and calls it **every** scan including with the empty array, which is what *releases* the pinned chunks when a peer leaves a room. `set_focus_points` no-ops on an unchanged set, so the steady state is one Dictionary compare; a changed set raises `focus_dirty`, which is what lets `_process` rebuild the field **off a boundary crossing** (otherwise a far teammate's ground would only be pinned when the *local* player happened to cross a chunk edge — precisely the far-apart case this exists for). **Why it exists:** the room master simulates the crocodiles for everybody but can only simulate the ones its own terrain has loaded, so a peer past `render_distance × chunk_size` (150 m on web) got no samples and its neighbours fell back to local sim after `CROC_SYNC_TIMEOUT`. `FOCUS_RING = 1` is derived, not guessed: 50 m of guaranteed coverage bounds `crocodile_lod_manager.SIM_RADIUS` (45), the radius inside which a crocodile is awake and therefore the radius inside which there is anything to publish. **The cap is the memory story:** the union of peer areas multiplies the active chunk count, so at most `MAX_FOCUS_CHUNKS` (27) chunks are admitted beyond the player's own square — worst case 49 + 27 = 76 on web (+55%), 121 + 27 = 148 on desktop (+22%). Past the cap, points are **dropped rather than rotated**, so the set is stable frame to frame (flickering chunks would be worse than none), and a room whose four players stand four different places degrades exactly as before for the rest. The cap is also the trust bound — these positions originate in presence packets, which `MpManager` bounds only by `MAX_PRESENCE_COORD`.

**Chunk generation is time-sliced (one chunk per frame, nearest-first).** `update_chunks` builds only the **safety ring** synchronously — missing chunks within Chebyshev distance ≤ `SYNC_RING` (1) of the player's chunk (9 at startup / after `new_run()`, ≤ 3 on a normal boundary crossing) — so the player never stands over an unbuilt chunk. Every other missing chunk is queued into `pending_chunks` sorted nearest-first (the queue is rebuilt from scratch on each boundary crossing, which dedupes for free), and `_process` dequeues and builds exactly **one** pending chunk per frame — progressive fill hidden behind the fog instead of a multi-second startup freeze. Generation ORDER cannot change content: every chunk's RNG is pure in its own coords + `run_seed`, and the road station cache is pure in `k`. `new_run()` clears the pending queue before rebuilding, and its `update_chunks(Vector2i(0,0))` call synchronously builds spawn + ring 1 — the load-bearing guarantee that the player teleported to `(0,2,0)` lands on solid ground the same frame.

**The ground is one shared `PlaneMesh`, shaded by vertex noise.** `_get_shared_ground_mesh()` (same lazy-getter pattern as `_get_shared_unit_box_mesh`) returns a single 16×16-subdivided `PlaneMesh` used by every chunk (all chunks are the same size), with `cast_shadow` OFF on the ground instance — a flat plane can only shadow itself, so skipping it removes every chunk from the shadow passes. The built-in default ground material is a `ShaderMaterial` on `assets/shaders/ground.gdshader`: a 2-octave world-space value noise computed **per-vertex** (the 16×16 subdivisions provide the vertices) blends two greens; the fragment stage does only the varying lerp, so fill rate is untouched, and world-space input makes the pattern seamless across chunk seams with zero per-chunk work. The `@export var terrain_material` escape hatch remains (now typed `Material`, not `StandardMaterial3D`): a material assigned in the editor wins over the shader.

**Blocks are rendered as one `MultiMeshInstance3D` per chunk, not one `MeshInstance3D` per block.** `create_box()` no longer instances a mesh+material per decorative block; it appends a `{ "transform": Transform3D, "color": Color }` entry to a per-chunk `block_batch` array (threaded through `create_chunk` → `spawn_objects_in_chunk` → `spawn_*` → `create_block` → `create_box`). After generation, `_build_block_multimesh()` builds one `MultiMesh` (shared unit `BoxMesh`, `transform_format = TRANSFORM_3D`, `use_colors = true`) whose per-instance basis is `Basis(Vector3.UP, yaw).scaled_local(dimensions)` and per-instance color comes from **three curated two-color ramps sharing a warm undertone** (the `RAMP_*` consts: sandstone→terracotta, slate→blue-grey, olive→moss), each sampled by one lerp. The material is a single shared `StandardMaterial3D` with `vertex_color_use_as_albedo = true` and `roughness = SHARED_BLOCK_ROUGHNESS` (0.85). **Determinism gotcha:** the ramp swap preserved the RNG draw sequence exactly — same `randi_range(0, 2)` selector, then per branch the same number of `randf_range` calls as the old per-channel-random colors (5/3/5 draws per branch, padding draws explicitly discarded), and `create_box()` still consumes the old per-block roughness `randf_range(0.7, 1.0)` draw (then discards it) — so the chunk RNG sequence, and the whole procedural layout, stays byte-for-byte identical. MultiMesh can't vary roughness per instance, hence the single shared value. `create_box()` carries **three optional, inert-by-default params** — `tilt` and `color_override` (added for artifacts, see below) plus `collide: bool = true`, which when false skips the `CollisionShape3D` and emits the visual batch entry only: tree canopies are visual-only, so a forest pays trunk collision instead of 3–4× that (see "Biomes"). None of the three affects RNG — the colour/roughness draws run identically whatever they are set to.

**Block collision is consolidated into one `StaticBody3D` per chunk.** Visual batching is decoupled from physics: each chunk has one `StaticBody3D` named `"BlockCollision"` (`block_body`, threaded down the same call chain as `block_batch`) that holds every block's `CollisionShape3D` child (a `BoxShape3D` at the block's chunk-local `position`/`rotation.y`). This replaces the old one-body-per-block scheme (~25× fewer block collision nodes). Layer/mask stay at the Godot defaults (1/1), so player collision and crocodile obstacle-avoidance raycasts are unchanged. **Ground collision stays in its own separate `StaticBody3D`** — folding it in would save one node and only muddy the code. A chunk that ends up with no blocks `queue_free()`s its empty `block_body` instead of leaving it in the tree.

**Coins live on a single continuous "coin road", not a per-chunk random scatter.** The road is a deterministic, station-indexed **parametric path** — a pure function of an integer station index `k` and fixed seeds (`ROAD_WORLD_SEED` + the per-run `run_seed`, constant for a whole run — **not** per-chunk RNG), so it lines up seamlessly across chunk seams. Station 0 sits at world origin, so the player spawns on the road. The centerline is built by integrating a per-station heading: `heading[k+1] = clamp(heading[k]*(1-ROAD_RESTORE) + _road_turn(k), ±road_max_heading_deg)` (a deterministic per-station turn plus a restoring bias toward +X). Because `road_max_heading_deg < 90` (asserted), `cos(heading) > 0` always, so the centerline's **X is strictly increasing in `k`** — the road always trends forward while still curving and zig-zagging (full loops / U-turns are intentionally excluded). Coins are **not** placed on the centerline as a single line. Each station instead **scatters a few coins** at ground height (`COIN_GROUND_HEIGHT`) at *random* offsets within a band around the centerline — up to ±band/2 laterally plus a small along-road jitter (`ROAD_COIN_LONG_JITTER`) — so the trail reads as a loose **swath of territory a few coins wide**, not an obvious conga-line. The band width varies between `road_width_min` (10 m) and `road_width_max` (20 m); per station, `road_coin_slots` candidate coins each spawn with probability `road_coin_chance` (≈1 coin/slice on average, so the swath stays sparse and irregular), and `road_coin_spacing` (6 m) is the longitudinal step between scatter slices. The scatter is deterministic — a per-station RNG seeded only from `k` + `ROAD_COIN_SEED` + `run_seed` (see `_road_coins_at`) — so it regenerates byte-identically within a run. `_road_coins_at` returns an array of `{ "pos": Vector3, "gem": bool }` **dictionaries, not bare Vector3s** — each slot rolls one extra `rng.randf()` against `ROAD_GEM_CHANCE` (0.04) to become a rare purple gem worth 10 (`coin.make_gem()`); its only caller is `spawn_coins_in_chunk`. `_road_width(k)` also **narrows the band with distance**: after the oscillating width it lerps toward `road_width_min * ROAD_NARROW_FLOOR_FACTOR` (0.4) over `ROAD_NARROW_STATIONS` (2000) stations — still pure in `k`, and since narrowing only ever *shrinks* the band, the seam `pad` below stays a safe upper bound. Per chunk, `spawn_coins_in_chunk` extends a contiguous, never-reset station cache (`road_stations`) to cover the chunk's widened X-range, then spawns **only** the scattered coins whose `world_to_chunk(coin) == chunk_pos` — each coin is claimed by exactly one chunk, so there are no gaps or duplicates at seams (the scan `pad` is derived from band/2 + jitter so no scattered coin near a seam is missed). **Off-road chunks get zero coins** (this is the incentive to follow the road). A coin that would land on a block footprint perches on the block's top if it's climbable, else is skipped. **Design note:** the forward bias is deliberate — a fully unbounded looping path can't guarantee bounded per-chunk station coverage (a 2D random walk is recurrent), which would break the bounded, deterministic per-chunk generation. If loops are ever wanted, they require the heavier spatial-bucket scheme (bucket every station into a `chunk → stations` dictionary, extend until all active chunks are covered) — noted as a future option, intentionally not built now.

**Rare "lost civilization" artifacts break up the field (~1 chunk in 20).** `spawn_artifact_in_chunk` (called from `create_chunk` **after** `spawn_objects_in_chunk` and **before** `_build_block_multimesh`, so artifact stone joins the chunk's single MultiMesh + single `BlockCollision` body) builds one of **five** code-built landmarks: leaning half-buried monolith with glowing rune strips, broken arch of floating stones, circle of tilted standing stones round a glowing altar slab, half-buried colossus head with emissive eyes, spiral of steps to nowhere. Placement is **split across two functions exactly like camps, for exactly the same reason.** `_artifact_at(chunk_pos)` is the rarity roll alone, on its own **independent hash stream** — `hash(Vector3i(chunk.x * 73856093, chunk.y * 19349663, run_seed ^ ARTIFACT_SALT))`, the `_boss_at` / `_road_coins_at` pattern — so it consumes **zero** draws from the chunk RNG; it returns `{}` or `{ "seed": int }`. The `ARTIFACT_PLACE_TRIES` (4) candidate loop lives in `spawn_artifact_in_chunk`, where `obstacles` exists, and each try is judged by `_biome_spot_ok(chunk_center, x, z, ARTIFACT_RADIUS 7.0, ARTIFACT_ROAD_CLEARANCE 14, obstacles)` — the same single home of the river + road-clearance + overlap rule that camps use. The road rejection is what produces the **off-road bias** and the hard "never on the centerline" rule; the overlap rejection is what keeps the landmark readable. **The loop was originally inside `_artifact_at`, where there is no geometry to test against, so artifacts were placed with no obstacle test at all: measured over a 61×61 chunk field, 51.5% interpenetrated a scattered block or feature structure, worst case 16.5 m — one artifact entirely swallowed by a pyramid, taking its coin ring and its one guaranteed gem, the whole reason to detour, into the stone with it.** Measured survival is 59.5%, so `ARTIFACT_CHANCE` is tuned to **0.08** → ~1 built artifact per 23 chunks, the same rarity the unchecked 0.05 roll produced (at 0.05 with the test added it fell to 1 per 38). `ARTIFACT_RADIUS` (7.0) is the widest footprint any of the five shapes can return — the real radius is only known after the builder runs — and must stay under `ARTIFACT_EDGE_MARGIN` (12) so nothing straddles a seam. **All solid stone routes through `create_box`**, which grew two **optional, inert-by-default** params for this: `tilt` (rotation about the local X axis applied after yaw as `Basis(UP, yaw) * Basis(RIGHT, tilt)`, used identically for the visual basis and the `CollisionShape3D` transform so a leaning stone's collision matches) and `color_override` (used only when `a > 0`, giving artifacts the weathered `ARTIFACT_STONE_*`/`ARTIFACT_MOSS` greys — deliberately distinct from the warm `RAMP_*` block ramps). Glow is the only extra geometry: at most `ARTIFACT_MAX_ACCENTS` (4) real `MeshInstance3D`s per artifact via `_spawn_artifact_accent`, sharing one unshaded emissive material (`_get_artifact_glow_material`, cyan, energy 3.0 — above `main.tscn`'s `glow_hdr_threshold` 0.85) with `cast_shadow` OFF. **Reward:** 3-5 ordinary coins on a ring round the base plus **exactly one gem** (`coin.make_gem()`, before `add_child` per coin.gd's contract) at the centre, offset by the shape's `gem_offset` for the two shapes whose centre is solid stone. These are ordinary chunk-local coins — the road station-claim logic is untouched. **Ordering gotcha:** the reward coins are settled through `_settle_coin_y` **before** the artifact's own footprint is appended to `obstacles`; settling after would perch them on the footprint circle's top, floating them metres up over the three mostly-hollow shapes. The footprint is appended last (`climbable = true`), so crocodiles avoid the artifact and road coins perch on it like any block. **Skipped honestly:** the optional proximity shimmer loop — `sound_manager.get_loop_player()` returns a non-positional `AudioStreamPlayer`, so a per-artifact hum would need a new positional audio path plus a per-frame proximity scan.

**Rare nomad camps — dome-hut villages round a fire pit (~1 chunk in 31).** `spawn_camp_in_chunk` is the artifact pattern applied to a *lived-in* landmark instead of a ruin: called from `create_chunk` **after `spawn_biome_content_in_chunk` and before `_build_block_multimesh`**, so 3–6 bone-white dome huts (2–3 stacked shrinking `create_box` tiers, the top one shortened into a cap, plus a dark doorway box facing the fire), a `CAMP_FIRE_STONES` (7) ring of dark stones, crates and tether posts all join the chunk's **single MultiMesh and single `BlockCollision` body** — a whole village costs **one** extra draw call and **zero** extra physics bodies. That one extra is the fire's ember: `_spawn_artifact_accent` grew an **optional trailing `material` param** (null keeps the artifacts' cyan glow, so every existing call site is unchanged) and camps pass `_get_camp_ember_material()` — a second lazily-created shared unshaded emissive material, **warm orange, energy 2.5**, deliberately the opposite temperature to the artifacts' cold cyan, and one material for every ember ever spawned. The palette (`CAMP_HUT_A`/`CAMP_HUT_B` bone-white, `CAMP_STONE`, `CAMP_WOOD`) is likewise distinct from both the warm `RAMP_*` block ramps and the artifacts' grey-green. Fire stones and doorways pass `collide = false` (visual-only clutter); huts, crates and posts collide.
- **Nothing solid in a camp overlaps anything else solid, and `_camp_spot_clear` is the single test that guarantees it.** Huts sit on evenly-spaced ring slots, but the ring radius is drawn *per hut* over a 2.5 m range and the angle is jittered ±0.25 rad, so the slots are no guarantee: at `CAMP_HUT_MAX` (6) an adjacent gap can shrink to 0.547 rad, putting two huts 2.16 m apart with footprint radii summing to 4.29 m. Measured before the test existed, **38% of camps had a pair of fused, interpenetrating domes** (35 of 36 six-hut camps) — and both huts collide, so it was a merged blob the player walked into. Props had the same bug one scale down — 3–6 crates and 2–3 posts share one 2.0–4.0 m ring, so testing them against the huts alone still left **a third of camps with an interpenetrating crate/post pair**. So every solid the camp builds — huts, crates, posts — now runs through `_camp_spot_clear` against **everything solid already built** (the accumulating `solids` list, not just the huts), and a colliding candidate is **dropped, not retried** (the same rule, for the same reason: a village pitched around what fits reads better than a retry loop that can still fail). So a camp is 3–6 huts *minus* drops — 3.7 on average — and a throwaway headless generator sweep over 710 camps measured **0 interpenetrating, down from 33.9%**, while leaving the camp count itself untouched at 710. A drop does **not** consume the same draws as a placement (it skips `create_box`'s yaw/colour/roughness draws, and a dropped hut skips all of `_camp_hut`) — that is harmless only because the camp RNG is **private to the camp** and the rarity/placement rolls all happen before any geometry is drawn. Don't lift the drop-mid-build pattern onto a shared chunk stream.
- **Placement is split across two functions, and the split is load-bearing.** `_camp_at(chunk_pos)` is the pure rarity roll on its own independent hash stream — `hash(Vector3i(cx * 40960001, cy * 26463089, run_seed ^ CAMP_SALT))`, coordinate primes deliberately different from the object/artifact (73856093 / 19349663) and biome (83492791 / 15485863) streams — returning `{}` or `{ "seed": int }`; it consumes **zero** draws from the chunk RNG. It holds **no candidate loop**: when it runs the chunk has no geometry yet, so the only tests available are road + river, which reject almost nothing (measured: 11 of 121 chunks), while the test that actually rejects is overlap with the chunk's ~12 scattered blocks. With the loop there, ~9% of rolled camps were built and camps landed ~10× rarer than intended. The `CAMP_PLACE_TRIES` (4) loop therefore lives in `spawn_camp_in_chunk`, where `obstacles` exists, and each try is judged by `_biome_spot_ok(chunk_center, x, z, CAMP_RADIUS 9.4, CAMP_ROAD_CLEARANCE 22, obstacles)` — the existing single home of the river + road-clearance + overlap rule. Measured survival is 14% (86% of rejections are overlap), so `CAMP_CHANCE` is tuned to **0.18** → ~1 camp per 31 chunks. Every try failing means **no camp** — a camp shoved through a mountain massif reads worse than a chunk without one.
- **Crocodile exclusion is one footprint, not a special case.** The camp appends a single round `CAMP_RADIUS` (9.4 m) **non-climbable** footprint at its centre — one circle, no per-hut footprints, because `CAMP_RADIUS` is picked to bound the widest hut on the outermost ring (`CAMP_HUT_RING_MAX` 6.5 + hut radius 2.86 = 9.36 ≤ 9.4), which is also what makes the placement test a true bound on the stone it admits — and `spawn_crocodiles_in_chunk` already rejects candidates within `ob.radius + min_object_clearance` of a footprint — so a camp reads as a calm pocket with **no edit to the crocodile spawner**. Its retry budget absorbs the rejections, so the croc **count** is unchanged — but the **positions are not**: a rejected candidate skips the successful spawn's `rotation.y` draw, shifting the rest of that chunk's crocodile stream (exactly like the river skip beside it). Within-run determinism still holds unconditionally, since the camp footprint is a pure function of chunk coords + `run_seed`.
- **Boss exclusion is by construction, not by code.** The camp test measures distance to road **station centres** (that is all `_road_lateral_distance` computes), and a boss does not stand on its station centre — `_boss_at` offsets it `BOSS_FORWARD_OFFSET` (8) *along* the tangent as well as up to `BOSS_LATERAL_MAX` (4) across it, so **both legs belong in the bound**: `CAMP_ROAD_CLEARANCE` (22) **must** exceed `CAMP_RADIUS` (9.4) `+ sqrt(BOSS_FORWARD_OFFSET² + BOSS_LATERAL_MAX²)` (8.94) = 18.34 — 3.66 m of slack, *not* the 8.6 the lateral leg alone suggests. With that, a boss can never stand in a camp — `spawn_bosses_in_chunk` is **untouched**. Likewise `CAMP_EDGE_MARGIN` (12) > `CAMP_RADIUS` (9.4) keeps a whole village inside its own chunk, never straddling a seam. Re-check both inequalities if any of those constants are retuned.
- **Reward: 2–4 ordinary coins by the fire and deliberately NO GEM** — the guaranteed gem stays the artifacts' distinction, so "an ancient prize worth a detour" doesn't flatten into "a village you walked through". Same **ordering gotcha** as artifacts: the coins settle through `_settle_coin_y` **before** the camp footprint is appended, or the non-climbable 9 m circle would skip every one. They can't collide with the road's station-claim logic either — 22 m of clearance versus a `road_width_max / 2` (10 m) scatter band.

**Treasure chests — a 1.3 m box opened on touch for a coin shower (~1 chunk in 13).** The third and deliberately *smallest* member of the artifact/camp family, built on the identical recipe: `_chest_at(chunk_pos)` is the rarity roll **alone**, on its own independent hash stream — `hash(Vector3i(cx * 86028121, cy * 50331653, run_seed ^ CHEST_SALT))`, coordinate primes deliberately distinct from the object/artifact (73856093 / 19349663), camp (40960001 / 26463089), biome (83492791 / 15485863) and croc-roll (179424673 / 32452843) streams — returning `{}` or `{ "seed": int }` and consuming **zero** draws from the chunk RNG. The `CHEST_PLACE_TRIES` (4) candidate loop lives in `spawn_chest_in_chunk`, where `obstacles` exists, judged by `_biome_spot_ok(chunk_center, x, z, CHEST_RADIUS 1.5, CHEST_ROAD_CLEARANCE 10, obstacles)` — the *same* split, for the *same* reason artifacts and camps both had to have their loop moved out of the roll (no geometry exists yet when the roll runs). It is called from `create_chunk` **after `spawn_camp_in_chunk` and before `_build_block_multimesh`**, last of the four landmarks so a chest can never be placed inside a camp or an artifact, and so its wood and brass join the chunk's **single MultiMesh and single `BlockCollision` body**.
- **Rarity is tuned from a measured survival rate, and the number means something different here than it does for artifacts.** Measured over a throwaway headless sweep of 41×41 = 1681 chunks: 136 chunks rolled a chest and **134 built one — 98.5% survival, 1 built chest per 12.5 chunks** at `CHEST_CHANCE` **0.08**. Survival is that high because `CHEST_RADIUS` (1.5 m) is a sixth of a camp's 9.4 and a fifth of an artifact's 7.0, so the overlap test — which rejects 86% of camp candidates — almost never fires. `CHEST_CHANCE` is coincidentally the same 0.08 as `ARTIFACT_CHANCE` and produces a landmark **twice as common**, because an artifact only survives placement 59.5% of the time.
- **Three `create_box` calls, one of them hinged.** Body (1.3 × 0.75 × 0.9, `CHEST_WOOD`, collides), a brass waist band (`CHEST_BRASS`, `collide = false` — 6 cm of trim inside the body's own collision box), and the lid, tilted open with the same `tilt` param the artifacts' leaning monolith uses. **The lid is hinged, not merely tilted, and the difference is visible:** `create_box` rotates a box about its own *centre*, so tilting a lid parked on the rim drives its rear half straight down through the body — at the widest angle the back corner sinks 0.25 m into a 0.75 m box. `spawn_chest_in_chunk` instead places the centre where a lid hinged on the **rear rim** would land (rotate the rest offset `(0, +h_y, +h_z)` about the hinge at `(0, body_top, −h_z)`). Sign gotcha: `Basis(RIGHT, t)` sends `z` toward `−y`, so the lid opens on a **negative** tilt. Measured over 20 chests: lid bottom sits exactly on the rim (0.000 m sink) and the whole chest reaches 0.924 m horizontally, inside `CHEST_RADIUS`.
- **Reward is `collect_coin(1)` × N staggered, never `collect_coin(N)` and never real coin nodes — this is mechanical, not decorative.** The coin economy counts **pickups, not value**: the streak multiplier steps every `STREAK_COINS_PER_STEP` (10) *pickups*, so one `collect_coin(12)` is a single link in the chain and a chest would never light the streak up at all. `scripts/treasure_chest.gd` pays `CHEST_COINS_MIN..MAX` (8–15, drawn from the chest's own seeded RNG) one coin at a time over `CHEST_BURST_DURATION` (0.8 s) — comfortably inside the 2.5 s `STREAK_WINDOW`, so the whole burst is one unbroken chain — and the extra-life threshold, the HUD and the `play_coin` blip all come free off the existing path. Its `_process` uses a `while`, not an `if`: at 15 coins the gap is ~53 ms, which one frame hitch would overrun. **Deliberately NO GEM**, the same reward-hierarchy rule that kept gems out of camps.
- **The open trigger is the chest's ONE non-batched node, and it has no mesh.** An `Area3D` (`collision_layer = 0`, `collision_mask = 1`, `TRIGGER_RADIUS` 2.0 sphere, the `coin.tscn` shape) parented to the chunk mesh, so it frees with the chunk — draw calls do not move at all. It shares one static `SphereShape3D` across every chest ever spawned, is `set_process(false)` until opened, and `set_deferred("monitoring", false)`s itself on open (a direct write is blocked from inside `body_entered`). Built by `set_script` + `add_child` + `setup()`, the `ability_effect.gd` shape, so there is no `.tscn` to keep in step. The lid pop is one `ability_effect.gd` flash parented to the **chunk**, not the chest — the chest frees itself when the burst ends. `ponytail:` a real lid swing would need the lid lifted out of the MultiMesh into its own `MeshInstance3D`, i.e. a draw call per chest; skipped.
- **Opened state is per-run and chunk-local, on purpose — there is no opened-chest registry.** A chest regenerates *closed* when its chunk unloads and rebuilds. That is exactly what road coins already do, and the road's strictly-increasing X makes walking far enough backwards to re-farm one a slow deliberate act rather than an accident.
- **Footprint is one small CLIMBABLE circle** (`CHEST_RADIUS` 1.5, top 0.75). Climbable is right for a 1 m box: a road coin whose column crosses it perches on the lid instead of being skipped (the non-climbable rule exists for trees, whose top is 5 m up in a canopy). `CHEST_ROAD_CLEARANCE` (10) equals `road_width_max / 2`, so a chest never stands mid-trail; `CHEST_EDGE_MARGIN` (4.0) exceeds both `CHEST_RADIUS` and the 2.0 trigger radius, so neither box nor pickup sphere straddles a seam. **Measured** (17×17 chunks, every spawner on, chests on vs off): all 269 chunks without a chest have byte-identical block collision, and **not one crocodile or coin moved anywhere** — 289/289 identical on both, stronger than camps manage, because a 1.5 m circle plus `min_object_clearance` is a 3 m disc in a 50 m chunk. The croc-stream shift mechanism still exists in principle; this footprint is just too small to have fired. Within-run determinism holds unconditionally: the same sweep regenerated 289 chunks twice with byte-identical blocks, crocodiles, coins and chest spots.
- **Multiplayer (phase 1, known and accepted):** opening is per-peer and local — the trigger fires for whoever walks into their **own** copy, so a chest one peer has opened still stands closed for another. Contested-chest arbitration belongs to the same claim machinery the epic defers for coins (`godot-test1-s86.5`).

### Player: character switching + procedural animation
`scripts/player_controller.gd` (a `CharacterBody3D`) is the player. Two non-obvious systems:
- **Character switching** (E key): cycles the `CHARACTERS` array, freeing the old model and instancing the new `.tscn` under the `$CharacterModel` node.
- **Procedural limb animation**: there is no `AnimationPlayer`. After loading a character, `setup_animation_references()` looks up child nodes **by exact name** — `Body`, and under it `LeftArm`/`RightArm`/`LeftLeg`/`RightLeg`. Walk/jump/idle poses are driven by sine waves on those nodes' rotations. **Any new playable character scene must use this exact node naming** or it will load but stay frozen.

### Camera view cycle (C key): third-person → first-person → front
Pressing **C** (the `toggle_camera` action, polled with `is_action_just_pressed` in `_physics_process` so synthesized touch input works) **cycles three views**: the shipped 3rd-person boom, a first-person view from the active character's eyes, and a **front/mirror** view whose camera stands ahead of the hero looking back — their face in frame, and the ground behind them. State is `var view_mode: int` over the `ViewMode` enum (`THIRD_PERSON` / `FIRST_PERSON` / `FRONT`, **in cycle order** — `(view_mode + 1) % ViewMode.size()` is the whole cycle, so adding a fourth stop is one enum entry). It is typed `int`, not `ViewMode`, because GDScript will not implicitly narrow the modular-arithmetic result back into the enum type. Design rules, all in `player_controller.gd`:
- **The front view is the SAME boom, yawed 180° in pivot space** — `Basis(Vector3.UP, PI) * third_person_arm_transform.basis`, with the cached origin and the cached `spring_length` untouched. A `SpringArm3D` slides its children along its own **+Z**, so the flip moves the camera from 8.25 m behind to 8.25 m in front, and the camera (which looks down its own −Z) is turned back toward the hero by the same flip. Two things fall out for free: the boom stays **collision-clamped**, so backing the front camera into a block slides it in rather than clipping through; and `camera.position` is still never written (the SpringArm gotcha below). The model stays **visible** — it is the whole point of the view — so the FP model-hide is the `FIRST_PERSON` branch alone, and the respawn blink treats front exactly like third-person (`view_mode != ViewMode.FIRST_PERSON` is the blink condition).
- **CONTROLS ARE NOT MIRRORED, and that is a decision, not an oversight.** In the front view A/D and the mouse turn the **body** exactly as they do in third-person; only the picture is mirrored. Inverting the inputs to match the screen reads clever and plays terribly — the world stops agreeing with the stick. Mouse *pitch* is likewise unmirrored at the source (it still drives `camera_pivot.rotation.x`), which the flipped boom renders as a mirror — inherent to standing in front of someone, and the cost of reusing one rig instead of adding a second camera.
- **`scripts/view_selfcheck.gd` is the runnable proof** (`godot --headless --path . --script res://scripts/view_selfcheck.gd`, prints `SELFCHECK OK`). It measures, for each of the three views, where the camera ends up along the body's facing axis, whether it looks back at the hero, and whether `$CharacterModel` is visible. It exists because a sign error in that basis puts the "front" camera **behind** the hero — an ordinary third-person view with a mirrored pitch, with no error anywhere and nothing to see on a headless machine. Mutation-tested: dropping the flip moves the measurement from +8.00 m to −8.00 m and the check fails.
- **One camera on a collision-aware boom.** The rig is `$CameraPivot/CameraArm/Camera3D`, where `CameraArm` is a `SpringArm3D` (`spring_length` 8.25, −14° pitch; the camera keeps a residual −1° so the shipped framing is visually identical to the old fixed `(0,2,8)` offset). The arm clamps its length against world geometry, so backing into a block slides the camera in instead of clipping through; `_ready()` calls `camera_arm.add_excluded_object(get_rid())` so it never collides with the player's own capsule. `_apply_view_mode()` is idempotent and does all the work: FP sets `camera_arm.spring_length = 0.0` and `camera_arm.transform = Transform3D(Basis.IDENTITY, _first_person_eye_position())` (zero length ⇒ no collision cast ⇒ FP bypasses the arm for free; identity basis + zeroed camera residual pitch make the pivot's mouse-look pitch alone the look pitch) and hides `$CharacterModel`; 3rd person restores the *cached* arm transform + spring length (`third_person_arm_transform`/`third_person_arm_length`, captured in `_ready()`) and re-shows the model. Mouse-look needs no changes: it only drives body yaw + pivot pitch, which serve both views.
- **Eye height tracks Teibi's scale.** `_first_person_eye_position()` derives eye Y from `collision_shape.scale.y` × `FIRST_PERSON_EYE_HEIGHT` (1.65), so small/giant Teibi looks from the right height; `_apply_teibi_scale()` and `set_active_character()` both re-run `_apply_view_mode()` when `first_person` (cheap, idempotent, defensive).
- **SpringArm gotcha — nothing may write `camera.position`.** A `SpringArm3D` overrides its children's local position every physics frame (it slides them along its local Z), so any code that sets `camera.position` is silently fought and undone. The bite shake therefore drives `Camera3D.h_offset`/`v_offset` (view-space slides of the lens, unaffected by the arm, identical in both views) and settles both back to 0.0. Any future camera motion must use those offsets or move the arm/pivot — never the camera's own transform.
- **Speed FOV + eased keyboard turn.** `camera.fov` eases each frame from `FOV_BASE` (75) toward `FOV_MAX` (97) as horizontal speed climbs from walk toward Windman's air speed, plus a transient `fov_punch` (Air Rush kicks it +12, decaying fast) — a `Camera3D` property, so it applies in both views. Keyboard turning is eased: `handle_turning` banks the turn into `camera_yaw_lag`, applied to `camera_pivot.rotation.y` and decayed at `CAMERA_TURN_EASE` (10/s), so the camera trails a keyboard turn and catches up — while **mouse turns stay 1:1** (they rotate the body in `_input` without touching the lag). The lag is zeroed in `reset_position()`.
- **View mode is a preference:** nothing in `reset_position()` / `restart_game()` / `_respawn_in_place()` touches `view_mode` or the camera rig, so the chosen view survives respawn, restart, and character switches. The touch UI has a small "View" button (top-centre, next to the steer toggle in `touch_controls.gd`) firing the same action through `_fire_action()` — its label is deliberately the mode-agnostic "View", so the third stop needed **no UI change** (and no new CSV row; the tightest width budget in the game is that button).

### Mobile / touch controls (web build, phone with no keyboard)
The goal is a **web build playable on a phone with no keyboard**: the player physically *steps* to walk, *tilts/twists* the phone to steer, and taps on-screen buttons for the keyboard-only actions. Three new pieces, all **touch-only** and wired by groups — `player_controller.gd` is essentially untouched.

**The KEY design rule: synthesize the EXISTING input actions, don't add controller code paths.** `player_controller.gd` already reads everything through named actions (`move_forward`, `turn_left`/`turn_right`, `jump`, `switch_character`, `special_ability`). The mobile code **drives those same actions** — analog held actions via `Input.action_press(action, strength)` / `action_release(action)`, discrete buttons via `Input.parse_input_event(InputEventAction)` — so movement, animation, and abilities keep working with **zero** controller changes (the lone exception is the one-line mouse-capture guard below).

The three components:
- **`scripts/mobile_sensors.gd`** (`class_name MobileSensors`, a bare `Node`) — the **sensor abstraction** that hides where motion data comes from. It supports **both** sources behind one source-agnostic API and prefers whichever is delivering live data: **native Godot `Input` sensors** (`get_accelerometer()`/`get_gravity()`/`get_gyroscope()`/`get_magnetometer()`) first, else a **`JavaScriptBridge` DOM shim** (`window.addEventListener('devicemotion'/'deviceorientation', …)` polled into GDScript). Public API: `enabled`, `has_data()`, `linear_accel()` (gravity removed — the *step* signal), `tilt()` (roll/pitch vs neutral — the *steer* signal), `yaw()` (twist vs neutral, absolute compass alpha when present, else integrated gyro), `request_permission()`, `calibrate()` (capture current pose as neutral). **iOS gotcha:** Safari fires **no** motion events until `DeviceMotionEvent.requestPermission()` is granted from a *user gesture* in a *secure (HTTPS) context* — `request_permission()` feature-detects this and only attaches listeners on `'granted'`. (GitHub Pages is HTTPS so it works there; a plain-`http` LAN host via `./serve.sh` may not grant motion on iOS.) **GC gotcha:** the JS callbacks are stored in member vars (`_js_motion_cb`/`_js_orientation_cb`) so they survive garbage collection — a dropped reference silently detaches the listeners. Every JS touch is gated behind `OS.has_feature("web")`, so on desktop/editor native reads zero, `has_data()` is false, and nothing throws.
- **`scripts/mobile_input.gd`** (a bare `Node` added once under `Main` in `main.tscn`, like `CrocodileLODManager`, in group `"mobile_input"`) — the **driver**. It owns a `MobileSensors` child and each frame: runs **step peak-detection** on `linear_accel().length()` (rising-edge crossing of `STEP_ACCEL_THRESHOLD` + `STEP_MIN_INTERVAL` refractory) feeding a decaying `walk_energy` → drives `move_forward` at an analog strength; and computes **steering** (tilt-roll default / twist-yaw toggle) through a deadzone→scale → `turn_left`/`turn_right`. Public API for the UI: `enable()`/`disable()`, `calibrate()`, `set_steer_mode(mode)` (also recalibrates — the toggle doubles as a re-zero, important because twist-yaw drifts), `request_permission()`. **It is idle unless `active`:** `_physics_process` early-returns while `!active`, so it never writes `Input` on desktop and the keyboard owns the actions; `disable()` releases any held action so nothing latches. `enable()`/`set_steer_mode()` call `calibrate()` so steering is centred from however the player is holding the phone. The `STEP_*` and `STEER_*` constants at the top are **starting defaults** meant to be tuned on a real device (Task 6 could not — no hardware in the build env).
- **`scenes/ui/touch_controls.tscn` + `scripts/touch_controls.gd`** (a `Control` under the `HUD` `CanvasLayer`) — the on-screen UI. Buttons (built in code in `_build_ui()`): **Jump**, **Special (F)**, **Switch (R)** stacked bottom-right; a small **steer-mode toggle** top-centre; and a first-run **"Tap to enable motion controls"** full-rect overlay that satisfies the iOS permission gesture then `enable()`s the driver and hides. It finds the driver via the `"mobile_input"` group (no hard refs, like `ability_hud.gd`).

**CRITICAL gotcha — `switch_character` is handled in `player_controller._input()`, NOT polled.** `Input.action_press("switch_character")` sets only the *polled* state and would never dispatch an `InputEventAction` through `_input()`, so the switch would silently not fire. Its button **must** use `Input.parse_input_event(InputEventAction)`, which flows the synthetic event through the full pipeline (including `_input()`). `touch_controls.gd` funnels **all three** action buttons through one `_fire_action()` → `parse_input_event` path for consistency (a pressed event now, a matching released event flushed at the top of the **next** `_process` frame via a small `_actions_to_release` queue — a guaranteed-later frame, not a same-frame `call_deferred`, so the press reliably lasts one full frame and `is_action_just_pressed`/`_input()` each see exactly one press).

**Live on-device tuning panel (`scripts/mobile_settings_panel.gd`, a `Control` under the `HUD` `CanvasLayer`, built fully in code like `touch_controls.gd`).** Because no hardware was available when the controls were written, the `STEP_*` / `STEER_*` tunables are **no longer `const`** — they are runtime-adjustable `var`s on `mobile_input.gd` (each starts at a `DEFAULT_*` const so behaviour is byte-for-byte identical until a slider is moved). A small **⚙ Tune** button (top-left, below the lives HUD) opens a translucent panel with a **live diagnostics read-out** (sensor source `native`/`js`/`none`, `accel now`/`peak`, `walk_energy`, step count, tilt/yaw degrees — the `peak` is the number to set the step threshold just under), **one slider per tunable** (step threshold/power/decay/min-interval, steer deadzone/full-angle), an **Invert steering** checkbox (negates the signed steer strength — fixes a reversed-feel phone), plus **Recalibrate**, **Reset to defaults**, and **Close**. The panel talks to the driver only through the `"mobile_input"` group via its public API: `get_tuning()` / `set_tuning(key, value)` / `reset_tuning_to_defaults()` / `get_diagnostics()` / `recalibrate()` (a passthrough to `MobileSensors.calibrate()`, re-added because it's now a live UI affordance). **Persistence:** `set_tuning()` (and the load in `_ready()`) read/write a `ConfigFile` at `user://mobile_tuning.cfg` — on web `user://` is IndexedDB-backed, so a player's dialled-in feel **survives a page reload** (measured on the deployed build in both Chromium and WebKit, though see the site-storage-eviction caveat under "Personal best-run records" — it will vanish wherever the browser purges site data); a missing file just keeps the defaults (first-run save does not error). `MobileSensors.current_source()` reports which source last fed data, for the diagnostics line.

**Gating convention (matches the project's "visual/behavioral changes are platform-gated" rule):** the UI's visibility is gated on `DisplayServer.is_touchscreen_available()` (plus a web `matchMedia('(pointer: coarse)')` fallback behind `OS.has_feature("web")`); the driver writes no `Input` when disabled; and `player_controller._ready()` **skips mouse capture** when `is_touchscreen_available()` (the only edit to the controller — `Input.set_mouse_mode(MOUSE_MODE_CAPTURED)` is wrapped in `if not DisplayServer.is_touchscreen_available():`). On desktop the touchscreen probe is false everywhere, so the UI is hidden, the driver never enables, and keyboard+mouse play is **byte-for-byte unchanged**. The tuning panel is gated by the same `MobileSensors.is_touch_session()` rule, so it too is hidden and inert on desktop.

**Debug keys (editor/desktop testing, all outside the project input map like F3):** **F4** toggles the `MotionDebug` sensor readout (`scripts/motion_debug.gd`, a `Label` under `HUD`; hidden by default in release/web, starts visible only in `OS.is_debug_build()` — it prints raw `Input.*` sensors plus the `MobileSensors` API output); **F5** force-enables the `mobile_input` driver; **F6** force-shows the touch UI; **F7** force-shows the tuning panel's ⚙ gear.

### Per-character special abilities (F key)
Each character has **one signature power**, fired with **F** (the `special_ability` input action, defined in `project.godot`). All abilities live in `player_controller.gd` under **SECTION 8** and share one mechanism: `try_activate_ability()` dispatches on the current character name, and every ability is gated by a **per-character cooldown** (`ability_cooldowns: Array[float]`, one slot per `CHARACTERS` entry, durations in the `ABILITY_COOLDOWN` dict). The abilities:
- **windman → Air Rush**: launches up + forward and flies at `WINDMAN_AIR_SPEED` (≈5× walk) with gravity softened by `WINDMAN_GRAVITY_FACTOR` for `WINDMAN_BOOST_DURATION`. Implemented by `windman_boost_timer`, read in the gravity step and in `calculate_current_speed()` (boost speed applies **only while airborne**).
- **primm → Phase Step**: an instant forward blink that passes *through* a block and is **guaranteed to land in open space on the far side** — it never gets stuck inside geometry. Rather than a blind fixed hop it scans outward from `PRIMM_BLINK_DISTANCE` in `PRIMM_BLINK_STEP` increments (up to `PRIMM_BLINK_MAX_DISTANCE`) for the first spot where the body fits, probing via `_is_body_blocked_at()` (a sphere at capsule-centre height so the flat ground never counts as blocked). If nothing is clear within reach, the blink doesn't fire and costs no cooldown.
- **teibi → Resize**: cycles normal → small → giant → normal (`teibi_size_state`). `_apply_teibi_scale()` scales **both** `$CharacterModel` and `$CollisionShape3D`, moving the collision node so the capsule's **bottom stays pinned to the ground** at any scale (no sinking/launching). Giant form sets `is_giant` (exposed to crocodiles via `crushes_crocodiles()`) and **can't jump** (the jump step checks `not is_giant` — too heavy). An altered form (small **or** giant) **auto-reverts to normal after `TEIBI_FORM_DURATION` (10 s)** via `teibi_form_timer` ticked in `_update_ability_timers()`, so Teibi can never get stuck transformed; the timer is a *total* budget for the whole excursion (a small↔giant switch does not refill it). `_revert_teibi_to_normal()` is the shared snap-back used by the timeout, character switch, and respawn.
- **phoboman → Stink Wave**: spawns staggered expanding `ability_effect.gd` waves and calls `flee_from(origin, PHOBOMAN_FLEE_DURATION)` on every node in the `"crocodile"` group.

Two cross-cutting pieces:
- **`scripts/ability_effect.gd`** — a self-building, self-freeing expanding/fading sphere "wave". Spawned by attaching the script to a bare `MeshInstance3D` (`set_script` + `setup(color, radius, lifetime, delay)`), parented to the player's parent so it outlives nothing and leaks nothing. Reused for the stink wave plus small flashes for the gust/blink.
- **`scripts/ability_hud.gd`** (the `AbilityHUD` `Control` under the `HUD` `CanvasLayer`, top-right under the coin counter) — an asset-free radial cooldown dial drawn in `_draw()`. It finds the player via the `"player"` group and reads the contract methods `get_ability_name()` / `get_ability_cooldown_ratio()` / `get_ability_remaining()` / `is_ability_ready()`.

Transient ability state (air boost, giant form, odd size) is cleared on respawn (`_reset_ability_states()` in `reset_position()`) and on character switch (in `set_active_character()`), so a power never bleeds across a death or a swap.

### Two parallel enemy implementations (important gotcha)
There are **two** enemy AI scripts with different contracts; know which one you're touching:

| | `piglet_crocodile_ai.gd` | `enemy_controller.gd` |
|---|---|---|
| Scene | `scenes/characters/piglet_crocodile.tscn` | `scenes/enemies/cyborg_piglet.tscn` |
| Groups | `crocodile`, `enemy` | `enemies` |
| Behavior | Wanders, **chases player** within `DETECTION_RADIUS` (loses scent when player jumps / leaves ground); crocodiles are **solid to one another** (bump and push apart, no overlap) | Wanders only |
| On player hit | calls `player.reset_position()` | calls `player.game_over()` |
| Spawned by terrain? | **Yes** | **No** |

`piglet_crocodile_ai.gd` is the live enemy: it's what `endless_terrain.gd` spawns and it calls `reset_position()`, which the player implements. `enemy_controller.gd` / `cyborg_piglet.tscn` are newer and **not yet wired in** — nothing spawns them, and their death contract `player.game_over()` does **not exist** on the player (only `reset_position()` does), so their collision is currently a no-op. If you intend to make cyborg piglets functional, either spawn them from the terrain and add a `game_over()` method, or converge them onto the existing `reset_position()` contract.

`piglet_crocodile_ai.gd` also implements two hooks for the player's special abilities (see "Per-character special abilities"): `flee_from(origin, duration)` makes it turn tail and run from the player (a `is_fleeing` state that **overrides chase/wander**, used by Phoboman's Stink Wave; a fleeing croc is harmless), and in `_on_player_collision` it checks `player.crushes_crocodiles()` first — if true (giant Teibi) it `queue_free()`s itself instead of biting.

**Per-crocodile variety.** In `_ready()` each crocodile rolls two independent randoms so the pack isn't uniform: a single **speed** multiplier (`SPEED_RANDOM_FACTOR`, ±50%) applied to *both* `move_speed_instance` and `chase_speed_instance` (so a "fast" croc is fast at everything yet its chase still outpaces its own wander), and a uniform **size** scale (`SIZE_RANDOM_FACTOR`, ±25%) applied to the whole `CharacterBody3D` via `scale` — this grows/shrinks the visual model and the physics capsule together, and gravity settles each croc onto the ground regardless of size. The model's own local scale stays `1`, so `model_base_scale` and the procedural body animation are unaffected by the body scale. These are rolled from the per-instance `rng`, which is **seeded deterministically by the terrain**, so size/speed are a pure function of chunk coords + croc index + `run_seed` exactly like the *positions* — a crocodile regenerates identically when its chunk is revisited, and every peer in a future multiplayer session derives the same pack from the shared seed. (This reverses an earlier single-player-era choice where `rng` was `randomize()`d and size/speed were deliberately non-deterministic.) The mechanism is the `setup_as_boss` shape one level down: `endless_terrain._croc_roll_seed(chunk_pos, index)` is **its own independent hash stream** — `hash(Vector3i(chunk.x * 179424673 + index, chunk.y * 32452843, run_seed ^ CROC_ROLL_SALT))`, coordinate primes deliberately distinct from the object (73856093 / 19349663), biome (83492791 / 15485863) and camp (40960001 / 26463089) streams — and it draws from **no** `RandomNumberGenerator` at all, so the crocodile spawner's own sequence is untouched and every croc **position is byte-for-byte what it was before** (measured over an 81-chunk field: 820 crocodiles, positions identical, 819 sizes changed — the one unchanged is the boss, which takes no roll). **Call-order contract, same as `setup_as_boss`:** the terrain calls `setup_roll_seed(seed)` on the instance **before** `add_child`, because `_ready()` is where the rolls happen. `index` is the spawn slot for ground crocodiles and `-1 - count` for platform guards, so the two spawners can't hand the same seed to two crocs in one chunk. The croc keeps `rng.randomize()` as the **fallback when no seed was given** (`has_roll_seed` false), so `piglet_crocodile.tscn` still runs standalone. Bosses are unaffected either way — the `is_boss` branch takes neither roll. Still non-deterministic and deliberately out of this contract: `time_since_direction_change`, which seeds off the global `randf()`. `_ready()` also applies the **difficulty gradient**: `chase_speed_instance` is multiplied by `1.0 + clampf(absf(global_position.x) / DISTANCE_SPEED_SCALE_DENOM, 0.0, DISTANCE_SPEED_SCALE_MAX)` (+60% at 3 km; valid in `_ready` because the terrain parents the croc before `_ready` runs), then clamped to `MAX_CHASE_SPEED` (8.5) — without the cap a top-rolled far croc (5.5 × 1.5 roll × 1.6 distance = 13.2) would outrun even a *running* player (slowest character runs at 9.0), breaking the running-escapes hatch, and `BASE_CHASE_SPEED` is **5.5 — deliberately above WALK_SPEED 5.0** so a walking player gets caught and must run or use abilities to escape. **Crocodiles are solid to each other:** the scene sets the body's `collision_mask = 3` (layers 1 **and** 2), where layer 2 is the crocodile layer — so `move_and_slide` pushes two bumping crocodiles apart instead of letting them overlap. `_handle_collisions()` deliberately ignores crocodile-vs-crocodile contacts (no eat-on-touch); the physical push is the whole behaviour. The player stays `mask = 1`, so the *player* still passes through crocodiles physically — player damage is driven entirely by the crocodile's own `_handle_collisions` detecting the player, unchanged.

**The spawn point is a crocodile-free bubble, enforced in world generation.** `spawn_crocodiles_in_chunk` rejects any candidate within `endless_terrain.SPAWN_SAFE_RADIUS` (25 m) of the world origin — a post-draw `continue` beside the river skip, so the RNG sequence is untouched, and the retry budget refills the count (measured: still 10 crocs per bubble-touching chunk). This is the *first run's* only spawn protection: the player's own `clear_nearby_crocodiles()` sweep runs on respawn and restart, never at initial spawn, so before the bubble a fresh boot dropped the player among ~10 crocs, several inside `DETECTION_RADIUS` (15) and chasing on frame one at `BASE_CHASE_SPEED` 5.5 > `WALK_SPEED` 5.0. It lives in generation rather than as a fourth sweep because a pure function of position needs no ordering dance with `_ready()` (the player is ready before any chunk exists) and covers `new_run()` for free. `endless_terrain.SPAWN_SAFE_RADIUS` and `player_controller.SPAWN_SAFE_RADIUS` are the same rule from two ends — keep them in step. **In a multiplayer room that respawn sweep FREES NOTHING** — `clear_nearby_crocodiles()` early-returns on `request_croc_flee(spawn_point, grace + blink, SPAWN_SAFE_RADIUS)` returning true and relies entirely on the relayed flight, because the sync layer's standing contract is that it never creates, re-parents or frees a crocodile (freeing on the master stops it broadcasting those ids and every other peer resumes local AI for bodies the authority no longer has; freeing on a non-master deletes bodies the master keeps sending samples for). So in a room the crocodiles stay solid and present and merely run away, and the guarantee narrows by `flee_from()`'s own two early-returns — bosses, and anything the LOD manager has asleep — neither of which the free-sweep cared about.

**Boss crocodiles (deterministic road-station giants).** Rare "boss" crocodiles stand on the coin road — same scene, same AI, differing only in flags set by `setup_as_boss(body_scale)` in `piglet_crocodile_ai.gd`. **Call-order contract:** the terrain calls `setup_as_boss` on the instance **before** `add_child`, so `_ready()` sees `is_boss` and branches — bosses skip *both* per-instance random rolls (speed and size; their size comes from the deterministic schedule, their chase speed is `minf(BOSS_CHASE_SPEED 7.0 × distance factor, MAX_CHASE_SPEED 8.5)` — walking (5.0) loses, running (9.0+) escapes). Placement lives in `endless_terrain.gd` (`_boss_at(i)` / `spawn_bosses_in_chunk`): boss index `i ≥ 1` owns road station `k = i * BOSS_INTERVAL_STATIONS` (50 stations ≈ 300 m; no boss at spawn), positioned ahead of the station along the heading plus a small lateral offset drawn from an RNG seeded `hash(Vector3i(i, BOSS_SEED, run_seed))` — its **own independent hash stream** like `ROAD_COIN_SEED`; it never consumes a draw from any existing chunk/coin/croc RNG sequence, so the rest of the world regenerates byte-identically. Size schedule: `minf(BOSS_BASE_SCALE 2.5 × (1 + (i−1) × BOSS_GROWTH 0.35), BOSS_MAX_SCALE 6.0)` → 2.5, 3.375, 4.25, 5.125, 6.0, 6.0, … Chunk-claim spawning exactly like road coins (only the chunk where `world_to_chunk(pos)` matches spawns it, parented to the chunk mesh), so outrunning far enough despawns the boss with its chunk — "you escaped it". **Footprint rejection:** `spawn_bosses_in_chunk` takes the chunk's `obstacles` like its siblings and walks `BOSS_PLACE_TRIES` (4) lateral candidates from the same `BOSS_SEED` stream, taking the first clear of every footprint by `ob.radius + BOSS_FOOTPRINT_RADIUS_PER_SCALE (0.7) × body_scale` — **scaled by boss size**, because the croc's collision capsule lies on its side (1.4 m long ⇒ 0.7 m reach at scale 1), so a 6x boss needs ~4.2 m where the ordinary croc spawner's fixed `min_object_clearance` 1.5 would be far too small (measured: half the bosses' primary spots overlap geometry, mostly since biomes added trees/mountains). The candidates are drawn *after* the original lateral draw, so the schedule (station, size, rarity) and every unobstructed boss's position are byte-identical to before. **Claim rule under retries:** `obstacles` only describes one chunk, so the candidate walk **stops** at the first candidate outside the generating chunk — a chunk can only ever spawn a boss whose *first* candidate lies inside it, which makes duplicates impossible; the price is that a boss whose clear candidate falls in a neighbouring chunk is skipped, like the ~8% skipped when all four candidates are blocked. Behavior flags: `flee_from()` early-returns when `is_boss` (Stink Wave immunity — group `"crocodile"` membership is **kept**, the wave finds bosses and they shrug it off); detection radius is `BOSS_DETECTION_RADIUS` 25.0 (**must stay well below `SIM_RADIUS` 45** — same always-awake-when-dangerous invariant as regular crocs); `_on_player_collision` checks `is_boss` **above** the giant-Teibi crush block, so a boss bites giant Teibi instead of being crushed (assumption: a 2.5x+ boss out-sizes giant Teibi). Visuals: `ToonShading.apply_boss_to_mesh` installs a darker red-shifted variant from its own static cache (one shared duplicate per source material, never per-boss), and the per-mesh `visibility_range_end`/margin are scaled by `boss_scale` so a 6x boss doesn't pop in at 60 m. On the not-chasing → chasing transition a boss fires `play_boss_growl()` on the sound manager (null-safe group lookup). Bosses participate in LOD sleep like any croc.

### Crocodile simulation LOD (sleep distant crocodiles, never remove them)
`scripts/crocodile_lod_manager.gd` is a `Node` (named `CrocodileLODManager`, added once under root `Main` in `main.tscn`) that keeps the in-browser frame rate up by **putting distant crocodiles to sleep**. It holds no hard references — it finds the player via the `"player"` group and crocodiles via the `"crocodile"` group. On a throttled tick (`SCAN_INTERVAL = 0.11`, ~9 Hz, **not** every frame) it compares each crocodile's squared distance to the player against `SIM_RADIUS = 45.0`, with a `HYSTERESIS_MARGIN = 5.0` dead-band (wake within 45 m, sleep only beyond 50 m) so a body on the boundary doesn't flicker. It calls `croc.set_lod_active(bool)` **only on a state change**.

The crocodile side of the contract lives in `piglet_crocodile_ai.gd`: it has `var lod_active := true` and `set_lod_active(active)`, which zeroes `velocity` and calls `set_physics_process(active)` — a slept croc's `_physics_process` is not dispatched at all (~460 saved script dispatches per physics tick across the pack). The `if not lod_active: velocity = Vector3.ZERO; return` early-return at the top of `_physics_process` stays purely as a backstop. A slept crocodile stays exactly put with all heading/chase/phase/confinement state preserved, and resumes seamlessly on wake. (The croc scene's old `HitBox` Area3D is **gone** — the script itself documented that nothing ever connected to it, so it was deleted; `set_lod_active` no longer toggles any Area3D monitoring.)

Independent of the simulation sleep, crocs also get a **pure draw cull**: `_ready`'s `_style_model_meshes()` walk sets `visibility_range_end = VISUAL_CULL_DISTANCE` (60) / `visibility_range_end_margin = VISUAL_CULL_MARGIN` (8) on every mesh in the model subtree (and applies `ToonShading.apply_to_mesh` — see "Art-directed look" below), so beyond ~60 m the renderer simply skips the meshes (works in `gl_compatibility`; the universal fog hides the pop). Two independent radii by design: LOD sleep at 45/50 m (simulation), draw cull at 60/8 m (rendering) — the cull is wider than the sleep radius, so a visible croc is never a frozen-mid-stride sleeper close up. Entity counts unchanged in both cases.

**The same scan publishes the danger telegraph.** Inside `_scan_crocodiles()` (zero extra passes) the manager tracks the minimum distance among crocs whose `is_chasing` is true (guarded with `"is_chasing" in croc`) and pushes `sqrt` of it — or `INF` when nobody is hunting — to the `"danger_vignette"` group node via a null-safe `set_danger_distance(d)` call. `scripts/danger_vignette.gd` (a `Control` under the HUD `CanvasLayer`, stacked BELOW `HitFlash` so a bite flash still reads on top) turns that into a red screen-edge vignette (one `ColorRect` with a tiny code-built `canvas_item` shader; alpha eased per frame so the 9 Hz scan doesn't step visibly; `visible = false` when clear so the shader costs nothing) and drives the sound manager's `"heartbeat"` loop — `play()` when danger appears (gated on `is_unlocked()`), `stop()` when it clears, with `pitch_scale` 1.0 → 1.8 and `volume_db` −18 → −6 as the chaser closes `DETECTION_RADIUS` → 0. This works because chasing crocs are always awake (`SIM_RADIUS` ≫ `DETECTION_RADIUS`), so the scan sees every chaser; bosses are in the same group and expose `is_chasing`, so they trigger it with no extra code.

The manager also gates **coin animation** on the same ~9 Hz tick (it is now the small animation/simulation LOD manager for crocs + coins; name kept for history): every node in the `"coin"` group gets `set_process(false)` beyond `COIN_ANIM_RADIUS` (30 m) from the player and `set_process(true)` within, with the same hysteresis (`COIN_HYSTERESIS = 5.0`) and only-on-state-change discipline. Distant coins just stop spinning/bobbing (invisible at 30 m+); collection is Area3D-signal driven and does not depend on `_process`, so a frozen coin still collects normally.

**Awake means near ANY member of the room, not just the local player** (phase 5). `_scan_crocodiles()` builds a `focus_points` array — the local player's position, plus every position the `"mp"` group node's `peer_positions()` returns — and the awake/asleep decision uses the **minimum** squared distance over it (`dist_sq_any`). **The same array (minus the local player) is also handed to `endless_terrain.set_focus_points()`** — see "Terrain focus points" below; waking a crocodile beside a far teammate is only half the job when the master's terrain has not loaded that crocodile at all. `peer_positions()` returns **`null` offline**, so that array is the one-element `[player_pos]` and the whole pass is byte-identical to before multiplayer existed — that null is the load-bearing claim for "solo play is unchanged". The danger telegraph deliberately keeps using `dist_sq_local`: the vignette is *this* player's fear, not the room's, so a croc hunting a teammate 80 m away must not redden our screen. A croc with `remote_driven == true` skips the awake/asleep **decision** (the sync layer owns its `_physics_process`) but is read for the telegraph **first**, so a synced croc chasing us still lights the vignette. See "Multiplayer (phases 3–5)".

Two non-negotiable invariants:
- **`SIM_RADIUS` (45) must stay well above `DETECTION_RADIUS` (15).** Any crocodile that could detect, chase, or touch the player is always fully awake, so near-player behavior is byte-for-byte identical; only crocodiles far out of reach are frozen. If you change `DETECTION_RADIUS`, keep `SIM_RADIUS` comfortably larger (it is currently 3× plus the hysteresis buffer).
- **Crocodiles are slept, never removed.** The manager only flips a flag — it never `queue_free()`s a crocodile — so entity counts are unchanged. The F3 perf overlay's `Crocs (active/total)` line proves this: active is a small handful while total stays large.

### Player death / lives / respawn contract
The player has a **lives system** (`MAX_LIVES = 3` starting hearts, drawn top-left by `scripts/lives_hud.gd`; coins can push `lives` up to `LIVES_CAP = 5` — see "Gameplay loop" below). `lives_hud.gd` holds **no `MAX_LIVES` constant of its own** — it reads the pip total from the player (`maxi(player.MAX_LIVES, player.lives)`) so a 4th/5th heart renders and the old duplicated-constant sync bug can't return. The damage entry point is still the crocodile calling `player.hit_by_crocodile()`, which plays the brief "caught" freeze/flash/shake. When that window ends, `_on_caught_finished()` spends one life and branches:
- **Lives remain → soft respawn in place** (`_respawn_in_place()`): the player stays exactly where it fell and **keeps all coins** — losing a life is the only penalty. **In a room, "in place" becomes "back with the group"**: `MpManager.group_anchor()` answers the group's live anchor (the *same* `_anchor_of()` rule the mid-run join uses — centroid, or the master past `GROUP_SPREAD_MAX` — but read off live presence rather than the join snapshots, with `stale` peers skipped like `peer_positions()` does), and the respawn reuses the join's own `_place_near()` ring probe plus the croc sweep **at the spot actually landed on**. Solo, `group_anchor()` returns `null` and the whole path is byte-for-byte what it was. **The relocation fires on the respawn EVENT and nothing else** — the standing lesson of the drag bug (`godot-test1-s86.17`): `_on_caught_finished()` calls this exactly once per death, so there is no arrival window to gate and `group_anchor()` is deliberately a latch-free pure query. It **composes with the frozen countdown** by moving *at the same moment the respawn settles the body*, so the whole grace freeze and the blink invulnerability after it are spent at the new spot — landing first and freezing afterwards would be a player unfrozen, unswept and standing in the group's crocodiles. **`own_distance_origin` is shifted by exactly the jump**, or dying beside a team kilometres down the road would write *their* distance into `user://best_run.cfg` as this player's personal best (the one thing that field exists to prevent — same re-origin `join_at()` does). `ponytail:` the group can be past this peer's loaded terrain (web streams ~150 m), so the ring probe may judge blocks that do not exist yet and the ground under the landing is built by the terrain's own streaming next frame — harmless while the body is frozen, at worst one shove-out; the upgrade path is building around the anchor first the way `_apply_join_placement()` does, which then also needs its `await physics_frame`. `mp_e2e.sh`'s phase 4 (`--role=respawn`) is the runnable proof, and it carries the solo **negative control** first. The grace period is split into two phases: first a **frozen** window (`RESPAWN_GRACE_DURATION = 1.5` s, one-decimal centred countdown via the `respawn_label` group node) with ability state cleared and crocodiles swept within `SPAWN_SAFE_RADIUS` (one more sweep on the final frame so nothing can bite on the first unfrozen frame); then control returns but the player stays **invulnerable while blinking** for `RESPAWN_BLINK_DURATION` (2.5) more seconds — `respawn_blink_timer` toggles `character_container.visible` on a `RESPAWN_BLINK_CADENCE` (0.1 s) cadence (skipped in first-person, where the model is already hidden) and visibility is restored through the idempotent `_apply_view_mode()` when it expires, so the current view mode is always respected.
- **No lives left → game over** (`_trigger_game_over()`): freezes the player, frees the mouse cursor, updates/saves the best-run records, and raises the Game Over screen (`scripts/game_over_ui.gd`, found via the `game_over_ui` group) via `show_game_over(coins, distance, best_distance, best_coins, is_new_best)` — distance is the headline, with the coin tally, a "Best: NNNm / NN coins" line, and a tween-pulsed "NEW BEST!" flash when the distance record fell. **Enter/Space also restarts**: `_unhandled_input` treats `ui_accept` (which covers both keys out of the box, no `project.godot` change) as the **Play Again** button, which calls `player.restart_game()` — that wipes coins/distance/streak, refills lives, recaptures the mouse, calls `terrain.new_run()` (via the `"terrain"` group) to regenerate the world with a fresh seed, then `reset_position()`.

Invulnerability is enforced in one place: `hit_by_crocodile()` early-returns while `is_caught`, `is_respawning`, `is_game_over`, **or `respawn_blink_timer > 0.0`** (the blink phase); `restart_game()` and `reset_position()` both zero the blink timer (and restore visibility via `_apply_view_mode()`) so the state never leaks across a restart. The "caught" flash comes from `scripts/hit_flash.gd`, whose `flash()` now takes an optional color argument (defaulting to the bite red), so other systems can reuse the full-screen flash in their own tint. `reset_position()` is now only the **hard reset to spawn** `(0,2,0)` (teleport + zero velocity/rotation + `clear_nearby_crocodiles()` + wipe coins + `_reset_ability_states()`) used by `restart_game()` and kept as the crocodile's legacy fallback — a normal bite no longer teleports to origin or clears coins. (Giant-form Teibi still **crushes** crocodiles on contact via `crushes_crocodiles()`, so those never reach the bite path at all.)

### Gameplay loop (score, per-run seed, difficulty gradient)

**Per-run world seed — the determinism contract.** `endless_terrain.gd` holds `var run_seed: int`, rolled once in `_ready()` from a private `RandomNumberGenerator` (never the global RNG) and mixed into **every** deterministic hash site as the third component of a `Vector3i` — the chunk object seed, ground-croc seed, platform-croc seed, `_road_hash01(k)`, the `_road_coins_at(k)` RNG seed, and (as `run_seed ^ SALT`, one salt per independent stream) the artifact / camp / biome / boss / per-croc-roll seeds. Within a run `run_seed` is constant, so every seed site stays a pure function of (chunk coords | `k`) and revisited chunks regenerate byte-identically; across runs it differs, so run 2 is a different world. `new_run()` (the only thing that changes it) re-rolls the seed, clears the road station cache back to its empty sentinel, clears the pending-chunk queue, frees every active chunk, and rebuilds around chunk (0,0) — spawn + ring 1 synchronously (so the player teleported to spawn lands on solid ground the same frame), the rest via the one-per-frame progressive fill. The terrain is in the `"terrain"` group; `player_controller.restart_game()` calls `new_run()` through it (with a `has_method` guard) **before** `reset_position()`. If you add a new deterministic spawn site, mix `run_seed` in the same `hash(Vector3i(a, b, run_seed))` shape.

**Distance is the headline score.** `player_controller.run_distance = maxi(run_distance, int(global_position.x))` each physics tick — valid as *distance travelled* because the coin road's X is strictly increasing by construction (see the coin-road section), so no path integration is needed. `coin_hud.gd` shows `Distance: %dm   Coins: %d` live (plus a ` (x%d)` streak suffix when the multiplier exceeds 1). Best-run records (`best_distance`, `best_coins`, tracked as independent maxima) live in **`scripts/best_run_store.gd`**, not in `player_controller.gd` — see "Personal best-run records" below. All the player does is fold whatever the store reports in with `maxi` (`_on_best_run_loaded`) and hand it a beaten record in `_trigger_game_over()`.

**Coin economy.** `coin.gd` has `value: int = 1` and `make_gem()` — the spawner calls it right after instantiate to make a rare purple gem (~1.6x scale, emissive material duplicated at runtime, never mutating the shared resource) worth 10; collection calls `body.collect_coin(value)`. `collect_coin()` applies a **streak multiplier**: consecutive pickups within `STREAK_WINDOW` (2.5 s) build `coin_streak`; every `STREAK_COINS_PER_STEP` (10) coins add +1 to the multiplier up to `1 + STREAK_MAX_BONUS` (x5). The streak breaks when the window lapses or on a *non-ignored* bite (`hit_by_crocodile()` resets it **after** the invulnerability early-return, so bites during grace don't break streaks). Every `EXTRA_LIFE_COINS` (75) banked grants +1 life up to `LIVES_CAP` (5) — checked with a `while` loop because one gem at high streak can jump multiple thresholds. Characters also have modest speed stats (`CHARACTER_SPEED`, 0.9–1.15x) multiplied into `calculate_current_speed()`'s duck/run/walk returns (not Windman's air-rush speed, which the ability owns).

**Difficulty gradient — all pure functions of position, deterministic within a run:** croc chase speed scales with `absf(global_position.x)` and `BASE_CHASE_SPEED` (5.5) outruns walking (see "Per-crocodile variety"); croc density scales with chunk distance (`spawn_crocodiles_in_chunk` targets `crocodiles_per_chunk + mini(8, absi(chunk_pos.x) / 6)`, cheap because the LOD manager sleeps distant crocs); the coin road band narrows with station index (see the coin-road section). Escape hatches stay: running, jumping (breaks scent), and abilities all beat 5.5.
### Personal best-run records (local store + lobby sync)
`scripts/best_run_store.gd` (`class_name BestRunStore`, a bare `Node` the player creates in its own `_ready()`) owns everything about where `best_distance` / `best_coins` are kept — **and, since the progression bead, `lifetime_coins` / `spent_points` alongside them** (same record, same request, same monotone rule; `progression.gd` owns what they mean, see "Meta-progression" below). Two layers, both monotone:

- **LOCAL** — a `ConfigFile` at `user://best_run.cfg` on desktop, `window.localStorage` on web. The ConfigFile is read on **every** platform, web included: that is the one-way migration, so a web player with an old `user://` record keeps it and the next write mirrors it into localStorage.
- **SERVER** — `GET`/`POST <lobby>/best?id=<player id>` on the existing Go lobby (`server/best.go`). Keyed by a client-generated 128-bit id (32 hex characters), minted once and stored beside the records. **Personal bests only — no leaderboard** (owner, 2026-08-25). Every failure is silent and non-fatal: the local layer has already answered, so an unreachable/old lobby costs only the server half. A request that cannot even *start* does `push_warning` — that is the one failure mode this feature is prone to and it must not be invisible.

**CEILING: "follows you between devices" means devices that SHARE THE ID, and nothing transfers one.** The id is per browser profile and per install, so a second device starts fresh, and wiping both local stores on the one device orphans the record (it sits on the server until the cap evicts it). That is the bead's design — the game has no accounts, and the owner scoped acceptance to "devices sharing the player id". `ponytail:` the upgrade path is showing the id where a player can copy it and accepting a pasted one (a UI feature); a real login is the step after. What the server layer buys unconditionally, and what the bug was actually about, is surviving the browser discarding site storage.

**`loaded` may fire more than once and the player folds each in with `maxi`** — local first (synchronously, inside `fetch()`), then the server if it knows better. The lobby merges rather than overwrites, so a POST is idempotent, a retry is free, and a late reply can never lower a record. `submit()` re-reads the local store before merging, so calling it without a preceding `fetch()` cannot overwrite a stored best with a worse run.

**Why the server layer exists at all, since `user://` measurably works.** The owner reported every run flashing NEW BEST. Driven headless against the deployed build (write → IndexedDB → reload → load → flash suppressed), `user://best_run.cfg` round-trips correctly in **both Chromium and WebKit** — the client logic and `game_over_ui.gd` were never wrong. What fails is *site storage surviving*: Safari/iOS purges IndexedDB for sites without recent interaction, a private window keeps none of it, and the GitHub Pages build and the deployed host are two different origins with two different stores. No client-side store fixes that; a server-side one does. The same caveat applies verbatim to `user://mobile_tuning.cfg`, which uses the identical mechanism — it does survive a reload in both engines, and it will vanish wherever site storage is evicted.

**`LobbyClient.http_url()`** is the shared resolver (public static): it runs the whole `--lobby=` / `?lobby=` / export / default precedence and rewrites `wss://`→`https://`, so a caller with no room and no socket can reach the plain-HTTP endpoints.

**Runnable check: `scripts/best_run_e2e.gd`**, run by `scripts/mp_e2e.sh` against the lobby it already starts (`BEST_RUN OK`, exit 0). It drives the real store over real HTTP because the Go tests cannot see the ways the *client* half fails silently — a wrong URL, a POST the server refuses over method/content-type, a response shape the parser drops, or a request that never leaves. Two traps it is written around, both of which made an earlier version pass while sending nothing: a node added to `root` inside `_initialize()` is **not** `is_inside_tree()` until the first frame (so `HTTPRequest.request()` answers `ERR_UNCONFIGURED` — the game is unaffected, the player adds the store from `_ready()`), and the reader will happily satisfy the assertion out of the **local** store `submit()` just wrote, so the local record is cleared between the write and the read. It restores `user://best_run.cfg` exactly as it found it.

### Meta-progression: lifetime coins → levels → skill points
`scripts/progression.gd` (`class_name Progression`, the `Progression` `Node` under `Main` in `main.tscn`, group `"progression"`) is the whole feature. It is deliberately **run-independent**: nothing in `restart_game()` / `new_run()` / `reset_position()` touches it, which is what makes the total *lifetime*.

- **The stored state is the raw count, not the level.** `level` is derived from `lifetime_coins` by `Progression.level_for()` every time the count changes, so there is no second number to drift. The curve is triangular — level N at `LEVEL_COIN_STEP (50) * N * (N+1) / 2` lifetime coins → **50 / 150 / 300 / 500 / 750 …**, one skill point per level. `level_for()` is a loop rather than the closed-form inverse: exact by construction at a threshold, which is precisely where it is read.
- **Owner-fixed rules (2026-08-25):** levels are **lifetime-cumulative and coins are NEVER deducted** — spending a point raises `spent_points`, it does not lower `lifetime_coins`. That is what lets *every* layer under it (ConfigFile, localStorage, the lobby record) merge with a plain monotone `max` and stop caring about ordering, retries and stale writes. `unspent_points()` is `level - spent_points`, clamped at 0; what spends them is the skill tree below.
- **TWO hooks, and both take the PRE-MULTIPLIER value.** `player_controller.collect_coin()` adds a null-safe group call `progression.add_coins(value)` — a plain coin is 1, a gem is 10 — and `bank_awarded(amount, base_total)` makes the **same** call with `base_total`, which is what a pickup won through the multiplayer claim protocol is worth before the room's multiplier — **derived locally from the winner's own pending claim, never read off the wire**, because a forgeable base value would let a hostile master mint *persisted* progression for any member (see "Pickup claims" below). The streak multiplier is a **score** multiplier (it multiplies what a run is *worth*, not how many coins were touched), and a multiplayer room's shared bank is a **run-scoped** total summed across peers; neither belongs in a lifetime count. Wiring either hook to the multiplied value is the easy mistake — the line directly above `collect_coin`'s does exactly that for `own_coins` — and it inflates every player's level by up to 5× with no error anywhere, which is why the self-check measures **both** through the real player, with the multiplier proven above 1 first and with `amount` deliberately different from `base_total` (so "the count went up" cannot pass for the bug). `base_total` is a **trailing parameter defaulting to 0**, and 0 credits nothing, so every call site that predates it is inert. Before this, a peer in a room credited lifetime coins only for the pickups it *lost* the race for (those fall through to `collect_coin`), i.e. it barely levelled at all.
- **Persistence rides `BestRunStore`, not a second store.** `lifetime_coins` / `spent_points` are two more monotone fields on the *same* record — the same `user://best_run.cfg` (its own `[progression]` section), the same `localStorage` keys, and the same `GET`/`POST <lobby>/best?id=<player id>` request (`server/best.go`'s `bestRecord` grew `lifetime` / `spent`). **So no new route, and no new entry in the Traefik path rule in `server/docker-compose.yml`** — the reason a second endpoint was not built. Both directions are version-tolerant by the monotone merge alone: an old client posts no `lifetime`/`spent`, which decodes as 0 and raises nothing, and an old lobby omits them from its reply, which reads as 0 and raises nothing. Progression owns **its own** `BestRunStore` instance (the player owns another for records) — safe because every field merges upward only, `submit*()` re-reads the local store before writing, and the two touch disjoint fields; reaching across to the player's instance would have made this file's correctness depend on `_ready()` ordering.
- **Saved on level-up and at game over**, nothing per-pickup. The level-up itself is what a player would be angry to lose to a closed tab; the game-over save catches the partial progress toward the next one.
- **Feedback:** a centred `LevelUpLabel` (`HUD`, group `"level_up_label"` — its **own** node, because the respawn countdown rewrites `RespawnLabel` every frame it is up and would eat the message) plus `sound_manager.play_level_up()`, which **replays the coin buffer twice a fifth apart** — the `play_splash()` precedent, so the "no audio asset files" invariant holds. The load at boot is deliberately **silent**: flashing "LEVEL 7" every time the game starts reads as a bug. `coin_hud.gd` gains a `Lv %d` prefix (cached group lookup, falls back to the old format string when there is no `Progression`) and an unspent-points suffix shown only when there are any — the same suffix-when-it-matters rule as the streak `(xN)`.
- **Every `_write_local()` is a read-modify-write merge, and that is what makes two stores on one file safe.** A store serializes all four fields but only ever *changes* the two it was told about, so a store mirroring a late GET reply would otherwise write its boot-time copy of the other pair over whatever the sibling store banked in between — the player's store demoting a level earned mid-run, or the progression store undoing a fresh best. `_write_local()` calls `_read_local()` first (which only ever raises), so the write is a merge; the cost is one file open on a path that runs at a level-up and a game over.
- **`@export var persistence_enabled`** is a test affordance in the `mp_manager.heartbeat_enabled` mould, exposed nowhere in the UI: with it off no `BestRunStore` is created, so `scripts/progression_selfcheck.gd` can drive the maths without reading, rewriting or POSTing a developer's real record. (The **player scene** it boots for the streak measurement still builds its own store and will mint a profile id on a fresh machine, so the check backs up and restores `user://best_run.cfg` with `best_run_e2e.gd`'s two helpers verbatim.) The persistence round trip is covered instead by `scripts/best_run_e2e.gd` against the local lobby `mp_e2e.sh` already starts.
- **`scripts/progression_selfcheck.gd` is effect-measured with a negative control per check**, the house rule: the curve is pinned at each threshold **and one coin before it** (a rounding-up inverse satisfies the first half alone), the store load is fed a **behind** answer that must change nothing, and the streak check fails loudly if the multiplier is 1 or the score did not rise by more than the base — because with either, the assertion it exists for is also true of the bug. Mutation-tested: hooking the post-streak value, an off-by-one in `level_for`, and an assign-instead-of-`maxi` on load are all caught.

### Per-hero skill trees (K, or the "Skills" button)
The other half of the progression epic: `Progression.SKILL_TREES` is **one const dict of plain dicts** in `scripts/progression.gd` — no class hierarchy, no custom `Resource` — and `scripts/skill_tree_ui.gd` (the `SkillTreeUI` `Control` under `HUD`, group `"skill_tree_ui"`) is the code-built panel that spends points into it.

- **Two branches per hero, five nodes.** Every hero shares a "Focus" branch (Quick Recovery −10% cooldown ×3 ranks → Second Wind −10% ×1; plus Fleet Foot +7% run/duck ×2) and differs only in a power branch that turns their own signature ability up: windman Long Gale (+15% `WINDMAN_BOOST_DURATION`/rank) → Updraft (+20% `WINDMAN_LIFT`); primm Long Step (+20% `PRIMM_BLINK_DISTANCE`/rank) → Phase Echo (a wall-pass refunds 1 s of cooldown — and **the wall is usually not at the landing spot**, so `_blink_passed_through()` walks the whole travelled segment rather than reusing the landing scan, which starts at the desired distance and only ever moves outward; keying off that scan meant a 2 m block three metres ahead, the ordinary case, refunded nothing and the skill silently did nothing most of the time. Gated on the skill being ranked, so an unranked Primm pays for none of the extra queries); teibi Held Form (+25% `TEIBI_FORM_DURATION`/rank) → Scurry (+10% run/duck **while small**); phoboman Lingering Reek (+20% `PHOBOMAN_FLEE_DURATION`/rank) → Billowing Cloud (+25% `PHOBOMAN_STINK_RADIUS`). A node's `prereq` needs **one** rank in its parent, not a maxed one — the tree is five nodes total, so demanding a full parent would make half of every branch unreachable until level 4. **Ranks are per hero; points are shared**, which is what makes the choice a choice.
- **THE HARD CAPS LIVE IN THE GETTERS, NOT IN THE TREE DATA.** `COOLDOWN_MULT_MIN` (0.60, the epic's −40%) and `RUN_SPEED_MULT_MAX` (1.20, the +20%) are clamps inside `skill_mult()` / `gait_mult()`, so retuning `per_rank`, adding a rank, or loading a hand-edited profile can shift the curve but cannot breach a contract. The self-check pins both **twice** — against the data a player can actually buy (so a retune past a cap fails loudly rather than being silently clamped into a node that buys nothing) and against a forced 99-rank profile (so the clamp itself is exercised).
- **`gait_mult(hero, small_form)` exists because the +20% is a cap on the SUM, and two capped multipliers are not one.** Teibi's Scurry is a movement passive as much as Fleet Foot is, so a product of two separately-clamped answers reaches x1.254 — past a cap both halves individually respect. The bonuses are therefore summed and clamped once, in one function, and `calculate_current_speed()` makes one call rather than two multiplications. The consequence is deliberate and measured: a small Teibi who has maxed Fleet Foot gets +6% from Scurry instead of +10%, while one who has not gets the full +10% — the self-check pins **both**, so neither the cap nor the node can silently become a no-op.
- **THERE IS NO WALK-SPEED EFFECT ID, AND THERE MAY NEVER BE ONE.** The catchable-walk contract (`BASE_CHASE_SPEED` 5.5 > `WALK_SPEED` 5.0, with Primm already walking at 5.75) is the tightest margin in the game. `calculate_current_speed()` computes `gait_mult` **above** the branch and uses it in the duck and run returns only; the `else` is textually the one return that does not. The self-check measures every hero's walk speed on a live player before and after every speed node is bought and fails on any difference at all — with "running did rise" beside it as the negative control, since "walk unchanged" is also true of a build where the skills do nothing. **The run multiplier goes INSIDE `maxf(..., WADE_RUN_MIN_SPEED)`**, i.e. before the floor: skills only ever raise the number, so the floor still holds and a speed passive cannot re-open the river-trap bug.
- **`_skilled_ability_cooldown()` exists so the charge and the HUD dial divide by the same thing.** `ability_hud.gd` reads `get_ability_cooldown_ratio()`, which is `remaining / duration`; leave that dividing by the raw `ABILITY_COOLDOWN` constant and a hero with cooldown ranks gets a dial that starts 60% full and empties early — no error anywhere, just a HUD that has quietly stopped meaning what it says. Mutation-tested.
- **Effects reach gameplay through ONE null-safe helper pair and the consts stay consts.** `player_controller._skill_mult(effect)` / `_skill_bonus(effect)` are the `_weather_is_raining_here()` shape — group `"progression"` + `has_method` — so the player scene standalone (and every self-check) gets 1.0 / 0.0 and behaves exactly as it did before this bead. `WINDMAN_BOOST_DURATION` is still 4.0; a skilled hero simply reads `CONST * _skill_mult(...)` at the point of use. **`WINDMAN_LIFT` is the one thing a skill may make jump higher** — there is deliberately no skill anywhere touching `JUMP_VELOCITY`, because mountain impassability assumes the base apex (3.6125 m) stays under `MOUNTAIN_MIN_LAYER_HEIGHT` (4.0).
- **Persistence: `spent_points` is the whole server surface; the ranks are LOCAL-ONLY.** `BestRunStore` gained a third field, `skill_ranks`, written to `user://best_run.cfg`'s `[progression]` section and to `localStorage` as **JSON on both layers** (one parse path to get wrong instead of two) and merged **per entry with `maxi`** by the static `BestRunStore.merge_ranks()` — the same monotone rule the scalars use, one dimension down, and correct precisely because **v1 has no respec** so a rank never falls. Nothing about the ranks goes on the wire: `server/best.go` is untouched, no route was added and the Traefik path rule in `server/docker-compose.yml` did not move. The ceiling, stated plainly: a device that learns a HIGHER `spent_points` from the server than its own rank map accounts for has fewer points to spend and no extra ranks — `unspent_points()`'s `maxi(0, …)` absorbs it, never a free rank and never a negative count. `progression._on_progression_loaded()` reads the ranks off `store.skill_ranks` rather than off the signal, because a GDScript signal cannot grow an optional third argument without breaking every existing connection.
- **The panel opens on K — a RAW KEYCODE outside the input map**, the rule this project already applies to P (pause), M (minimap), +/− (zoom) and F3–F7: named actions exist for rebindable *gameplay* input read by `player_controller`, and a key that only opens a panel has nothing to rebind against. The other half is a **"Skills" button top-right under the ability dial** (the free space beside `coin_hud`'s `Lv N`), carrying a `(N)` suffix while there are unspent points — which is what makes the tree reachable **by touch alone**, since a phone has no K.
- **It pauses the tree, with the shared `_paused_by_us` guard** `start_overlay.gd` / `pause_controller.gd` / `mp_ui.gd` / `mobile_input.gd` all carry. Pausing rather than merely freezing the player is not a preference: `player_controller` reads gameplay through the *global* polled `Input` and through `_input()`, neither of which a `Control` on top suppresses, so an unpaused panel would re-fire the desktop-web click-to-capture on every click and leave the world running while the player reads a menu. It **declines to open over somebody else's pause** (`tree.paused and not _paused_by_us`) — the start overlay, the P-pause overlay and the MP panel all draw at or above it, so the card would be invisible while still holding input — and it **does not pause over Game Over**, the exemption `mp_ui` documents. It also hides its button and force-closes while `touch_controls.has_modal()`, the same three lines for the same non-negotiable reason.
- **Localization:** the skill `name` / `desc` / `branch` strings are English source strings, i.e. their own CSV keys. Names go on buttons and are width-budgeted in `locale_selfcheck.gd`; the **descriptions autowrap** inside their fixed column so German grows the card downward (it scrolls) instead of overflowing, which is why 11 long sentences are deliberately absent from that table.
- **Deliberately not built:** no respec (the trees are tiny and points keep coming — a later polish bead if the owner wants one), and no new verbs (that is `godot-test1-20z.4`). **Known weak node:** Billowing Cloud widens the *visible* stink wave only — `_ability_phoboman()` walks the whole `"crocodile"` group with no distance test, so `PHOBOMAN_STINK_RADIUS` has never been a gameplay bound. `ponytail:` making it one means adding a `distance_to` to that loop, which would NERF the unranked ability from an unbounded sweep to a 9 m one; that is a balance change, not this bead's.

### Synthesized audio (no asset files)
`scripts/sound_manager.gd` (a `Node` named `SoundManager` under `Main` in `main.tscn`, in group `"sound_manager"`) is the entire audio layer. **Invariant: there are no audio asset files** — every sound is generated in code at `_ready()` as an `AudioStreamWAV` (mono 16-bit PCM at `MIX_RATE = 22050`), so the web build size is unchanged. One-shots play through a round-robin pool of `ONESHOT_PLAYER_COUNT` `AudioStreamPlayer` children (overlapping sounds don't cut each other off); the quiet ambient wind bed (`WIND_VOLUME_DB = -26`, far below the −6..−10 dB one-shots) has its own dedicated looping player.

Public API (all void, all safe to call anytime): `play_coin()` (random `pitch_scale` jitter per pickup), `play_jump()`, `play_land()`, `play_footstep()` (pitch-jittered soft noise "pat", fired from the walk-cycle sine's zero crossings — each sign flip is one foot planting), `play_buzz()` (low square-wave "blocked" buzz — the cooldown-refused F press), `play_crunch()` (harsh noise burst — giant Teibi crushing a croc), `play_ability(character_name)` (per-character pitch via the `ABILITY_PITCH` dict), `play_bite()`, `play_game_over()`, and `unlock_audio()`. Callers never hold a reference — hooks are null-safe group lookups (`get_first_node_in_group("sound_manager")` + `has_method` guard), so any scene run without `Main` stays silent instead of erroring: `coin.gd` and `touch_controls.gd` inline the lookup at their single hook each, while `player_controller.gd` (five hooks) funnels them through its `_sfx(method, arg)` helper. The landing thud fires on the raw floor transition in `update_character_animation()` (before the animation branch chain, so an active sidestep can't swallow it) and is muted during the frozen caught/respawn/game-over windows. (The coin's pickup sound plays through the manager's players, not the coin, because the coin `queue_free()`s itself on pickup.)

**Web unlock gesture rule:** browsers block audio until a user gesture, so every `play_*` early-returns until `unlock_audio()` flips `_unlocked` (which also starts the wind loop). The manager's own `_input()` calls it on the first key/click/touch (then disables input processing), and `touch_controls.gd`'s "enable motion controls" overlay tap calls it explicitly — the guaranteed gesture on mobile web. Don't add a `play_*` path that bypasses this gate.

**Runtime-varied loops:** `get_loop_player(name)` fetches (or lazily creates) a dedicated looping `AudioStreamPlayer` per named ambient bed. Two built-ins: `"wind"` (started by `unlock_audio()`) and `"heartbeat"` — one baked "lub-dub" cycle built in `_ready()` as a `LOOP_FORWARD` `AudioStreamWAV` (`loop_begin = 0`, `loop_end = data.size() / 2` — frames, not bytes, at 2 bytes/frame), which the manager **never plays itself**: the danger vignette owns play/stop/pitch/volume through `get_loop_player("heartbeat")` (see the danger telegraph above). A future system needing a live-modulated loop follows the same pattern — request a name, assign a looping stream, vary `pitch_scale`/`volume_db` per frame — and must check `is_unlocked()` before calling `play()`, because the gesture gate only guards the manager's own `play_*` methods.

### Weather: clouds, storm rain zones, birds
`scripts/weather_manager.gd` (a `Node` named `Weather` under `Main` in `main.tscn`, in group `"weather"`) owns **all** ambient weather in one self-contained file. It is deliberately **not** part of `endless_terrain.gd`: the terrain is the *world* engine and everything it spawns is a deterministic pure function of chunk coords + `run_seed`, while weather is *ambience* — clouds drift across chunk seams, follow the player rather than the grid, and nobody cares whether run 2's sky matches run 1's. So it uses a plain `randomize()`d `RandomNumberGenerator` (the same precedent `fauna_manager.gd` follows) and never touches the terrain's hash streams.

- **Clouds.** A fixed pool of `CLOUD_COUNT` (26) blocky clusters (4–9 flattened boxes each) floats at 45–70 m in a `FIELD_RADIUS` (250 m) disc around the player, drifting along one global `WIND_DIR`/`WIND_SPEED` with per-cloud speed variation and a sine bob. A cloud that leaves the disc **in any direction** is **recycled, never freed**: re-rolled and re-placed on the rim *opposite* the side it left by, so the field never depletes and nothing pops in view. **The "any direction" part is load-bearing** — `WIND_SPEED` is 1.6 m/s and `WIND_DIR` is mostly +X while the player runs +X at 5–10 m/s (≈25 during Air Rush), so clouds are in practice left *behind*, never overtaken. An earlier downwind-only test (`to_cloud.dot(WIND_DIR) > FIELD_RADIUS`) therefore never fired: the whole field stranded out of range within ~40 s and the sky stayed empty for the rest of every run, taking `is_raining_at()` — and with it rain particles, the rain bed and both Windman-in-rain rules — down with it. All of it renders as **one `MultiMeshInstance3D`** (shared unit `BoxMesh`, `use_colors`, one `StandardMaterial3D` with `vertex_color_use_as_albedo`) — one draw call for the whole sky. `cast_shadow` is **OFF** on purpose: `directional_shadow_max_distance` is 55 m, so clouds at 45–70 m are outside the shadow range anyway. No transparency anywhere — alpha-blended sky quads that big are mobile fill-rate poison.
- **Storm clouds + rain.** `STORM_CHANCE` (~1 in 7) makes a cloud bigger, dark (`STORM_COLOR`), and gives it a **circular ground rain zone** whose radius is measured from its actual rolled boxes (`RAIN_ZONE_FACTOR` × cluster radius), moving with the cloud. Rain is **one `CPUParticles3D`** (never `GPUParticles3D` — web runs `gl_compatibility`), 120 thin streaks, `local_coords = false` so drops keep falling in world space while the emitter box follows the player. `emitting` flips **only on the enter/exit transition**, so outside a zone the whole rain path costs nothing beyond the manager's own tick.
- **Rain audio.** The rain loop is synthesized **inside the weather manager** (`_synth_rain_stream()` — the same one-pole-noise + crossfaded-seam recipe as `sound_manager._synth_wind()`, with a much brighter filter) and played through `sound_manager.get_loop_player("rain")`, so `sound_manager.gd` needed no edit. A `_rain_mix` 0..1 lerped at `1/RAIN_FADE_TIME` drives both the rain volume and a `WIND_DUCK_DB` duck of the ambient wind bed (whose base volume is *captured*, never assumed); the voice is `stop()`ped once fully faded out, and `play()` is gated on `is_unlocked()` because `get_loop_player` voices bypass the manager's own gesture gate.
- **Gameplay API + the Windman rule.** `is_raining_at(world_pos: Vector3) -> bool` is a flat XZ circle test against the handful of storm clouds — cheap enough to call per frame. `player_controller.gd` uses it through **exactly one** null-safe helper, `_weather_is_raining_here()` (group `"weather"` + `has_method`, same shape as `_sfx()`), in two places: pressing **F** as Windman inside rain fails like a cooling-down press (`ability_hud.flash_blocked()` + `play_buzz`) and **does not consume the cooldown**; and a Windman *already flying* who enters a zone has `windman_boost_timer` zeroed — wet wings, normal gravity resumes mid-air.
- **Birds.** Every `BIRD_INTERVAL_MIN`–`MAX` (60–120 s) a flock of 3–7 birds crosses at 30–40 m and despawns past the field radius: no collision, no AI, no interaction. Each bird is 3 instances (body + 2 wings) in a **second MultiMesh**, parked at zero scale between flocks. Birds are the one thing updated **every frame** rather than on the throttled tick — a ~3 Hz wing beat sampled at 10 Hz would alias into a stutter — which is affordable because ≤21 instances exist only during the rare seconds of a crossing.
- **Perf shape:** everything runs on a throttled `TICK_INTERVAL` (0.1 s, ~10 Hz) tick like `crocodile_lod_manager.gd`; total cost is 2 MultiMeshes (clouds + birds) plus 1 `CPUParticles3D` that only emits inside a rain zone. The F3 overlay is the measure: draw calls should rise by a couple, not dozens. A full-screen darkening `ColorRect` for rain mood was **deliberately skipped** (fill-rate cost for a subtle effect) — noted in the script, trivial to add if the mood falls flat.

### Minimap HUD (M)
`scripts/minimap_hud.gd` (the `MinimapHUD` `Control` under the `HUD` `CanvasLayer`, **left edge, vertically centred** — the one corner-free strip: lives/⚙/MP/coins/ability/touch buttons all sit in corners, and only the F3 perf overlay and F4 motion readout, both debug-only, can reach it) is an asset-free `_draw()` map in the `ability_hud.gd` mould, found via groups (`"player"`, `"terrain"`) with `has_method` guards so it runs blank in a scene missing either. It is **north-up** (world +X → screen right, +Z → screen down) rather than rotating under a fixed arrow: the coin road's X is strictly increasing by construction, so a fixed frame makes "the road goes that way" legible and costs no per-point rotation. It shows the player as a facing triangle, the **coin road** as a polyline, crocodiles within `CROC_VIEW_RADIUS` (30 m — everything that can currently *see* the player, vs the map's 60 m reach) as red dots, and world X/Z plus the biome underfoot, with a `~ river ~` marker while wading. **It reads the road out of `endless_terrain`'s existing station cache** (`road_stations` / `road_k_min` / `road_k_max` / `_road_first_k_at_or_after_x`) and **never extends it** — the stations covering the player's chunk are already cached, and anything outside the cached range simply isn't drawn. Points whose Z wanders off the disc are **clamped to the rim**, not clipped, so the polyline stays unbroken (one draw call) while still pointing where the road left. Everything is recomputed on a throttled `TICK_INTERVAL` (0.2 s) tick like `crocodile_lod_manager.gd`'s scan — `_draw()` only paints the snapshot, allocates nothing, and redraws at the tick rate, not the frame rate. **Every primitive was chosen by its draw-call count, measured against a deliberately frozen world with the same counters F3 reads** (a live world's crocs/clouds swing draw calls by ±50, several times the whole HUD's budget): one `draw_polyline` for the road (~20 `draw_line`s cost ~20 calls — antialiased lines don't batch), one `draw_multiline` for the whole croc pack (`draw_circle` cost **1 call per dot**, unbounded to 40), one `draw_multiline_string` pair for both text lines, and a filled ring circle instead of an antialiased `draw_arc` (3 calls → 1). Total: **+10 draw calls, no measurable CPU change**. **M** toggles it (raw keycode outside the input map, like F3/F4).

**ZOOM: +/- step `ZOOM_RADII` (30/45/60/90/130 m), the widget NEVER changes size, and `_view_radius()` / `_map_scale()` are the only two places the map's reach is defined.** Same raw-keycode rule as M (both the main row and the numpad; `KEY_EQUAL` is accepted because "+" is shift-equals and nobody holds shift to zoom a map), and zoom is ignored while the map is hidden rather than silently eaten. Every layer derives from those two: the road window, the teammate dots and their rim clamp, and the crocodile radius — which is now `CROC_VIEW_FRACTION` (0.5) of the reach, **a fraction rather than a metre count**, so it follows the zoom instead of needing its own step table (at the default zoom that is exactly the 30 m the map shipped with). The one layer that derives from *nothing* is the biome/river caption: it is a single sample under the player's feet, so it is scale-independent by construction — there is no grid to widen. The zoom is **session-only, no ConfigFile** (a glance-scale preference, not a setting). Touch sessions get a small on-widget **+/- pair**, gated on `MobileSensors.is_touch_session()` like all touch UI and built `FOCUS_NONE` like every other button in this project (`ui_accept` is Space, Space is jump). Cost: **0 draw calls** — zooming fully out changes the number of road points, not the number of primitives (measured 246 → 246).

**MULTIPLAYER TEAMMATES: dots in each peer's own colour, off-map ones clamped to the rim as an outward radial TICK rather than a blob** (a clamped blob reads as "standing at the edge"; a tick reads as "further, that way"). One `draw_multiline_colors()` for the whole room — the `_colors` variant rather than the plain `draw_multiline()` the crocodile pack uses, because that one takes exactly one colour, and this variant wants **one colour per SEGMENT** (`colors.size() * 2 == points.size()`), which is why the two buffers are different lengths. Both are permanently sized to `MAX_PEER_DOTS` and the unused tail is parked off-control and transparent, exactly like the crocodile tail. The data is `MpManager.peer_markers()` through the usual group lookup + `has_method` guard, and it answers **`null` solo**, so single-player draws and scans nothing at all — see "Teammate locator bar" under Multiplayer below for why that method exists beside `peer_positions()`.

Deliberately skipped: river *bands* on the map — even a coarse 9×9 `is_river_at` grid is 81 noise evaluations per tick, a GDScript spike for decoration (the `ponytail:` upgrade path is amortising a few cells per tick). `scripts/minimap_selfcheck.gd` (`godot --headless --path . --script res://scripts/minimap_selfcheck.gd`, prints `SELFCHECK OK`) is the one runnable check: it guards the reach into the terrain's road internals — which fails **silently** behind the `has_method` guard — plus the north-up sign convention and the croc-dot cap staying a bound rather than a limit reached in play. **The zoom and teammate checks are EFFECT measurements with a negative control each, never getter read-backs**, because the failure they exist for is silent and delayed: a layer that keeps its own hardcoded metre count draws perfectly at the default zoom and only parts company with the picture once somebody presses +. So it places a **probe crocodile at 40 m** — deliberately between the default 30 m croc radius and the 45 m one step out — and requires it undotted at one zoom and dotted at the other (a with/without pair *at each zoom*, because zooming out legitimately brings the world's own crocodiles into range too); it counts **road points at two zooms** and requires growth; it requires a teammate at 70 m to clamp on the 60 m map and **not** clamp on the 130 m one; and it requires zero dots and a hidden locator **solo**. Both HUDs are driven from a `StubMp` in the `"mp"` group (the real, offline manager is *removed from the group* rather than freed — the smallest change that redirects both), so known positions can be asserted with no room, no lobby and no WebRTC addon. Mutation-tested, all five caught: hardcoding the croc radius, hardcoding the road window, dropping the rim clamp, swapping the dot's X/Z axes, and flipping the locator's bearing sign.

### Ambient fauna (migrating herds + herder caravans)
`scripts/fauna_manager.gd` (a `Node` named `FaunaManager` under `Main` in `main.tscn`, in group `"fauna"`) is the whole feature: every so often a family of elephants, a flock of giraffes, or a herder caravan walks across the landscape in the distance. It is **pure scenery** — sibling in spirit to `crocodile_lod_manager.gd`, it finds the player via the `"player"` group (null-safe: no player, no herds) and owns its entities directly.

- **One herd at a time, ever — that is the entire perf story.** `_spawn_herd()` early-returns while `_animals` is non-empty. An event is at most 8 animals (elephant/giraffe herds) or 10 members (a caravan: `CARAVAN_HERDERS_MAX` 4 + `CARAVAN_BEASTS_MAX` 6) × ~12 boxes, alive only during that event; between events the per-frame cost is one float subtraction on `_event_timer`. Animals are parented to the manager itself, **never to a terrain chunk** — chunk unloading must not free a herd mid-walk. Despawn is a distance check against the **live** player position (`DESPAWN_RADIUS` 150, just past the `FIELD_RADIUS` 140 spawn circle), so "the herd walked past" and "the player ran away" are the same branch. Both radii are bounded by the same terrain-extent argument — the *whole lifetime* has to stay on solid ground, not just the spawn frame.
- **The spawn heading is a rearward cone, not a random compass bearing.** The player runs +X at 5–11 m/s and a herd ambles at 2–3, so a herd heading anywhere near the run direction is simply outrun and despawns behind the camera, unseen. `MIGRATION_HEADING_SPREAD` (±0.6 rad) draws the heading against +X, putting the herd origin ahead down the road so it walks back through the player's area. `FIELD_RADIUS` 140 is likewise a constraint, not taste: the web build's terrain reaches only ~150 m (`WEB_RENDER_DISTANCE` 3 × 50 m chunks), and a herd spawned past that stands over open sky. The migration line is also offset sideways by `MIGRATION_MISS_MIN..MAX` (25–60 m, either side) — the origin sits on the ray *from the player*, so with no offset the herd would walk straight **through** them, guaranteed whenever the player can't step aside (the respawn grace freeze, a pause, the game-over screen). The along-heading setback shrinks by Pythagoras to keep the origin on the spawn circle, so the lateral offset can never push a fresh herd past `DESPAWN_RADIUS` and get it freed on its first frame. **Both radii bound the herd CENTRE, and members sit at `centre + offset`, so both ends subtract `FORMATION_MAX_EXTENT` (17.5 m, bounded by the widest formation — the giraffe echelon at 17.43; the caravan line is second at `hypot(9.9, 1.6)` = 10.03):** the spawn circle is `FIELD_RADIUS − FORMATION_MAX_EXTENT` and the despawn test is against `DESPAWN_RADIUS − _herd_offset_max` (this herd's *actual* widest slot, filled in by `_add_animal`, so a small elephant family stays on screen as long as it always did) measured on the same meandered `centre` the animals are placed against. Without both, the outermost giraffe spawned at 157 m and lived out to 164 m — over the open sky past the web build's ~150 m of terrain, which is the exact failure both constants exist to prevent. Measured after the fix: 136 m worst at spawn, 149 m worst while alive.
- **The animals join NO group.** This is a hard contract, not a style choice: Phoboman's Stink Wave iterates `"crocodile"` and the LOD manager iterates it too, so a fauna node in any enemy group would be grabbed by both. Animals are `MeshInstance3D` trees with **no per-animal script** — one `_physics_process` on the manager moves and animates all of them, reading only pivot references cached at build time (zero allocations, no `get_node()` in the loop).
- **Herds steer around obstacles by moving the CENTRE, never the individuals.** On a throttled `AVOID_PROBE_INTERVAL` (0.25 s) tick, **ONE box the full width of the formation is swept along the heading** (`PhysicsShapeQueryParameters3D` + `cast_motion`), producing one signed lateral offset that is added to the same `_herd_lateral` axis the meander already rides, so every member inherits the detour through its existing formation offset: **no per-animal work, no new state in `_update_herd` / `_animate_animals`, and the isolation contract is untouched** (the query *reads* the world; fauna keeps `collision_mask = 0` and still collides with nothing but a rider). Five things are load-bearing, each of which was measured failing before it was there:
  - **A physics query, not the terrain's `obstacles` footprints.** The exact per-chunk footprint list is a *local* inside `create_chunk`, dropped when the chunk finishes — querying it needs a new public API on `endless_terrain`. A layer-1 query needs none and sees strictly more: massif layers, camp huts, tree trunks, chest bodies, artifact stone and scattered blocks all live in the same per-chunk `BlockCollision` body.
  - **The probe is as wide as the MEMBERS, not the centre's line** (`_herd_offset_max + AVOID_EDGE_MARGIN` either side). Angled whiskers report where the *centre* can walk, so a herd steers until its middle is clear and drags its outermost giraffe (a 28 m-wide echelon vs a ~20 m massif) straight through the rock: 100% of aimed trials still clipped, 6.0 m mean penetration.
  - **A SWEPT BOX, not three parallel rays — that is the v2 change and it is what the owner playtest forced.** v1 sampled the corridor with three rays (centre + both edges); a ~30 m swath sampled at three infinitely thin lines walks a 1–2 m scattered decorative block between two of them, and elephants strolled through the scenery with no error anywhere. Re-measured on the v1 code with a lone 1.5 m block parked on the line: **50% of aimed trials clipped, worst −1.64 m, mean closest approach 0.17 m**. A swept box has no gaps by construction — anything solid in the swath is hit whatever its width — and detection plus the measured distance now come from that one query.
  - **The two EDGE RAYS survive, and only to pick a side.** `cast_motion` answers how far the box got, never *what* it grazed, so it cannot say which way to go round; "is the extreme edge of the swath free?" is exactly the question that can, and it is v1's rule unchanged (clearer edge wins, ties go to the side already committed to). Deriving the side from a `get_rest_info` contact point instead was tried and is the version that **FAILS**: the reported contact can sit anywhere on the manifold, so a massif lying mostly to the left answers with a contact on its right edge and sends the herd left into the bulk of it — **12.5% of aimed massif trials clipped, worst −2.44 m**. The rays are cast **only on a tick that is already blocked**, so open country costs ONE query where v1 paid three.
  - **The berth is HELD until the herd has walked past what it stepped around.** The sweep points forward, so once the swerve is wider than the obstacle the rock is no longer inside the box at all, "all clear" arrives while it is still abeam, and unwinding there walks the rear of the formation back into it (45% of aimed trials still clipping, every failure on the unwind). `_avoid_hold_until` is set from the distance the sweep actually measured plus the formation's depth, so it scales itself instead of guessing a constant.
  - **The player is excluded by RID.** `scenes/player.tscn` leaves `collision_layer` at 1 — the layer the probe watches — so without `_refresh_probe_exclude` a herd would swerve around the *player*, the loudest possible breach of the isolation contract and the least visible. `PhysicsShapeQueryParameters3D` carries `exclude` with the same meaning the ray params did, so the shape-cast upgrade left this rule untouched (**both** query objects get the list). Crocodiles (layer 2) and fauna itself (layer 3) are invisible to the mask by construction.
  - **The box's bottom must clear the ground slab.** `AVOID_PROBE_HEIGHT` (1.0) is its *centre* and `AVOID_PROBE_BOX_HEIGHT` (1.6) its height, so it spans 0.2–1.8 m: above the chunk ground collision (a 0.1 m box straddling y = 0, top 0.05) and below nothing that matters. Lower the centre or raise the height until they meet and **every herd everywhere swerves around the floor**.
  - **Measured** (aimed sweeps, 40 trials each, obstacle parked on the herd's freshly rolled line, v2): massif **0%** clipped / worst **+3.34 m** clearance, camp-sized hut ring **0%** / **+9.52 m**, lone 1.5 m scattered block **0%** / **+12.53 m** (from 50% / −1.64 m on v1). An empty field deflects a herd by **0.00 m** with the player standing directly on its inbound line, i.e. open-country crossings are unchanged. Entity and draw-call counts are untouched (no new nodes, no new materials), and the query cost went **down**: 1 query per 0.25 s in open country, 3 while actually swerving, against v1's flat 3 — and nothing at all between events.
  - `scripts/fauna_selfcheck.gd` (`godot --headless --path . --script res://scripts/fauna_selfcheck.gd`, prints `SELFCHECK OK`) guards the three rows that fail silently — a herd clearing a massif, a herd clearing a lone 1.5 m block, and an empty field plus a player producing zero deflection (which is also the negative control: without it, "always swerve" would pass the other two). Mutation-tested — narrowing the box back to ray width passes the massif row and fails the block row with `herd walked INTO the block (worst clearance -1.41 m)`.
  - `ponytail:` the remaining ceiling is warning DISTANCE, not width — a herd that meets a massif with under ~35 m of notice (a chunk streaming in late, or a mountain range with no gap) still runs out of room to open the full berth. The upgrade path is a longer `AVOID_LOOKAHEAD` plus a faster `AVOID_EASE_SPEED`, both of which cost readability of the swerve.
- **Fauna is SOLID TO THE PLAYER ONLY, and you can ride it.** The one loosened clause in the isolation contract: each of the three **quadrupeds** (elephant, giraffe, pack beast) has its *root* built by `_make_rideable_root` as an `AnimatableBody3D` carrying one `BoxShape3D` around the barrel, so the player can jump onto a walking camel's back and be carried like a moving platform — **walking off is the dismount**; there is no mount state, no camera change, no input handling and no multiplayer sync. **Herders stay walk-through** (plain `Node3D` root, no collider). Three things make it work, each of which was measured and each of which breaks silently if reversed:
  - **Layer 3 (`FAUNA_COLLISION_LAYER = 4`), mask 0.** The player masks layers 1+3 (`scenes/player.tscn`, `collision_mask = 5` — the whole player-side change, in the scene, not the controller). Crocodiles are layer 2 / **mask 3**, so they never see layer 3: a croc still walks through a camel and its avoidance never fires on one (measured: a croc parked inside a beast's barrel and pushed at it for 340 frames ended 12.5 m away, undeflected). **That second half is only true because `_feeler_blocked` passes the croc's own `collision_mask` to `PhysicsRayQueryParameters3D.create` — its default is all 32 layers, and fauna is in no group, so the group test cannot reject it.** Ordinary crocs were saved only by geometry (the feeler sits at 0.28–0.43 m, under every deck), but `_avoid_obstacles` scales both probe dimensions by the body, so a boss at scale ≥ 3.375 lifts it past 1.1 m and would swerve away from — and cut speed for — a pack beast it cannot touch. **Never put fauna on layer 1** — the croc mask includes it. Mask 0 keeps fauna itself walking through terrain, as before.
  - **The ROOT is the body — never a body parented under the root.** An `AnimatableBody3D` only pushes to the physics server when its *own* transform changes, and `_update_herd` moves the root; a child body never sees a local change, so its collider stays pinned at the spawn point while the visual walks away (measured: 12.5 m of beast travel, 0 m of player travel, `platform_velocity` zero — the player rides a phantom).
  - **`sync_to_physics` MUST STAY OFF** — the property every moving-platform tutorial turns *on*. It means "physics drives this node", so every local-transform write is snapped back to the last server-confirmed transform; since `_update_herd` moves an animal by lerping *from its own position*, that pins it forever (measured: 16.6 m of herd travel, 0.00 m of animal travel). With it off, writes stick and the carry is exact (12.077 m vs 12.077 m, platform velocity matching the herd speed) — Godot derives platform velocity from the per-physics-step transform delta either way. **This is also why the driver is `_physics_process` and not `_process`.**
  - **The `MAX_HERD_LIFETIME` (240 s) despawn is DEFERRED, not skipped, while the player is standing on a herd member** (`_player_is_riding`, which matches the player's slide collisions against the animal roots). Riding is exactly the "player pins the herd alive" case the cap was written for, so it is exactly the case that trips it — and firing it frees the herd under the player's feet, dropping them ~2 m mid-stride. It is re-tested every tick, so the cap resumes the moment they step off. The **distance** despawn can't fire while ridden (a rider is inside `_herd_offset_max`), and terrain extent is a non-issue because chunks stream around the player.
  - Deck tops are bounded by the player's 3.6125 m jump apex so every animal is mountable from flat ground: pack beast 2.07 m (the collider reaches the **bundle** tops, not the barrel's — the cargo is what you stand on), elephant 2.60 m, giraffe 3.00 m, elephant calf 1.43 m (the collider scales with `CALF_SCALE` off the existing root-scale write, for free). A rider is croc-safe exactly like standing on a decorative block, and herds amble at 2–3 m/s — well under `BASE_CHASE_SPEED` 5.5, so riding is slower than walking and there is no escape-hatch interaction.
  - Multiplayer (cross-ref `godot-test1-s86.3`): a ridden player is just a player transform, which presence already carries. Fauna is local and non-deterministic, so a **remote peer does not see the camel** and a ridden avatar appears to glide ~2 m off the ground. Known, accepted cosmetic artifact — do not design around it.
- **Shared resources: ONE `BoxMesh` + one material per species, in `static var` lazy getters** (same trick as `endless_terrain._get_shared_unit_box_mesh()` and `ToonShading`'s material cache). The feature's material total is a constant 6 (elephant, giraffe, off-white tusk accent, dark patch/horn, herder cloak, pack-beast wool) no matter how many animals ever spawn — **never `duplicate()` a material per animal or per part**. Models are code-built from that unit box, scaled per part; there are no asset files and no Python pipeline. `cast_shadow` is ON for adult body/legs/neck and OFF for small accents (ears, trunk, tusks, horns, patches) and for every part of a calf.
- **Feet rest at y = 0 by construction** — the ground is a flat `PlaneMesh` at y = 0, so fauna needs no raycasts and no terrain queries. If the terrain ever gets height variation, this is the assumption that breaks.
- **Deliberately non-deterministic.** The manager uses its own `randomize()`d `RandomNumberGenerator` and never touches the terrain's `run_seed`. Ambience is not part of the determinism contract — do not wire it in.
- Animation follows `piglet_crocodile_ai._animate_body()`'s idiom, with one improvement: the stride phase is a pure function of **metres walked** (`_herd_travelled * STRIDE_FREQUENCY` + the animal's phase offset), not an accumulator — so feet keep pace with the ground at any walk speed and the phase can never drift. Diagonal leg pairs sit a half-cycle apart (a real trot), the body bobs at **twice** the stride rate, and per-animal phase offsets keep the herd out of lockstep. The body bob is deliberately **offset to stay at or above rest**: the legs hang off `Body`, so a bob dipping below rest would push every foot through the ground plane. The giraffe neck bob composes **on top of the neck's cached rest lean** rather than overwriting it.
- **Herder caravans are the third migration type, and they are just N more records.** `CARAVAN_CHANCE` (0.15) is rolled **first** in `_spawn_herd()`, taking its slice off the top so the existing `ELEPHANT_CHANCE` split stays exactly the elephant/giraffe branch (0.425 each) — one extra branch, not a restructure. A caravan shares the fauna event timer rather than owning one, so the "one herd at a time, ever" perf story is unchanged. `_spawn_caravan()` puts `CARAVAN_HERDERS_MIN..MAX` (2–4) herders at the **front** of the line and `CARAVAN_BEASTS_MIN..MAX` (3–6) laden pack beasts trailing behind, one slot per member stepping `CARAVAN_LINE_SPACING` (2.2 m) back along the heading with `CARAVAN_LINE_JITTER` lateral wobble — the spacing is bounded, not chosen by eye: half a full ten-member line is offset back **and** sideways, so its `hypot(4.5 × 2.2, CARAVAN_LINE_JITTER 1.6)` = 10.03 m has to fit inside `FORMATION_MAX_EXTENT` (17.5), which is what both the spawn circle and the despawn test subtract (see the migration-line rules above) — the plain 9.9 m understates it, and the old "≤ `DESPAWN_RADIUS − FIELD_RADIUS` (10 m)" form left 12 mm of slack that one more pack beast would have eaten silently. It hands each member to the existing `_add_animal(record, offset)` — so formation easing, facing, phase offsets, movement, animation and despawn all come for free with **no new state in `_update_herd` / `_animate_animals`**.
- **The caravan builders return the same species-agnostic record** (`root`/`body`/`legs`/`neck`/`neck_rest`/`trunk`), which is why nothing downstream needed a branch. `_build_herder()` is a torso + head + staff over **two** `_make_leg` hip pivots — the animation loop indexes `LEG_PHASE_OFFSETS` by leg index, so two legs get the 0/π alternating stride for free — with `neck = null` and `trunk = []` (already the elephant/giraffe cases). `_build_pack_beast()` is a woolly body with a shag fringe, four legs in the required FL/FR/RL/RR order, bundles strapped on the back, and a curved neck in the `neck` slot so the existing neck-bob (composed on top of `neck_rest`) drives it. Same shadow discipline as the herds — `cast_shadow` ON for torso/legs/beast body/neck, OFF for staff, fringe, bundles and head nubs — and the same hard isolation contract: **no group, no reaction to player, crocodiles, abilities or rain** (the pack beasts do carry a rideable layer-3 collider and the herders carry none — see the rideable-fauna bullet above).
- Deferred by design: the elephant trumpet one-shot (a `sound_manager` `play_*` in its synth style is the upgrade path); the caravan bell one-shot, skipped for the same reason plus one more — `sound_manager` voices are non-positional and a caravan spawns ~140 m away, so a bell would misread as coming from the player (the upgrade path is an `AudioStreamPlayer3D` on the lead herder); and caravan↔nomad-camp pathing, which is out of scope (the upgrade path is a nearest-camp query on the terrain).

### Art-directed look (main.tscn + ToonShading)
The rendering look is authored in `main.tscn` plus a couple of shared pieces, all verified to work in the web `gl_compatibility` renderer (SSAO/DOF/volumetrics do **not** exist there — don't attempt them):
- **Key light** (`DirectionalLight3D`): warm `light_color (1, 0.94, 0.82)`, `light_energy 1.15`, rotated to ~35° elevation raking sideways across the +X run direction; `light_angular_distance = 1.5` makes the ProceduralSky draw a real sun disc. Shadows are tuned: `directional_shadow_mode = 1` (2 PSSM splits instead of the default 4), `directional_shadow_max_distance = 55`, `directional_shadow_blur = 1.2`, `shadow_normal_bias = 0.8` — crisper contact shadows *and* a 2–4× cheaper shadow pass than the old 100 m / 4 splits.
- **Sky** (`ProceduralSkyMaterial`): `sky_top_color (0.25, 0.45, 0.75)`, sky and ground horizon both `(0.85, 0.86, 0.80)` — the same value as `FOG_COLOR` (the fog-tracks-horizon contract) — desaturated-green ground bottom, `sun_curve 0.08` for a visible halo.
- **Glow + grade** (`Environment`): `glow_hdr_threshold = 0.85`, `glow_intensity = 0.6`, `glow_bloom = 0.05` — the glow pass was already always paid; now coins (emission raised to 1.6, `cast_shadow` off, permanent 15° rest tilt so the spin shows face and edge) genuinely cross the threshold and bloom. If glow ever blooms hot in the compatibility renderer (it hardcodes screen-blend), tune `glow_intensity` DOWN — don't raise the threshold. BCS grade: `adjustment_contrast 1.08`, `adjustment_saturation 1.18`, `tonemap_exposure 1.05`, `tonemap_white 1.2` (Filmic). **The `adjustment_*` BCS grade is desktop-only**: Godot's Compatibility renderer ignores `Environment.adjustment_*` entirely, so the web build renders without the contrast/saturation lift (harmlessly — the properties are skipped, not broken). That's consistent with the "desktop keeps full quality" convention (like MSAA 2 vs 0); don't try to reproduce the grade on web via a fullscreen shader.
- **`scripts/toon_shading.gd`** (`class_name ToonShading extends RefCounted`): one static `apply_to_mesh(mesh)` carrying the toon+rim material treatment (per-surface duplicate → `DIFFUSE_TOON`, rim 0.4 / rim_tint 0.25) plus a **static styled-material cache keyed by the source material's instance id** — the cache is the whole point: ~490 crocodiles sharing the same GLB materials get ONE styled duplicate per source material, never per-croc duplicates (which would be ~490 extra materials and break batching). `player_controller.apply_toon_shading` now just delegates to it; crocs apply it in their `_ready` mesh walk but get **no** inverted-hull outline overlay (a second draw call × 490 is unaffordable).

### Biomes (flat-world): desert / plains / forest / mountain + rivers
Walking ~1 km crosses visibly distinct regions. **The whole system is built *within* the flat-world invariant — do not break it.** The ground stays a flat `y = 0` plane (`terrain_height = 0.0`) because coin heights, coin-road placement, crocodile gravity settle, the player spawn at `(0, 2, 0)` and the per-chunk box ground collision all assume it. So **mountains are impassable block massifs you walk *around*, not raised terrain**, and **rivers are flat tinted wading bands** — a shader tint plus a speed penalty, with no water mesh, depth, transparency or reflection. Only the ground *shader* learns about biomes. The `ponytail:` upgrade path (recorded twice in `endless_terrain.gd`, in the `BIOME FIELD CONFIGURATION` constant banner and at the head of the `BIOME FIELD` function section): give the ground mesh vertex displacement plus a matching CPU height function, then make every y-placement site (`COIN_GROUND_HEIGHT`, croc spawn y, spawn point, block bases) ask it.

**One noise field decides everything.** `_biome_noise(world_x, world_z)` is a single octave of world-space value noise at `1.0 / BIOME_CELL_SIZE` (400 m ≈ 8 chunks), sampled at `world_xz / BIOME_CELL_SIZE + biome_offset` and clamped to 0..1. `biome_offset: Vector2` is how `run_seed` reaches the GPU (a shader can't take a 64-bit int): `_roll_biome_offset()` derives it from its own RNG seeded `hash(Vector3i(BIOME_SALT, 0, run_seed))` and is called from `_roll_run_seed()`, so `_ready()` and `new_run()` both get a fresh biome layout for free. Thresholding gives the four bands (`BIOME_DESERT_MAX` 0.34 / `BIOME_PLAINS_MAX` 0.62 / `BIOME_FOREST_MAX` 0.82 — plains most common, mountain rarest) and a thin **contour** of the same field gives rivers: `is_river_at(pos)` is `absf(noise - RIVER_LEVEL 0.5) < RIVER_HALF_WIDTH 0.007` (**tune by eye, not algebra** — the half-width was originally 0.02, derived from a guessed 0.005/m gradient; the field's measured mean gradient is ~0.0017/m, which made 6.7% of the world water with a 31 m median crossing. 0.007 gives a ~2.3% water share and an ~11 m median crossing along +X. Value noise has zero gradient at every lattice corner, so a corner hashing near 0.5 still yields the occasional lake — p95 crossing 61 m; rare enough to read as a landmark). `biome_at()` / `is_river_at()` are the **public API**; both are pure functions of world position + `biome_offset`, contain zero RNG draws, allocate nothing, and are safe to call every physics tick.

**CPU/GPU parity contract — `_biome_noise` in `endless_terrain.gd` and `biome_noise` in `assets/shaders/ground.gdshader` are the SAME function in two languages and must be edited together.** The blue band the player *sees* and the wading zone the player *feels* have to be the same band; rather than upload a texture or read back from the GPU, the GDScript port mirrors the GLSL exactly (`mod`↔`fposmod`, `fract`↔`v - floor(v)`, same `dot(p, p.yx + 33.33)` magic constants, same `f*f*(3-2f)` smoothstep weights), and the shader's `biome_noise` **reuses the existing `hash2`/`value_noise`** — that reuse is what keeps parity honest. `_apply_biome_shader_params()` pushes only the **parity-critical** uniforms (`biome_offset`, `biome_cell_size`, the three thresholds, `river_level`, `river_half_width`, `biome_blend`) onto the shared ground `ShaderMaterial`, guarded by an `is ShaderMaterial` check so the `@export var terrain_material` escape hatch still silently wins; it is called from `_ready()` after the default material is built and again from `new_run()` (after `_roll_run_seed()` in both). The **band colours are deliberately NOT pushed** — they live as shader defaults so an art pass can retint from the material without touching GDScript.

**Parity gotcha — `_biome_hash2` runs every step through `Vector2` on purpose, and that is not stylistic.** GDScript scalars are float64 while GLSL is fp32, and `Vector2` stores `real_t` = float32, so round-tripping through one is the only fp32 cast GDScript has. This matters because the hash **amplifies**: `v` reaches ~9.2e3 before the final `fract`, where an fp32 ULP is ~1e-3, so a last-bit difference upstream emerges ~200× larger. A float64 port therefore does not give "the same answer, more precisely" — it gives a *different field*. Measured against a strict-fp32 model of the GLSL, the naive version diverged by mean 3.1e-3 / max 1.0 with **8% of lattice corners past `RIVER_HALF_WIDTH` (0.007)**, i.e. ~20% of river area where the blue you see and the wading you feel disagreed — precisely the failure this contract exists to prevent. The current form matches the GLSL bit-for-bit over all 289×289 lattice corners. Don't "simplify" any line of it back to scalar arithmetic. `ponytail:` the residual risk is a driver contracting the `dot` into an FMA; the durable upgrade is hashing the wrapped *integer* lattice indices with `uint` bit ops (GLSL ES 3.00 has them, GDScript ints are exact), which removes float precision from the equation but changes the field, so `RIVER_HALF_WIDTH` would need re-tuning by eye.

**Shader side** (`ground.gdshader`, extended not replaced): the original two-green vertex noise stays as the PLAINS look and as base mottling under every biome. `vertex()` gains `v_biome` (raw noise) and `v_world_xz`; `fragment()` blends the plains albedo toward `desert_color`/`forest_color`/`mountain_color` with `smoothstep` over `BIOME_BLEND` at each threshold (soft boundaries; chunk seams were already free because the field is one continuous world-space function), then derives the river band factor `v_river` from the interpolated `v_biome`, `mix`es in `river_color` by it and pulls `ROUGHNESS` toward 0.3 for a wet sheen. **All the noise stays per-VERTEX**; the two per-fragment additions are the river band factor (a subtract, an abs and a `smoothstep` — no noise) and, guarded behind `if (v_river > 0.0)` so the ~95% of pixels outside a river pay nothing, the shimmer. **The band factor must NOT be a varying:** the band is ~8 m wide and its soft edge spans under 2 m, while the ground plane's vertex spacing is ~3 m (16×16 over a 50 m chunk), so interpolating it undersamples the one nonlinear quantity in the shader and the blue you *see* parts company with the wading zone you *feel* by a metre or two — exactly what the CPU/GPU parity contract exists to prevent. `v_biome` itself is safe to interpolate (a 400 m wavelength is near-linear over 3 m).

**Determinism: independent stream + post-draw skips.** New geometry uses its own stream — `spawn_biome_content_in_chunk` seeds `hash(Vector3i(cx * 83492791, cy * 15485863, run_seed ^ BIOME_SALT))`, deliberately *different* multiplier primes from the artifact/object streams (73856093 / 19349663) so the sequences can't correlate. Every place a biome *removes* an existing placement is a `continue` **after** the RNG draws that produced the candidate — the draws still advance the stream. Sites: `spawn_objects_in_chunk` (river skip, plus the desert thinning below), the four `spawn_feature_structure` builders (one centre test each — a centre check is deliberately enough; no footprint-vs-band intersection), `spawn_crocodiles_in_chunk` (river skip with `chunk_croc_target` **untouched** — the retry budget absorbs it), and `_artifact_at` (the river test is folded into the *existing* candidate-acceptance condition, so the 2-draws-per-try shape is unchanged). **One exception to "the world outside rivers is byte-identical to before biomes existed", worth knowing when auditing determinism:** a feature structure rejected for standing in a river `return`s *before* its own `create_box` loop, and `spawn_feature_structure` runs off the **shared chunk RNG** ahead of the scattered-block loop — so those 10–60 skipped draws reshuffle that one chunk's scattered blocks, including blocks nowhere near the water. Hoisting the draws to keep them would be a large change for a property with no gameplay value; what is load-bearing is determinism **within** a run, and that holds unconditionally because `is_river_at` is a pure function. **Coins and bosses are deliberately not excluded**: road coins in a river stay (wading for coins is the intended micro-decision) and bosses own road stations, which are the one thing that crosses a river.

**What each biome builds** (`spawn_biome_content_in_chunk`, gated by `@export var spawn_biome_content`, wired into `create_chunk` **after `spawn_artifact_in_chunk` and before `_build_block_multimesh`** — same ordering contract as artifacts, so the geometry joins the chunk's single MultiMesh + single `BlockCollision` body and its footprints land in `obstacles` before crocodiles and coins read them). The chunk **centre** picks which builder runs; individual builders re-test `biome_at` at each candidate's own position so biome edges feather across chunk seams instead of stopping dead at one.
- **DESERT** — sparse, not empty. The emptiness comes from `spawn_objects_in_chunk` dividing its scattered-block **target** by `DESERT_BLOCK_KEEP_EVERY` (3) — a **target, not a roll**, so no draw is inserted anywhere (measured: 4 scattered blocks per desert chunk vs 12 on plains). An earlier version keyed the skip off the loop's `attempts % 3` counter instead; that was silently a no-op, because `max_attempts` is `objects_per_chunk * 3`, so exactly `objects_per_chunk` attempts stayed eligible and the quota still filled (~84% kept). The builder then adds 4–9 cactus stacks (2–3 thin green boxes, sometimes one arm), kept `CACTUS_ROAD_CLEARANCE` 12 m off the road — cactus footprints are non-climbable, so one standing on the coin swath makes `_settle_coin_y` **skip** road coins rather than perch them, punching holes in the trail. **Croc density is unchanged** — a desert reads empty through decoration only, per the "entity counts are never reduced" rule.
- **FOREST** — 25–40 trees, each one solid trunk box + 2–3 shrinking canopy slabs passed `collide = false`. All of it rides the chunk's one MultiMesh, so **a forest chunk is the same single block draw call as a plains chunk**; only trunks pay a `CollisionShape3D`. Each trunk appends a **non-climbable** footprint stopping at *trunk* height — non-climbable on purpose, so `_settle_coin_y` **skips** a road coin over a tree instead of perching it 5 m up in the canopy where nobody can reach it.
- **MOUNTAIN** — 2–4 massifs, each a stack of tapering boxes (8–20 m tall) with per-layer yaw and lateral jitter so it doesn't read as a wedding cake, grey scree colours from a small ramp, and the top 1–2 layers forced snow-white above `MOUNTAIN_SNOW_HEIGHT`. The layer count is **not rolled** — it is `maxi(2, int(height / MOUNTAIN_MIN_LAYER_HEIGHT))` (4 m), so 2–5 layers. That is what makes "impassable, walk around it" true: at 8 m over 7 layers a massif would be a 1.14 m staircase with a 1.7 m ledge per level, i.e. a walkable ziggurat, and the player's jump apex is 3.61 m. (An earlier version drew a 4–7 count and clamped it with the same expression; the clamp always won, so the draw was dead and the "4–7 layers" never happened.) Bases keep `MOUNTAIN_EDGE_MARGIN` (10 m, covering the rotated `MOUNTAIN_BASE_WIDTH_MAX * 0.71 + MOUNTAIN_LAYER_JITTER` = 9.73 m reach — layers are yawed, so the half-*diagonal* is the bound, not the half-width) from the chunk edge so a massif never straddles a seam, while still leaving a 30×30 m placement box so peaks spread out instead of piling into every chunk's centre. Massifs are overlap-tested against **other massifs plus any obstacle already in the chunk with `radius >= MOUNTAIN_AVOID_RADIUS` (2 m)** — a local `avoid` list, not the chunk's full `obstacles`: a massif footprint radius is ~9.7 m, so demanding clearance from all dozen scattered blocks (radius ≤ 1.78 m) would cover the whole chunk and mountains would stop generating, and a block swallowed by rock is invisible anyway — but an artifact (radius ≥ 2.5 m) swallowed by rock takes its coin ring and its one guaranteed gem with it. One non-climbable footprint each with the real top height.

**`_biome_spot_ok(chunk_center, local_x, local_z, radius, road_clearance, obstacles)`** is the single home of the "would something solid here spoil what is already there?" rule: true when the spot is **not** in a river, is at least `road_clearance` from the coin-road centerline (`_road_lateral_distance`), and its `radius` overlaps nothing in `obstacles`. Callers pass different clearances — `CACTUS_ROAD_CLEARANCE` 12 m, `FOREST_ROAD_CLEARANCE` 14 m (≥ half of `road_width_max` 20, so the scattered coin swath stays tree-free) and `MOUNTAIN_ROAD_CLEARANCE` 24 m, which buys **a canyon through the range for free**. `radius` is always the **widest the thing could be**, because the real width is drawn *after* this call and reordering the draws to know it exactly would shift the biome stream for nothing. Its river test is **inert as the constants stand** (`RIVER_LEVEL` 0.5 falls inside the plains band, and these three callers only build in desert/forest/mountain) — kept as the thing that stays correct if `RIVER_LEVEL` or the thresholds are retuned; the river exclusions that actually fire are the plains-capable ones listed above. There is no upper bound on the clearance: `_road_lateral_distance(world_x, world_z, clearance)` sizes its station scan window from the clearance it is handed (it used to hardcode `ARTIFACT_ROAD_CLEARANCE` 14, which left `MOUNTAIN_ROAD_CLEARANCE` 24 just under the honest-answer bound).

**Player + audio side — you visibly sink, jump worse, and move slower.** `player_controller.gd`'s whole river awareness hangs off `_terrain_is_river_here()` (group `"terrain"` + `has_method("is_river_at")` guard, modelled on `_weather_is_raining_here()`, returns false when absent so the player scene still runs standalone), which sets `var is_wading` once per physics tick, and only while `is_on_floor()` — flying over a river is not wading. The flag itself needs **no reset plumbing**: it is recomputed from scratch every tick and holds no history. `scripts/wade_selfcheck.gd` (see Commands) is the runnable proof of all four effects below, and it is mutation-tested against five ways to break them silently.

- **`is_wading` is computed at STEP 1.5, ABOVE the jump step, and that placement is load-bearing.** It used to sit at STEP 6.5, immediately before `calculate_current_speed()`, which was fine while speed was its only consumer. The jump now reads it too, and reading it after the jump would hand the jump the **previous** frame's answer — wrong in exactly one case, which is exactly the case the design calls out: a **coyote-time jump** off a river bank, where the previous frame was grounded-and-wet and this one is airborne. Nothing between STEP 1 and STEP 6.5 ever read the flag, so the move is inert for every other consumer.
- **SLOWER: `WADE_SPEED_FACTOR` (0.5) multiplies into the grounded gaits only** in `calculate_current_speed()`; Windman's `WINDMAN_AIR_SPEED` early-return is untouched. It was deepened from 0.6 on owner feedback ("slower in general while submerged") — and it bites **walk and duck alone**. **The run gait is floored at `WADE_RUN_MIN_SPEED` (9.0), which is a HARD CONTRACT and was not touched**: the difficulty rule is "running always escapes", which is why `MAX_CHASE_SPEED` (8.5) sits under the slowest character's run (10.0 × 0.9 = 9.0). The raw factor would drop that run to 4.5, below even `BASE_CHASE_SPEED` 5.5, turning a river into an unescapable trap (crossings are not length-bounded — see the `RIVER_HALF_WIDTH` note). The floor already absorbed the whole drag at 0.6 and still does, so deepening the factor **cannot** be read as making the run slower; the self-check pins `run_wet > MAX_CHASE_SPEED` by reading the cap out of `piglet_crocodile_ai.gd` rather than re-typing it.
- **WEAKER JUMP: `JUMP_VELOCITY * WADE_JUMP_FACTOR` (0.75) when the jump starts from wading.** The consequence is deliberate and worth stating plainly: apex drops from `JUMP_VELOCITY² / (2 × gravity)` = 3.61 m to **2.03 m**, which is *below* the 2.5 m top of a single decorative block — a block you can hop onto from the bank is genuinely unjumpable from inside the water. That reads as "jumping is harder in water", not as a bug; wade out first. Because it keys off `is_wading`, which is only ever true while grounded, a **coyote jump keeps full power** — it was pushed off a bank, not off water.
- **VISIBLE SUBMERSION, and it is a MODEL OFFSET — never physics.** `_wade_sink` eases toward `WADE_SINK_DEPTH` (0.35 m) at `WADE_SINK_EASE_SPEED` (depth / 0.2 s) and is written to **`$CharacterModel.position.y` and nothing else**, exactly as the walk bob and the landing squash write to the model's own nodes. The `CollisionShape3D`, the body's `global_position` and the flat-world `y = 0` plane are untouched — every y-placement site in the project (coin heights, croc gravity settle, the spawn point, block bases) assumes that plane, so "submerged" has to be a picture. Nothing else writes `$CharacterModel.position`, so the offset owns that property outright: Teibi's resize tweens `scale`, the landing squash writes `scale` plus `$CharacterModel/Body.position` — **different properties, so none of them fight**, which is why this composes with both instead of needing to know about either. `ponytail:` the depth is **fixed**, not scaled by Teibi's form — a river is a river, so giant Teibi is barely wet and small Teibi is in up to the chest, which reads correctly and costs no coupling to the resize state. **First person dips by the same amount**: `_first_person_eye_position()` subtracts `_wade_sink`, so every path that re-seats the arm (`_apply_view_mode`, a Teibi resize, a character switch) gets it for free, and the submersion is *felt* rather than merely watched. `_apply_wade_sink()` is idempotent like `_apply_view_mode()`. The ease runs **below** the frozen-window early returns, so a player frozen mid-river stays sunk through the respawn countdown; **Both teleport paths zero it** — `reset_position()` and `_place_near()` (the shared ring-probe landing behind `join_at()` *and* the in-room "respawn back with the group") — because unlike `is_wading` the eased value does hold history, and the frozen grace window early-returns out of `_physics_process`: without the reset a player who died wading would stand 0.35 m sunk, camera and all, at the group's dry feet for the whole countdown. Landing in *another* river just eases back down over the next fifth of a second, which is the right reading of "arrived somewhere new". That is the only reset plumbing wading needs.
- **Multiplayer: a teammate wading sinks too, and NOTHING was added to the presence packet.** `remote_avatar.gd` mirrors the same offset onto its `model_root` using the *same* constants read off its existing `PLAYER_SCRIPT` preload (so the two can never drift), gated on the on-floor bit presence has always carried plus a null-safe `"terrain"` group `is_river_at(target_pos)`. `is_river_at` is a pure function of world position and the shared run seed, so "is that peer standing in a river" is something every peer can work out locally for free. The name tag hangs off the avatar root, not `model_root`, so it stays at a readable height.
- **Audio (unchanged):** at the existing footstep hook in `update_character_animation`, a one-line ternary fires `"play_splash"` instead of `"play_footstep"`, so the splash cadence comes free from the walk sine's zero crossings (no new timer). `sound_manager.play_splash()` **replays the existing footstep buffer** at `SPLASH_PITCH` 1.9 and ~5 dB louder — a brighter, wetter slap — through `_play_oneshot`, so it inherits the `_unlocked` gesture gate and bakes no new stream (the "no audio asset files" invariant holds).
- **Self-check gotcha worth keeping:** a `jump` press synthesized from a `physics_frame` handler is stamped with the **next** physics frame, so the frame the tree runs immediately after `Input.action_press` does not see `is_action_just_pressed` — the one after it does. With one `await physics_frame` the press is released before anything ever sees it and the jump silently never fires; the coyote case additionally has to press *at the same instant* as the step-off, or it gains a frame of slack and passes over the frame-late-`is_wading` bug it exists to find (measured — it did, until the harness was tightened).

## Performance & web build
The game ships primarily as a **web (WebGL) build**, which is the performance-sensitive target. Several systems exist purely to keep it smooth in a browser without changing how it looks or plays on desktop:

- **Debug perf overlay** (`scripts/perf_overlay.gd`): a `Label` named `PerfOverlay` under the `HUD` `CanvasLayer` in `main.tscn`. Shows FPS, process ms, physics ms, draw calls (`RENDER_TOTAL_DRAW_CALLS_IN_FRAME`), primitives, total node count, and `Crocs (active/total)`. **Toggle with F3.** It starts visible only in `OS.is_debug_build()` and stays hidden in release until F3 is pressed, so it never ships in the player's face. This is the measurement tool — use it to prove perf changes and catch regressions.
- **Simulation LOD** for crocodiles — see the "Crocodile simulation LOD" section above.
- **MultiMesh block rendering + consolidated per-chunk collision** — see "Everything in the world is spawned procedurally" above.
- **Web-only render/GPU tuning** in `project.godot` `[rendering]` via Godot's `.web` per-platform override suffix (the un-suffixed key is the desktop/editor default, the `.web` key only applies in the HTML5 export): `renderer/rendering_method.web = "gl_compatibility"` (the lightweight WebGL2 path; desktop keeps `Forward Plus` from `config/features`), `anti_aliasing/quality/msaa_3d.web = 0` (desktop keeps `msaa_3d = 2`), `lights_and_shadows/directional_shadow/size.web = 1024` (shadows stay **on**, just smaller), and `scaling_3d/mode = 0` + `scaling_3d/scale.web = 0.8` (renders web at 80% then upscales; desktop scale stays 1.0 and `mode = 0`/Bilinear is inert there).
- **Runtime tuning** in `endless_terrain.gd`: `_ready()` lowers `render_distance` to `WEB_RENDER_DISTANCE = 3` on web only (49 active chunks vs 121 on desktop, gated behind `OS.has_feature("web")`), and `_setup_fog()` enables exponential depth fog **on every platform** — the sanctioned exception to the web-gate rule, see "Performance conventions" below. `fog_light_color = FOG_COLOR = Color(0.85, 0.86, 0.80)`, which **must equal** `sky_horizon_color` and `ground_horizon_color` in `main.tscn` (the fog-tracks-horizon contract: if the sky changes, all three move together, so the view edge dissolves into the sky); `fog_sun_scatter = 0.15` adds a gentle bright streak toward the warm sun. Only the **density** stays platform-gated: `FOG_DENSITY_WEB = 0.005` (thick — masks the short web view distance) vs `FOG_DENSITY_DESKTOP = 0.0022` (thin depth haze over the long desktop view). The fog is built on a runtime `duplicate()` of the `WorldEnvironment.environment` so the shared inline SubResource is never mutated.

### Performance conventions (important)
When optimizing, follow the split this work established:
- **Visual-affecting changes are web-gated.** Anything a player could see (renderer, MSAA, shadow size, internal resolution, render distance) must be limited to the web build via `OS.has_feature("web")` at runtime or a `.web` project-setting override. Desktop/editor stay at full quality. **One sanctioned exception: fog is universal** — an owner-approved art-direction call (desktop gets the thin 0.0022 haze so the horizon dissolves instead of hard-edging). The fog *density* is still platform-gated, so the perf/view-distance side of fog remains a web concern; don't use the fog exception as precedent for other visual changes.
- **Purely invisible optimizations are global.** MultiMesh batching, crocodile simulation LOD, and consolidated collision change neither look nor gameplay anywhere, so they run on every platform (and benefit desktop too).
- **Entity counts are never reduced as an optimization.** Same blocks per chunk as before; croc count per chunk changes only by *design* (the distance-scaled density in the difficulty gradient), never for perf. (Coins are an exception only because their placement changed by *design*, not for perf: they are now road-shaped rather than uniform per-chunk scatter, so off-road chunks legitimately have no coins — see "coin road" above.) Distant crocodiles are **slept** (frozen, monitoring off), never removed — counts stay unchanged and gameplay near the player is identical.

## Multiplayer lobby service (`server/`)
A small Go service — **the only server in the multiplayer architecture** — sharing this repository with the game and nothing else. It does **signalling, membership and master-naming**, and deliberately no game logic and no game state: rooms live in memory in one `Hub`, and a restart just drops them (clients re-create a room from its 6-character invite code). Everything else about multiplayer is peer-to-peer. **One documented exception to "no persistence"** (owner order, 2026-08-25): `best.go` keeps per-player best-run records for `GET`/`POST /best` — see "Personal best-run records" above for why the client cannot keep them itself. It is a JSON file dumped every 30 s, not a database, and it is the ONLY persistent state in the service.

- **Four files, one responsibility each.** `room.go` is the whole state machine (rooms, membership, master election, hero assignments, signal fan-out) and imports no network types, so tests drive it directly; `conn.go` is the websocket layer that turns a socket into a `*Member` and translates inbound JSON into `Room` method calls; `best.go` is the best-run store and its handler, sharing nothing with the hub; `main.go` is config-from-env plus six routes (`/ws`, `/ice`, `/rooms`, `/best`, `/healthz`, and the embedded test page at `/`). Full protocol table in `server/README.md`.
- **A new route must also be added to the Traefik path list in `server/docker-compose.yml`.** The game client's catch-all owns `/` in production, so a route missing from the lobby's narrow rule silently serves `index.html` — it works locally and 404s (or returns HTML) deployed. `/best` is on the list; `main.go` carries the reminder at the `mux.HandleFunc` call.
- **The master is the oldest surviving member** (lowest global join `seq`). Re-elected on master disconnect, and when strictly more than half of the *non-master, non-voted-out* members send a `stalled` report naming it **and the lobby has itself heard nothing from that master for `stallMasterSilence` (3 s)** — the stall *detection* is client-side, but the lobby refuses to act on a claim it can see is false. **That corroboration is load-bearing, not defence in depth:** "strictly more than half the non-master members" is **one** vote in a two-member room, and every room code is public over `GET /rooms`, so without it a stranger joins a room somebody is hosting alone, sends a single `stalled` frame, and owns pickup arbitration, croc sync, the `dead`/`flee` broadcasts and the only accepted `seed`. It costs nothing to satisfy honestly: the master heartbeats over the relay once a second, which is a socket read here. `Member.lastSeen` is an `atomic.Int64` because it is written from the peer's own read goroutine and read under the hub mutex; it is stamped at join too, or the first vote against a member that has not spoken yet would succeed. A **voted-out peer keeps its socket but loses its vote, and leaves the electorate on both sides of the comparison** — otherwise one peer that hiccups once forms a quorum against every master the room ever elects. **A vote EXPIRES after `stallVoteTTL` (10 s, ~5× the client's `STALL_REPORT_INTERVAL`) and is pruned before every count**: a report is evidence about right now, and a monotone set means two peers whose connections hiccuped at unrelated moments an hour apart still add up to a quorum against a perfectly healthy master, each spurious migration costing a visible croc-sim handover. A peer that still believes the master is gone keeps its vote alive by re-sending on its own timer. A voted-out peer is never elected again while the room lives, **unless** every remaining member has been voted out, in which case the slate is wiped rather than leaving the room master-less.
- **The lobby never inspects `payload`.** Offers, answers and ICE candidates all ride the same opaque `signal` relay — that opacity is the point, and it is what keeps the server out of the game.
- **Trust-boundary guards that must stay:** a 64 KB read limit, a **32 KB cap on the relayed `signal` payload** (the read limit bounds the *inbound* message, but the lobby re-frames it — a 65509-byte payload is accepted at exactly 65536 and relayed at 65562, past the 65535-byte default inbound buffer of the Godot `WebSocketPeer` on the other end, so one message would drop every other peer in the room), a **byte-denominated** per-connection token bucket (a per-*message* bucket let 130 × 64 KB frames through before firing, ~8 MB fanned at peers whose queues are 64 frames deep — measured on a 4-peer room, every victim was evicted inside 100 ms while the flooder was still inside its budget, i.e. exactly what the bucket exists to prevent), a 32-character display-name clamp, a 4-member room cap (the game's player limit), `maxListedRooms` (200) bounding the work one unauthenticated `GET /rooms` provokes under the hub mutex, and a bounded per-peer send queue — a peer that cannot drain it is disconnected rather than silently dropped, because a lost ICE candidate is a connection that never forms. A ping every 20 s reaps peers whose TCP died without a close frame; without it a crashed master would hold its title forever.
- **`GET /ice` serves the STUN/TURN config from the deployment's environment**, so TURN credentials are never baked into the game build.
- Deployment is the owner's standard git-ops compose pattern: `server/Dockerfile` + `server/docker-compose.yml` (lobby behind Traefik at `wss://$LOBBY_HOST/ws`, plus a coturn container on the **host network** — a TURN relay hands out a port range, which the bridge would make painful). **`network_mode: host` is exactly why coturn's `--denied-peer-ip` list has to be complete:** an unblocked range is a pivot into the deployment host, and `/ice` hands the credentials to any unauthenticated caller — CORS is browser-only, so `curl` gets them regardless. RFC1918 alone left loopback (the lobby itself), cloud instance metadata on 169.254/16, CGNAT and **every IPv6 address** relayable; the list now covers those plus `--no-loopback-peers` and `--user-quota`/`--total-quota`. **The credentials themselves EXPIRE whenever the deployment sets `TURN_SECRET`:** `turnCredentials()` in `server/main.go` mints coturn's REST pair per `/ice` call (username `<unix expiry>:ck`, credential `base64(HMAC-SHA1(secret, username))`, TTL `turnCredentialTTL` 24 h — long enough that a credential never expires under a player mid-room, since coturn re-checks the timestamp on every authentication), so a scraped response goes stale instead of relaying forever. **The two halves cannot be migrated one at a time and are deliberately gated on the same one variable:** `docker-compose.yml` passes coturn `--use-auth-secret`/`--static-auth-secret` only via `${TURN_SECRET:+…}` (which expands to an empty argument when unset — coturn 4.6.3 ignores those, so an un-migrated deployment gets byte-identical args), and with the secret configured coturn refuses the static `--user` pair outright (`check_stun_auth: Cannot find credentials of user <…>`) — which is exactly why `turnCredentials()` falls back to `TURN_USER`/`TURN_PASSWORD` when no secret is set rather than always minting REST pairs. `.github/workflows/lobby.yml` is gated on `server/**`, never touches the Pages deploy, and **only tests** (vet, gofmt, `go test -race`, a no-push image build) — publishing lives in `build.yml`, see "CI/CD" below.

## Multiplayer (phases 3–5): WebRTC mesh, presence, mid-run join, shared crocodiles
2–4 browsers in a room see each other running in the **same** world. Phase 5 added the **shared crocodile simulation**, **pickup claim arbitration**, a **shared game over** and **master migration** on top of phases 3–4; weather and fauna are still fully local per peer and deliberately ignore remote players. Six things travel — the **world seed** (so everyone generates the same terrain), a 15 Hz **presence packet** per peer, a one-shot **join snapshot** per (incumbent, joiner) pair so a peer arriving mid-run inherits what it missed, a 10 Hz **crocodile sync** from the master, a **claim → confirm** round trip per pickup, and a 1 Hz **heartbeat** on the relay. Phase 4 added the hero split, the shared bank / lives / distance and the join placement on top of phase 3; phase 5 added the last three on top of phase 4; every earlier rule below still holds. Six client scripts plus one terrain entry point:

- **`scripts/lobby_client.gd`** (`class_name LobbyClient`) — a `WebSocketPeer` wrapper over the Go lobby's `/ws` protocol plus an `HTTPRequest` fetch of `/ice`. It knows nothing about WebRTC, the world or the UI: it turns JSON frames into signals (`joined` / `peer_joined` / `peer_left` / `master_changed` / `heroes_changed` / `relay` / `lobby_error` / `closed`) and `send_signal_to()` / `send_hero()` calls back into frames. It leans on three things the lobby's code guarantees — `welcome` is **always the first frame** and already carries the master (only *later* changes arrive as a `master` frame), `welcome.members[]` **includes yourself**, and peer ids are 16 lowercase hex characters. `heroes_changed` is emitted from **both** the `welcome` frame and every later `heroes` broadcast; only `welcome` carries the `pool`, so the client remembers it (`_hero_pool`) and re-emits it with each assignment-only broadcast — a subscriber always gets the whole picture and never has to remember half of it. The `pong` frame is parsed and deliberately unused (stall detection is phase 5). **A typo is not a room:** the lobby *creates* any well-formed code it does not know (`server/room.go`'s `Join`), so one wrong character in a 6-character code joins a brand-new empty room and looks exactly like success from the `welcome` frame. `MpManager` keeps the code it asked for and treats "typed a code, came out alone AND master" as the typo — it says so and leaves, instead of two friends watching member lists that never grow.
- **`scripts/mp_manager.gd`** (`class_name MpManager`, node `Multiplayer` under `Main`, group `"mp"`) — owns the lobby socket, the `WebRTCMultiplayerPeer` mesh, seed distribution, presence, the hero pool, the join snapshot, the room's shared totals, and — phase 5 — the crocodile sync, the pickup claim arbitration, the dead-croc set, the ability requests and the master heartbeat / stall watch.
- **`scripts/remote_avatar.gd`** (`class_name RemoteAvatar`) — one remote peer, rendered with the existing character scenes and the project's procedural limb animation. Visual only.
- **`scripts/mp_ui.gd`** — a code-built `Control` under `HUD` (an "MP" button bottom-left opening a host / join / code / **hero row** / member-list / leave panel), found via the `"mp"` group with `has_method` guards, so a scene run without the manager shows an inert button. **Not** touch-gated: hosting is a desktop feature too and there is no keyboard shortcut for it. Every button it builds goes through `_make_button()`, which sets `focus_mode = Control.FOCUS_NONE` — **that is load-bearing, not cosmetic**: `ui_accept` is Space, Space is jump, and a focused button would fire on every jump for the rest of the run. The hero row's buttons are built through the same helper for exactly that reason (the invite-code `LineEdit` is the one control that keeps focus, and it releases it on submit/close).
- **`scripts/teammate_locator.gd`** (the `TeammateLocator` `Control` under `HUD`, bottom-centre, group `"teammate_locator"`) — a **Minecraft-style bearing strip**: the centre is straight ahead, and a teammate's marker slides left or right as you turn. The bar spans a **full turn** (bearing 0 at the centre, ±PI at the two ends), so a teammate is always somewhere on it and nothing needs clamping or hiding; the price is a seam directly behind you, which is the honest place for it — the one bearing you cannot walk toward. Distance modulates marker height *and* alpha together, floored at `LOCATOR_RANGE` (250 m) rather than hidden, because the direction of somebody 800 m away is still the most useful thing this bar can say. **Solo it does not exist** (`peer_markers()` answers null → hidden, nothing scanned, nothing drawn). Its perf shape is a **deliberate split, not the minimap's flat 5 Hz**: positions are re-read on the throttled tick because that call crosses a boundary and allocates, while **bearings are recomputed every frame** because that is the thing the player is watching — at 5 Hz a mouse turn steps the markers across the bar in visible jumps — and a redraw is only queued when the facing actually moved (or the snapshot refreshed), so standing still costs nothing. Two primitives when visible: one backdrop rect and ONE `draw_multiline_colors()` carrying every marker **and the centre notch** (slot 0 of the buffers, which is why they hold `MAX_MARKERS + 1` segments). **Measured F3 delta for the whole feature — locator plus minimap dots, 3 teammates, against a paused world: +2 draw calls; 0 solo.**
- **`scripts/mp_selfcheck.gd`** — `extends SceneTree`, run headless with `godot --headless --path . --script res://scripts/mp_selfcheck.gd`. Prints `SELFCHECK OK` / exits 0. It guards the isolation contract **for every one of the four playable characters, with a fresh avatar per index** (one scene would let an `Area3D` added to three of them through, and `set_character` silently drops a swap inside `SWAP_COOLDOWN_MS`, so re-using one avatar would re-walk the first model four times), all three decoders (`decode_presence`, `decode_state`, `decode_croc_sync`), the forced seed, the peer-id mapping, `Coin.id_at()`'s stability plus a live coin's id surviving its bob, `shared_lives_from()`'s arithmetic, `room_multiplier_from()` pinned against `player_controller`'s own streak constants, `croc_id_for()`'s stability and per-name distinctness (including a live croc's `croc_id()` matching it), the hero-name → `CHARACTERS` index lookup, and `_anchor_of()`'s group-anchor rule (a spread group must never anchor on the empty midpoint — **including for a dying master, which is never in `_peer_state`**) — the pure things a refactor could break silently. It also holds the one **effect** measurement in the file: the join snapshot's two world sweeps, driven against real nodes (two live crocodiles, two live chests) **with a negative control each**, because a kill list that squashes every crocodile in the world and one that squashes none both "work" from the inside and neither shows up headless. It likewise pins the kill list's **master-only** rule from both sides (a stranger's snapshot must delete nothing; the master's must land) — a `from == _master` test that never passed would take the whole fix back out with every other assertion still green, because those drive `_absorb_dead` directly. Mutation-tested, all seven caught: dropping the `squash_and_die` call, dropping the `fresh.has(id)` test, dropping the chest loop, dropping the `dead` list's validator, and the authority test forced to each constant. The `"t"` discriminator is pinned from both ends **through `packet_kind()`** — a phase-3/4 packet with no `"t"` reads as presence, a packet whose `"t"` names an unknown verb reads as that verb — because that is the only form of the assertion that can fail. The forced-seed check likewise sets **two different seeds** and requires the biome offset to change, or a `_roll_biome_offset()` ignoring its seed entirely would satisfy it. Don't grow it into a suite and don't put anything needing a socket in it.
- **`scripts/mp_e2e.gd` + `scripts/mp_e2e.sh`** — the automated two-instance check of the **relay path**: the shell script builds and starts a local lobby on a per-run port, runs one headless Godot as `--role=host` (which prints `E2E_ROOM=` / `E2E_SEED=`) and a second as `--role=join --code=…`, and fails unless both printed the **same** `run_seed`. This is the standing evidence for the production bug in "seed distribution" below. A **second phase** proves phase 5's master migration over the same relay: the host is restarted with `--stall` (which sets `heartbeat_enabled = false` — a simulated throttled tab) **while keeping its socket open**, because letting it disconnect would fire the lobby's ordinary disconnect re-election and the test would pass for the wrong reason; the joiner runs with `--await-master` and the script fails unless its `E2E_NEWMASTER` equals its own `E2E_YOU` and differs from the host's. A **third phase** (`--role=drag`, printing `E2E_NODRAG=`) is the regression check for the mid-run drag above — and it is deliberately **one instance with no lobby traffic**, because the assertion is about arrival *timing* and two real processes cannot schedule "late": the joiner is placed within one relay round trip, long before the harness can throttle anything (measured while writing it). It therefore drives `_on_lobby_joined` / `_on_lobby_relay` directly, with an `_ensure_lobby()` LobbyClient that was never connected so its outbound frames drop silently instead of erroring on a null. A **fourth phase** (`--role=respawn`, printing `E2E_REGROUP=`) is the same one-instance shape again, for the same reason — the trigger under test is the *local* respawn event, not anything on the wire — and covers the in-room death respawn: it runs the **solo negative control first** (out of a room, the player must not move by so much as a metre), then dies 600 m from the group and fails unless the player comes back inside the join ring *and* `own_distance_origin` moved by exactly the teleport. It asserts the anchor `group_anchor()` actually offered, not only where the body ended up — the same anti-vacuity rule the drag phase's seed-adoption assertion follows. **The host must use `host()`, never a fixed shared code** — a fixed code is indistinguishable from a typo to the *first* instance, so the typo guard would drop it and the test would fail for the wrong reason. **ponytail:** it covers the relay (room, seed broadcast, adoption), not the mesh or the avatars — desktop headless has no `webrtc-native` addon, hence `--lobby-only`; once the addon is vendored the upgrade is to drop that flag and additionally assert one remote avatar per instance. Wiring it into CI is a one-job follow-up (`.github/workflows/` is owned elsewhere).- **`fetch_webrtc_addon.sh` + `scripts/webrtc_addon_check.gd` — the desktop-only WebRTC install, and its proof.** Godot 4.5's desktop builds ship the WebRTC *classes* but no implementation (`WebRTCPeerConnection.new()` returns null), so `MpManager.webrtc_available()` is a `FileAccess.file_exists` probe of `WEBRTC_ADDON_PATH` and desktop MP is dead without the official `webrtc-native` GDExtension. The script installs it from a **pinned release URL + SHA-256** (bump both together; GitHub publishes the hash as the release asset's `digest`) and then runs the check, which is the opposite of `mp_selfcheck.gd`: it exists to **fail** on a desktop machine that has not installed the addon. **The addon is fetched, never vendored** — 37 MB / 92 MB unpacked of binaries for twelve platform/arch pairs the production build never uses, and its bundled libraries (libdatachannel, libjuice, plog) are **MPL-2.0**, which attaches source-availability duties to a redistributor; `webrtc-native` itself is MIT and the rest of the bundle is BSD-3 (libsrtp, usrsctp) / Apache-2.0-or-GPL-2.0 (mbedtls). Three gotchas worth keeping: (1) upstream unpacks to `addons/webrtc_native/webrtc_native.gdextension` while the game probes `addons/webrtc/webrtc.gdextension`, so **the script renames both** — safe only because the library paths inside a `.gdextension` are relative to that file, not `res://` absolute; (2) the Web preset's `exclude_filter="addons/*"` is what makes an installed addon *structurally* unable to reach the published build (without it the export warns "No wasm32 library found" and packs the stray `.gdextension`) — `addons/` being gitignored already keeps it out of CI, the filter covers the developer exporting locally; (3) a GDScript runtime error unwinds the erroring function and returns the **default** for its return type, so a `mp_manager.gd` that failed to compile would have made the check print `WEBRTC OK` — hence its `has_method` guard, and hence the `--import` step (a never-opened clone has no global class cache and `class_name` types do not resolve). The phase-4 `--lobby-only` flag is the *other* answer to the same problem: it skips the WebRTC probe and the mesh entirely so the relay path stays testable headless with no addon at all (see `mp_e2e.sh` above).

**The feature is inert until a room is joined, and that is the rule that keeps solo play byte-for-byte unchanged.** `mp_manager._process` early-returns while `_state == OFFLINE`, no socket is opened, no avatar exists, no other system is touched — the same "idle unless active" discipline `mobile_input.gd` follows, for the same reason. Every phase-4 read is null-guarded the same way: the player's single `_mp()` group lookup, `coin.gd`'s two, and every shared-total call returning `null` offline so the caller falls through to solo semantics on one `== null` test. `leave()` unwinds everything — including `_collected_ids`, `_peer_state`, `_heroes`/`_pool`, the frozen `_gone_*` totals, the join latches and the seed-request counters — and is idempotent, so a dropped socket, a lobby error and the Leave button all land in exactly the same place. (`_room_seed` is deliberately *kept* across `leave()`: leaving a room must not regenerate the ground under the player's feet. **`_has_seed` is deliberately CLEARED**, though — it is the "already adopted" latch `_receive_seed` early-returns on, and carrying it across a leave silently drops the *next* room's seed, so "host, nobody joins, leave, join a friend's code" would connect happily onto two different worlds.) The one thing that is **not** inert while offline is the node's `process_mode`, which is `PROCESS_MODE_ALWAYS`: a paused tree that stopped `LobbyClient._socket.poll()` would stop answering the lobby's 20 s ping and get the peer reaped out of its own room.

**Two places relay traffic can arrive before it can be used, and both are handled rather than dropped.** `_on_lobby_joined` cannot build the mesh immediately — it first fetches `/ice` over HTTP — while the lobby tells the peers already in the room about us *at once*, so whichever of them sorts lower by the offer rule offers into that window. `_buffer_signal()` parks offers/candidates for a peer with no connection yet (capped at `MAX_BUFFERED_SIGNALS` — it is peer input over an opaque relay) and `_add_peer` replays them in arrival order, which is the order WebRTC needs. Without it the loser of that race sits in a populated room whose avatars never appear, with nothing to re-offer and nothing to time out; localhost `/ice` answers in ~1 ms, which is exactly why the documented dev recipe never reproduces it. The symmetric rule is that `_rtc.remove_peer()` is only ever called for an id actually in `_connections` — it errors on an unknown one, and a peer that left inside that same window was never added.

**"Play Again" in a room rebuilds the SHARED world.** `player_controller.restart_game()` asks the `"mp"` group for `room_seed()` (null when offline or when no seed has arrived — a `null`, not a sentinel int, because `0` is a legitimate seed) and passes it to `new_run(seed)`; only a null falls through to the ordinary random re-roll. A local re-roll here would leave that peer on different terrain, biomes and rivers for the rest of the room's life while the avatars kept drawing at coordinates that no longer meant anything.

**The MP panel pauses the tree while it is open, and that is load-bearing, not polish.** `player_controller` reads gameplay through the *global* polled `Input` state and through `_input()`, neither of which a focused `Control` suppresses — so with the game running, every click inside the panel re-fires the desktop-web click-to-capture (warping the cursor to screen centre, making Join/Copy/Leave/Close unreachable after the first click) and typing an invite code walks, turns, switches character and fires abilities, because the lobby's code alphabet contains W, A, S, D, E, F, C and R. `process_mode` gates `_input` and `_physics_process` together, so one pause fixes both; `MpManager` being `PROCESS_MODE_ALWAYS` is what keeps the socket and the mesh alive underneath it. `mp_ui` carries the same `_paused_by_us` guard `pause_controller.gd` and `mobile_input.gd` use on each other, so closing the panel can never cancel somebody else's pause — and the reverse guard now exists on the phone too: `mobile_input.paused_by_driver` marks the pauses **it** owns, and both the touch resume overlay and the enable-overlay tap are gated on it, so a tap can no longer unpause the game underneath an open MP panel. Two exceptions the panel inherits from its siblings: it **does not pause over the Game Over screen** (`GameOverUI` is PAUSABLE, so pausing there kills Play Again — the panel still opens, it just leaves the tree running, which is safe because a game-over player is frozen and click-to-capture is itself `is_game_over`-guarded), and it **hides its button and force-closes while `touch_controls.has_modal()`** — `MultiplayerUI` is the last `HUD` child, so it draws over the three full-rect touch overlays and would otherwise steal the one gesture iOS grants motion permission and the browser grants WebAudio (the same three lines `mobile_settings_panel.gd` runs for its ⚙ gear). The portrait guard pauses on the **tree's** paused state rather than its own visibility for the same reason — latching visible under somebody else's pause would leave the game running behind an opaque guard once that pause lifted.

**THE ISOLATION CONTRACT — a `RemoteAvatar` is a picture of a player, not a player.** Three load-bearing rules: it joins **no group** (above all not `"player"`), it adds **no** `CollisionObject3D` / `Area3D` / `CharacterBody3D`, and it is parented to the MP manager, **never** to a terrain chunk (a chunk frees its children on unload, which would delete a peer mid-run). Rule 1 is the sharp one because this whole codebase discovers the player by group: a second node in `"player"` would be picked up, silently and wrongly, by `endless_terrain.gd` (chunk streaming would thrash between two positions), `piglet_crocodile_ai.gd` (crocodiles chasing a hologram), `crocodile_lod_manager.gd` (sleep/wake radii + coin animation LOD), `danger_vignette.gd`, `fauna_manager.gd` and `weather_manager.gd`. `fauna_manager.gd` is the precedent being copied — no group, no collision, hangs off its manager. `mp_selfcheck.gd` asserts rules 1 and 2 so a regression fails loudly instead of turning into "why are the crocodiles ignoring me?". The character scenes cost nothing to honour: they are already pure `Node3D` trees (they only ever live under the local player's `$CharacterModel`).

**`_rtc` is NEVER assigned to `multiplayer.multiplayer_peer` — the single most important line in `mp_manager.gd`.** The `WebRTCMultiplayerPeer` is used as a plain `PacketPeer`: `poll()` in `_process`, `put_packet()` / `get_packet()` / `get_packet_peer()`. Leaving the global `MultiplayerAPI` untouched is what keeps solo play unchanged — no scene replication, no RPC checks, no `multiplayer_peer` for some other system to trip over. There is still no shared simulation to replicate, so the whole high-level multiplayer stack would be cost with no benefit. (`grep -rn 'multiplayer_peer' scripts/` must never show an assignment.)

**Peer id derivation — a pure function, so the mesh needs no numbering protocol.** `MpManager.peer_int_id(lobby_id)` is `("0x" + lobby_id.substr(0, 7)).hex_to_int() + 2`: the first 7 hex digits give 28 bits, and `+ 2` clears the two ids `MultiplayerPeer` reserves (0 = broadcast, 1 = server). Every peer derives every *other* peer's int id the same way, so nobody has to be told what to call anybody. **Ceiling:** two of four peers colliding on the same 28-bit prefix is a ~2e-7 birthday chance; the upgrade path is the master assigning small ids over the relay, which costs a round trip this buys for free.

**The lexicographic offer rule kills glare with no round trip.** In `_add_peer`, the peer whose lobby id string sorts **lower** calls `create_offer()`; the other waits for it. Both sides know both ids the moment they learn about each other, so neither can end up offering at once (the classic glare that collapses both connections). Ordering gotcha in the same function: `_rtc.add_peer()` is called **before** `create_offer()`, because `WebRTCMultiplayerPeer` creates its data channels inside `add_peer` and they must exist before the offer describing them is generated. Setting a remote **offer** makes the connection generate the answer itself, which comes back through `session_description_created` — there is no separate `create_answer()` call.

**Seed distribution is MESH-INDEPENDENT and self-healing — this was a production bug, and both belts stay.** The seed travels over the **lobby relay**, not the mesh, because it has to arrive *before* any data channel is open: a joiner needs to regenerate its world at once rather than after ICE finishes. It is tiny and sent about once per room, so the relay costs nothing. (1) **Latched at `welcome`.** `_broadcast_seed_if_master()` is called from `_on_lobby_joined`, not from `_setup_mesh()`. It used to be latched only inside the mesh setup — i.e. after an HTTP round trip to `/ice` — so a master whose fetch was still in flight when somebody joined answered the direct send in `_on_lobby_peer_joined` with a silently-skipped `_has_seed` check, and **the joiner then walked its own private world for the room's life, with no error anywhere**. (2) **`seed_req` retry.** A peer still without a seed asks the master directly every `SEED_REQUEST_INTERVAL` (2 s), up to `SEED_REQUEST_MAX_TRIES` (10) — 20 s, long enough to cover a master still booting its terrain — then stops asking but **stays in the room**. `_tick_seed_request` runs **before** the `_rtc == null` guard in `_process` for exactly this reason. The master answers `seed_req` by latching from its own terrain first (the case a master elected before the seed reached it used to leave open) and then replying to the asker directly — it already missed at least one broadcast, so another broadcast is no use. (3) **Made visible.** The first retry emits `status` "Waiting for the shared world…" and giving up emits "No world from the host — is their tab still open?", which `mp_ui.gd` already renders, so a silent failure now shows in the panel with no UI change. The ordering fix removes the *known* way the direct send got skipped; the retry covers every unknown one (a master mid-election, a frame lost while its socket reconnected). The master's own world is always the reference — `_broadcast_seed_if_master()` reads `run_seed` off the `"terrain"` group node rather than rolling a new one, and a **re-elected** master re-broadcasts the seed it already has and never re-rolls (yanking the world out from under everyone mid-run is worse than the drift). Only the master's `seed` is accepted (`from != _master` is dropped): the relay is opaque to the lobby, so without that check any member could race the broadcast and `_has_seed` would latch the wrong world. **JSON number gotcha:** `JSON.parse_string` makes every number a float, so the `int()` cast is mandatory, not cosmetic — `run_seed` round-trips exactly through a double (it is a `randi()`, 0…2³²−1), but passing the float through would make every downstream `hash(Vector3i(...))` see a different type.

**Hero split — THE LOBBY IS THE SOURCE OF TRUTH, and nothing is ever decided locally.** `server/room.go` already implements `hero` / `heroes` / `pool`; no server code was added. `_heroes` (hero name → holder id) and `_pool` are **replaced wholesale** by each broadcast and never edited locally, so two peers pressing the same button in the same frame cannot both end up in the same body — one is refused. `claim_hero(hero)` only *asks*; the local body moves in `_apply_my_hero()` when the confirming `heroes` broadcast lands, and it moves through **`set_active_character()`**, never by poking `current_character_index` (that setter frees the old model, instances the new one, clears Teibi's resize state and re-runs `_apply_view_mode()`). `_auto_claim_hero()` claims on join so nobody has to open the panel — preferring the body the player is already in, else the first free hero — **at most one claim per `heroes` frame and never in a loop**, because the lobby answers every claim with another broadcast and retrying in place would be a claim storm. **Release on leave is server-side**: the lobby frees a departing member's hero itself, so this client must never do it. The E-cycle is restricted by `my_character_indices()`, which returns `null` meaning "all of them" — offline, no room, or holding no hero — so `switch_to_next_character()` keeps its solo behaviour behind one `== null` test; with one hero held the set is a singleton, the press is a refusal, and it gets the **same dial flash + denial buzz a refused F press gets** so the player reads "this hero is locked" rather than "E is broken". **⚠️ LANDMINE — a hero rejection must NOT end the session.** The lobby answers a refused claim with a plain `error` frame on a socket it deliberately keeps **open** (`errUnknownHero` / `errHeroTaken`), and two peers reaching for the same hero at the same moment is an ordinary event; the blanket `leave()` every other lobby error takes would drop **both** of them out of a perfectly good room. `HERO_ERRORS` matches those two strings exactly (the string is all the frame carries) and downgrades them to a status line.

**Coin identity is derived from position, so none of the three spawners was edited.** `Coin.id_at(pos)` is `hash(Vector3i(roundi(pos.x * COIN_ID_QUANT), …))` with `COIN_ID_QUANT = 8.0` — a 12.5 cm cell. Every coin in the world comes from one of three deterministic, `run_seed`-derived spawners (road scatter, artifact reward ring, camp fire coins), so two peers sharing a seed put the same coin in the same place and the position alone identifies it; threading an explicit id out of three call sites would have been a much larger diff. **The id is LATCHED in `_ready()` (`coin.gd`'s `_id`), never recomputed from the live position, and that is a contract rather than an optimisation:** `_process` bobs the coin `BOB_AMOUNT` (0.12 m) around `base_y`, which is **±0.96 of a 12.5 cm cell**, so an id read at collection time names a different cell than the one read at spawn — the joiner would ask `is_coin_collected()` about one id while the collector published another, and the replay would miss on most pickups. `mp_selfcheck.gd` spawns a real coin, moves it by `BOB_AMOUNT` and fails if the id changes. `coin.gd` asks the `"mp"` group `is_coin_collected(coin_id())` in `_ready()` — **after** `base_y` is captured and the id is latched, and **before** `body_entered` is connected, so a coin freed there can never fire a pickup on its way out — and calls `report_coin_collected(id)` in `_on_body_entered` after `collect_coin`. Both are one failed group lookup per coin **at spawn**, never per frame, and `report_coin_collected` is a no-op offline so a solo run allocates nothing. **ponytail — two ceilings, both cosmetic by construction:** two *distinct* coins inside one 12.5 cm cell share an id (a joiner despawns one coin too many — never a wrong bank), and a coin exactly on a cell boundary can round the other way on a peer whose float arithmetic differs by an ulp (its id then does not match and the coin is simply not despawned — a duplicate, not a crash). Upgrade path for both: thread an explicit `(k, slot)` / `(chunk, index)` id out of the spawners.

**The join snapshot is the THIRD trust boundary, and every incumbent sends one.** On `peer_joined`, **every** member (not just the master) relays `{"mp": "state", cc, ls, dd, px, py, pz, gc, gs, ids, dead}` to the joiner — absolute values, never deltas, because a joiner has exactly one chance to hear this. It is every member because the collected-coin set is the **union** across the room and each peer only knows the ids it banked itself, while bank/lives/distance are a sum over per-peer contributions: a snapshot from the master alone would hand the joiner a world still full of coins the others took. `decode_state()` is static and `_rtc`-free (so the selfcheck can beat on it) and validates the payload **whole or not at all**, exactly like `decode_presence()`: every number checked for finiteness *before* any cast (`int(NAN)` is undefined and on wasm the float→int trunc can trap the module), counters bounded by `MAX_STATE_COUNTER`, the position bounded by `MAX_PRESENCE_COORD`, and each id bounded by `MAX_STATE_ID_MAGNITUDE` (2⁵³ — ids cross the relay as JSON doubles). The **one** place it keeps part of a payload is an over-long `ids` array, which is **truncated** to `MAX_STATE_IDS` (2048) rather than rejected: the sender orders ids most-recent-first, so the head is the part nearest the joiner, and the snapshot's position and counters are still worth having. A malformed *entry* still drops the whole snapshot. `MAX_STATE_IDS` caps both ends — `_recent_collected_ids()` truncates the send the same way. **ponytail:** a long enough run overflows the cap and the *oldest* ids drop, so an already-taken coin can reappear kilometres behind the group in chunks nobody is near; the upgrade path is filtering by distance to the join anchor rather than by age. **`_absorb_collected()` also sweeps the live world** — it `queue_free()`s any coin already in the `"coin"` group whose id it just learned, and `consume_silently()`s any chest in the `"chest"` group — which is what makes arrival order irrelevant: a snapshot landing after the terrain was built despawns those pickups now, and one spawned afterwards asks `is_coin_collected()` in its own `_ready()` / `setup()`.

**The snapshot carries a second bounded id list, `dead` — the room's crushed-crocodile kill list — and it is the crocodile half of the same "a joiner must not see a stale world" rule.** A joiner's terrain generates every crocodile the shared seed describes, including the ones giant Teibi already crushed, so without it the newcomer walks into a pack containing animals nobody else can see. Sender `_recent_dead_ids()` and receiver `_absorb_dead()` are `_recent_collected_ids()` / `_absorb_collected()` one thing over, sharing `MAX_STATE_IDS` and the one static `_decode_id_list()` validator so the two lists cannot drift apart at the trust boundary — and `dead` follows `gc`/`gs`'s **missing-is-not-malformed** rule (a peer on an older build is still worth its position, counters and coin ids) while present-but-bad still drops the payload whole. `_absorb_dead()` makes **one** walk of the `"crocodile"` group for the whole list, never `_apply_dead()` per id: that single-id path rebuilds the id cache on a miss, and a joiner's list is mostly ids naming crocodiles in chunks this peer has not built. **`dead` is taken from the MASTER ALONE, and that asymmetry with the `ids` beside it is the point.** The collected set is a **union** — each peer only knows the coins it banked itself, so every incumbent's ids are needed and every incumbent is entitled to assert them. A kill is the opposite: it is **arbitrated** (`_resolve_kill` on the master, broadcast as `dead`), so every member's `_dead_crocs` is already a copy of the master's one set and a non-master has nothing to add — while `_absorb_dead` deletes a crocodile **permanently** on this peer, which is exactly why `_receive_dead` accepts the live verb from the master only. Honouring a stranger's list here would have reopened that hole through the relay, which any room member can reach (`GET /rooms` makes every code public). The test lives in `_receive_state`, where the sender is known; the price is that a wedged or older-build master leaves the joiner without a kill list, the same degradation its missing coin ids already cause. **Both sweeps are the JOIN EVENT, not a replay** — the `_state_received` latch admits exactly one snapshot per sender for the room's life, so neither can run twice for the same peer. `ponytail:` the shared cap means a room that crushes more than `MAX_STATE_IDS` (2048) crocodiles drops the *oldest* kills, so a joiner can see one alive kilometres behind the group; cosmetic in the collected set's way (a crocodile too many, never a wrong bank), and the upgrade path is the same distance-to-anchor filter.

**PLACEMENT BELONGS TO THE ARRIVAL, NEVER TO MID-RUN PLAY — `_arriving()` is the gate, and a latch alone was not enough.** `_can_join_place()` is a pure *state* test ("we still owe a placement and both inputs are in hand") and `JOIN_SNAPSHOT_WAIT` never disarmed it — that deadline only stops the *waiting* (`_tick_join_wait` returns early once it is spent), it never says "too late". So whichever input landed last fired the teleport, however many seconds of play later, and **either input can be arbitrarily late**: a backgrounded browser tab stops polling its socket, `seed_req` retries for 20 s (`SEED_REQUEST_INTERVAL` × `SEED_REQUEST_MAX_TRIES`), and a master migration hands that whole budget back (`_on_lobby_master_changed`). Measured: a peer that arrived, waited out the deadline with a silent master and then walked 400 m was teleported to the world **origin** by the late `seed` (through `reset_position()`, which also wipes the run's coins, distance and streak) and then onto the group's ring by the late `state` — 397 m of drag, twice, while alive and playing. That is the owner-reported "players dragged toward each other". `JOIN_PLACE_WINDOW` (5 s from the `welcome` stamp `_join_msec`) now bounds **both** placement sites: `_can_join_place()` and `_receive_seed()`'s fallback. The healthy case is nowhere near that bound — every incumbent sends the seed and its snapshot from the *same* handler that observes our arrival (`_on_lobby_peer_joined`), so both land in one relay round trip. **Outside the window `_receive_seed` still adopts the seed but rebuilds around the PLAYER's chunk instead of (0,0) and does not teleport** — same shared world, no yank, still on solid ground the same frame (`new_run`'s `around` builds that chunk plus ring 1 synchronously). `ponytail:` a wall clock cannot tell "playing for 5 s" from "tab backgrounded for 5 s during the arrival"; the latter loses its placement and plays on where it stands, and — having never run `join_at()` — stays a non-contributor to the room's totals, exactly as a peer whose seed never arrived at all already did. That is the safe direction to be wrong in; the upgrade path is the player publishing a "has taken control" bit for this to read instead of a clock. `mp_e2e.sh`'s phase 3 (`--role=drag`) is the regression check, and it asserts the late seed was **adopted** as well as that nothing moved, or "the player did not move" would also be true of a packet that was simply dropped.

**Join placement — arrive beside the group, on ground that exists.** `_apply_join_placement()` runs **once per room** (`_join_applied`) and only inside the arrival window above, only when the peer was *not* alone in the `welcome` frame (`_first_member` — a host has nothing to join, so its spawn is phase-3's), and only when both halves are in hand: the seed **and** the snapshot positions. Either can land last, so both `_receive_seed()` and `_receive_state()` call in and the latch decides. **It waits for EVERY incumbent's snapshot** (`_expected_snapshots`, taken from the `welcome` member count — peers arriving *after* us never send us one, so counting them would always burn the deadline), because the anchor is only the documented centroid once the whole group is in it: placing on the first snapshot drops a joiner beside whichever peer's relay message won the race. `JOIN_SNAPSHOT_WAIT` (1.5 s) is the fallback — a wedged, older-build or vanished peer must not strand the joiner at the origin forever, and a worse anchor beats no placement. The deadline is ticked by `_tick_join_wait()` because nothing else would re-trigger the placement once the last snapshot fails to arrive. Snapshot arrivals are counted off `_state_received`, **not** `_peer_state`, which presence packets also fill. `_join_anchor()` is the centroid of the snapshot positions, unless somebody is further than `GROUP_SPREAD_MAX` (60 m — a bit over one chunk, well inside the fog) from it, in which case the **master's** position: the centroid of two players who went opposite ways is empty ground between them, and arriving beside one player beats arriving beside none. The terrain is rebuilt **around the anchor chunk**, and then the placement **waits one `physics_frame` before touching the player** — the whole relay chain runs on an *idle* frame, so at that instant the physics space still holds the freed old-run chunks and none of the new ones, and the ring probe below would judge every candidate against geometry that no longer exists. `player_controller.join_at(anchor)` takes the first spot the body fits on rings of `JOIN_RING_RADII` (3/5/8/12 m, `JOIN_RING_ANGLES` 8 candidates each, nearest ring first) probed with the same `_is_body_blocked_at()` Primm's Phase Step lands with, drops in from `JOIN_SPAWN_HEIGHT` (2 m) and sweeps crocodiles with `clear_nearby_crocodiles()` so a joiner is not bitten on its first frame. **`join_at` is NOT a restart:** it does exactly `reset_position()`'s teleport hygiene (velocity, facing, camera pivot, ability state, blink i-frames) and **none** of its score wipe, because the coins, distance and lives now belong to the room. It does zero **`own_coins` / `own_lives_spent` / `own_distance` / `run_distance`**, though: those are this peer's *solo* tally from a different world, and while an inflated bank is only cosmetic, a solo `own_lives_spent` is **subtracted from the room's shared hearts** — joining after two solo deaths would take two hearts off everybody — and `run_distance` is what this peer *publishes* as the room's distance, so a 3 km solo run carried into a room 100 m in would raise the shared distance to 3 km for everyone **permanently**, a max having no way back down. Zeroing them is also what makes a reconnect safe, since the incumbents froze the old contribution in `_gone_coins` / `_gone_spent`.

**Shared bank / lives / distance — a sum of per-peer contributions, with no authority and no round trips.** Each peer broadcasts its own absolute numbers and each peer adds them up, so every reader agrees within one presence interval. The player keeps `own_coins` and `own_lives_spent` **separate from the displayed `coins_collected` / `lives`**, and that separation is load-bearing: `_refresh_shared_totals()` overwrites the displayed fields with the room's totals every physics tick, so summing the displayed number would feed the room's bank back into itself and double it every frame. `shared_bank()` / `shared_lives_spent()` / `shared_distance()` each take the caller's own contribution and return **`null` offline — and `null` until `_join_settled()`**, so the player falls through to solo behaviour on one `== null` test; **the second half of that guard is what stops a joiner game-overing itself on a half-arrived snapshot set.** A joiner is `IN_ROOM` from the `welcome` frame while `_peer_state` fills one relayed snapshot at a time, and each snapshot carries one peer's coins **and** its spent lives — so a partial set is not a partial average, it can be all of the room's deaths and none of the bank that bought the extra hearts. Reading it mid-fill computes zero hearts in a healthy room, `_check_shared_game_over()` fires, and the Game Over screen is undone only when the placement runs — so a joiner still waiting on the seed sits on it for the whole 20 s `seed_req` budget, or forever if the seed never lands. `_join_settled()` is `_can_join_place()`'s condition minus the seed: the totals become readable once the **snapshots** are in or their deadline is spent, whether or not a world has arrived to place into. **Lives are the one shared total the master owns as real state, exactly as it owns the room's streak.** `_tick_room_lives()` (master only, once per frame from `_process`) advances `_room_lives` in solo's own **order**: deaths are charged as a **delta** against `_room_spent_seen`, then grants are walked with `collect_coin()`'s own `while` loop **including its `if lives < LIVES_CAP`, which BURNS a grant landing at the cap**. The count rides the master's presence packet as `rl` (absolute and idempotent, so unreliable is right; omitted by a non-master, and the decoder reads absent as **-1 "not published"**, never as 0 hearts), is accepted **from the master alone** — the `seed` / `cnf` / croc-sync authority rule — and is latched into `_room_lives_seen`, which is both what a non-master answers from *and* what a **promoted** master adopts as its starting count (a migration must not hand the room three fresh hearts; the two watermarks are re-seeded from the current totals so nothing is charged or paid twice). **Taking ownership with nothing published seeds from `shared_lives_from()`, never from MAX_LIVES** — two paths reach that and both already have deaths behind them (hosting from a live solo run in which the player has been bitten, since `_first_member` makes their own tally the room's opening balance; and a promotion where no `rl` ever arrived), so starting full and *then* marking those deaths already-charged handed the room free hearts. `player_controller._refresh_shared_totals()` reads it through `shared_lives(own_coins, own_lives_spent)`, the usual `null`-offline shape. The old static, pure `shared_lives_from(bank, spent, max_lives, per_extra, cap)` (base hearts + `bank / EXTRA_LIFE_COINS` − spent, clamped into `[0, LIVES_CAP]`) **remains as the fallback and is still pinned by the selfcheck**: `--lobby-only` has no presence at all, a master on an older build sends no `rl`, and the first packet from a fresh master is up to 66 ms away. **Why the stateful owner was worth building:** the formula is stateless, so it *banks* the overshoot solo burns — a room that banked fast pinned at 5 hearts and deaths stopped being visible until `spent` caught up, i.e. it became unlosable. No formula over `(bank, spent)` alone fixes that (solo's outcome depends on the *order* of grants and deaths), and the obvious alternative (`mini(max_lives + bank / per_extra, cap) - spent`) trades it for a worse one, where the room gets exactly `cap` lives for the whole run and coins banked after a death stop buying hearts back. **`ponytail:`** within one 15 Hz presence tick a death and a grant arrive together and their true order is not on the wire, so deaths are applied **before** grants — the forgiving side, and it differs from grants-first only at the cap; the upgrade path is a per-peer event sequence number rather than an absolute counter. Distance is a **max**, which is why it needs no frozen accumulator and why feeding it back into the player's own running max cannot inflate it — but that feedback is exactly why the **persisted personal records read `own_distance` / `own_coins`, never the displayed fields**: `_trigger_game_over()` writing `run_distance` would save the furthest *teammate's* distance (and the whole room's bank) into `user://best_run.cfg` as this player's best. `own_distance` exists for that one purpose and is wiped with the rest by `reset_position()`, which also owns the `own_lives_spent` wipe so the two can't drift. **A departed peer's share is FROZEN, not dropped** (`_gone_coins` / `_gone_spent`) — dropping it would shrink the room's bank in front of everyone and, much worse, **refund** the lives that peer spent. `_prune_dead_connections()` handles the *other* case and must **NOT** freeze: a peer whose WebRTC died while its lobby socket stayed up gets no `peer_left` **and has not left** — it is still playing and still counted live by every peer whose mesh link survived, and `_gone_*` rides the join snapshot as `gc`/`gs`, which a later joiner merges *alongside that same peer's own snapshot and presence*, counting its coins and its spent lives twice (hearts the room actually has, missing from the joiner's HUD). So it marks the entry **`stale`** instead: the counters stay attributed to the peer, and only `peer_positions()` and `nearest_member_position()` skip it — which is the bug the drop was written for, since a frozen coordinate nobody is standing on had the master's whole pack chasing, and the LOD manager holding awake, empty ground for the room's life. A real `peer_left` later freezes the correct final figure. The frozen figure rides the join snapshot too (`gc`/`gs`), merged with `maxi` and never `+=`, because every incumbent replays the same number and adding them would multiply it by the number of snapshots received.

**"Play Again" inside a room LEAVES the room, and that is a correctness rule rather than a policy choice.** `restart_game()`'s only caller is the Game Over screen, and in a room that screen can only be up because the room's shared hearts hit **zero** (a peer with hearts left soft-respawns in `_on_caught_finished()` instead). The hearts are a room-wide figure — base hearts + the room's bank / `EXTRA_LIFE_COINS` − the room's spent lives — so wiping *our* numbers cannot bring it back: the lives the other peers spent still count, `_refresh_shared_totals()` re-zeroes `lives` on the very next physics tick and `_check_shared_game_over()` puts the Game Over screen straight back up. Play Again was an infinite loop with no exit but leaving, so it leaves: `restart_game()` calls `leave()` (guarded on `shared_bank(own_coins) != null`, the standard "am I in a room" test) before the wipe. `leave()` is the manager's single complete unwind, so the collected-coin set, the dead-croc set, the frozen `_gone_*` totals and the room streak all go with it, and `room_seed()` then answers `null` so the world is **re-rolled** instead of replayed with every coin already taken. There is deliberately **no** "retired contribution" bookkeeping: this peer's share is always simply its live `own_coins` / `own_lives_spent`, which is what presence and the join snapshot report. **`ponytail:`** the room dissolves as each member presses the button; the upgrade path is a room-wide restart verb the master broadcasts (`{"t":"rst"}` beside `cnf`/`dead`) on which every peer clears `_collected_ids`, `_dead_crocs`, `_gone_*` and restarts in place. `coin_hud.gd` and `lives_hud.gd` were deliberately **not** edited: they already read those very fields, so they show the room's numbers in a room and this peer's own numbers solo, with no branch of their own. **`_on_caught_finished()` re-reads the room's totals before it spends a life**, and that call is not redundant: `_physics_process` early-returns for the whole `is_caught` freeze (`CAUGHT_DURATION`, 0.55 s), so `lives` is up to half a second stale by the time the bite resolves — long enough for a teammate's pickup to have crossed an `EXTRA_LIFE_COINS` threshold — and branching on the stale value ends a player's run on a heart the room still has.

**Three trust boundaries, all in `mp_manager.gd`.** The lobby never inspects `payload` (that opacity is what keeps game logic off the server), so *everything* relayed is unvalidated peer input: `_on_lobby_relay` type-checks every field and drops anything malformed with a warning, and a payload with no `"mp"` key — or an `"mp"` verb from a later phase — is ignored **without** a warning, which is what makes this client forward compatible. (`seed_req` is the one verb with nothing to validate: the verb *is* the whole message.) The second is `decode_state()` above. The sharpest is the presence decoder: **`bytes_to_var`, never `bytes_to_var_with_objects`** — the "with objects" form instantiates arbitrary classes named in the byte stream, i.e. hands any peer in the room code execution in our process, and there is no situation in this game where a peer needs to send an object. Past that, `MpManager.decode_presence()` (static and `_rtc`-free precisely so the selfcheck can beat on it) rejects non-finite positions (a NaN would poison the avatar's smoothing forever) plus finite-but-absurd magnitudes (`MAX_PRESENCE_COORD` / `MAX_PRESENCE_SPEED` — `s` is the one that latches, since `RemoteAvatar._animate` accumulates it into `stride_phase`, so a single `1e30` makes every limb rotation NaN for the rest of the room), wraps `y` into `[0, TAU)` rather than dropping it (`lerp_angle` is `from + short_way * weight`, and `1e30 + anything small IS 1e30`), and range-checks `c` before it can index `CHARACTERS`. A packet is trusted whole or dropped whole — no partial trust. Range-checking `c` makes it safe to *index*, not safe to *obey* 15 times a second, so `RemoteAvatar.set_character()` also rate-limits the swap (`SWAP_COOLDOWN_MS` 500): a peer alternating two valid indices every packet would otherwise force a `queue_free` + `instantiate` + full `_style_model_meshes` walk per packet per peer. Dropping the swap is lossless because presence repeats `c` every packet — a genuine switch lands on the first packet past the window.

**Presence packet:** `var_to_bytes({"p": Vector3, "y": float, "c": int, "s": float, "g": bool, "cc": int, "lv": int, "dd": int})` — position, yaw, character index, horizontal speed, on-floor, plus this peer's own coins, own lives spent and own distance — broadcast **unreliable** at `PRESENCE_HZ` (15). The three counters are **absolute, never deltas**, which is what makes an unreliable channel self-healing: a dropped packet is corrected 66 ms later instead of leaving the room's totals permanently short. In `decode_presence` they are validated exactly like `c` with one deliberate difference — **missing is not malformed**: a phase-3 peer sends a packet without them, and dropping those whole would make an older peer *invisible* rather than merely un-counted, so absent reads as 0 and only a value that is present and bad drops the packet. Presence is sent to `_rtc.get_peers()`' **connected** entries, not to `_connections` (which holds every peer negotiation has *started* with, so broadcasting off it means send errors at 15 Hz through the whole negotiation). ~70 bytes × 15 Hz × 3 peers ≈ 3 KB/s out, smaller than the UDP headers carrying it; a dropped sample is replaced 66 ms later, so re-transmitting stale positions would be strictly worse. `RemoteAvatar` smooths toward the newest sample at `INTERP_RATE` and teleports past `TELEPORT_DISTANCE` (10 m) — a respawn, a restart or Primm's Phase Step moves further than one tick ever could, and without the teleport the avatar would take a long serene glide to catch up. **ponytail:** plain exponential smoothing, not a timestamped interpolation buffer; upgrade to a buffered ~100 ms delay interpolator if it visibly rubber-bands on a real connection. The avatar's walk-cycle constants are *copied* from `player_controller.animate_walking()` on purpose — three floats duplicated is cheaper than coupling a network avatar to the script that owns input, physics, abilities and lives.

**MASTER-SIMULATED CROCODILES — the crocodile's LIFETIME does not change at all, and that is the headline design decision of phase 5.** Crocs stay chunk-parented, per-peer, deterministic and freed on chunk unload, exactly as phase 1 built them. The sync layer **overlays dynamic state onto locally-existing nodes matched by a deterministic id**; it never creates, re-parents or frees a crocodile (the one exception is the explicit kill broadcast below). That is what let the whole feature land with **not one character of `scripts/endless_terrain.gd` edited**. The two directions of the chunk-parenting landmine, and why neither can produce a duplicate or a vanished croc: (1) *"a peer may not have generated the chunk a synced croc lives in"* — it cannot happen for a croc that matters, because a croc is only ever broadcast while **awake**, i.e. within `SIM_RADIUS` (45 m) of some peer, and every peer's own terrain builds `render_distance` chunks around itself (3 × 50 m = **150 m** on web, 250 m on desktop); 45 ≪ 150, so any croc near a peer is already loaded on that peer, and a sample naming a croc this peer does not have is **dropped silently** — the expected case, not an error, and warning on it would be one line per croc at 10 Hz. (2) *"the master may unload a chunk another peer still stands in"* — it could, and that was the real **coverage ceiling**: the master only simulates crocs *its own* terrain has loaded, so a peer more than ~150 m from the master got no samples for its neighbours and those crocs **fell back to local simulation** after `CROC_SYNC_TIMEOUT` (2 s). **That is now closed from the terrain side** (`endless_terrain.set_focus_points()` — see "Terrain focus points" above): `crocodile_lod_manager.gd` hands the terrain the same peer-position array it already builds, and a 3×3 chunk block stays loaded around each teammate, covering the 45 m `SIM_RADIUS` inside which a crocodile is awake at all. Focus points affect **only which chunks stay loaded**, never what one contains, so the determinism contract is untouched. **`ponytail:`** the residual ceiling is the **cap** — at most three teammates and 27 extra chunks (`MAX_FOCUS_POINTS` / `MAX_FOCUS_CHUNKS`), because the union of peer areas multiplies the active chunk count and web memory is what the whole perf design protects; past it, behaviour degrades to exactly what it was. Nothing duplicates, nothing vanishes either way. The same overlay-only design delivers **hot standby for free**: a non-master's synced crocs *are* real local nodes holding the master's last transform, so promotion is one loop of `clear_remote_drive()` and every croc carries on from where it stood — and a ~1 s election gap is well inside the 2 s timeout, so crocs never visibly stall through a handover.

**Crocodile identity is derived from the node name, exactly as coin identity is derived from position.** Every crocodile the terrain spawns is named deterministically *before* `add_child` from a pure function of chunk coords and `run_seed` — `Crocodile_<cx>_<cy>_<index>`, `PatrolCrocodile_<cx>_<cy>_<count>`, `BossCrocodile_<i>` — so two peers sharing a seed put the same croc, with the same name, in the same place. `static func croc_id_for(node_name: String) -> int` is `node_name.hash()` **sign-extended to int32**, **latched in `_ready()`** into `_croc_id` and exposed as `croc_id()` (latched for the same contract reason `coin.gd` latches its id, even though a croc's name never changes). **`ponytail:` two ceilings.** (1) A croc spawned outside the terrain (the standalone `piglet_crocodile.tscn`, a future spawner) has a non-unique name and would collide — it never happens in a room, and the failure mode is one croc following another's transform, not a crash. (2) `String.hash()` is 32-bit, so a collision across the ~1000 loaded crocs is a ~1e-4 birthday chance per run; the upgrade path is the coin id's — thread an explicit `(chunk, index)` id out of the spawners. **The sign extension is not tidiness.** `String.hash()` is *unsigned* 32-bit widened into a GDScript int, but the sync packet carries ids in a `PackedInt32Array`, so every id above `INT32_MAX` wrapped negative in transit, missed the receiver's `_synced_crocs` lookup and was dropped on the deliberately-silent "not my chunk" path — measured over the real name scheme, **43% of crocs hash above `INT32_MAX`**, so nearly half the pack was never synced at all and fell back to local simulation after `CROC_SYNC_TIMEOUT`. Sign-extending here rather than widening the packet keeps sender, receiver, `_dead_crocs` and `_synced_crocs` naming a croc by one number at zero bandwidth; `mp_selfcheck.gd` sweeps the real name scheme through a `PackedInt32Array` round trip, because the stability and distinctness checks alone passed throughout.

**The crocodile side of the sync lives in `piglet_crocodile_ai.gd` and is four small pieces.** `set_remote_state(pos, yaw, flags)` stores the sample, decodes the flag byte into `is_chasing` / `is_fleeing` / `is_paused` / `is_biting`, and **snaps** rather than interpolates on the first sample or past `CROC_TELEPORT_DISTANCE` (8 m) — it is the only place `remote_driven` is turned on. It also forces `set_physics_process(true)`: the LOD manager sleeps anything past 50 m while the master syncs anything within `CROC_SYNC_RADIUS` (55) of a peer, so a synced croc in that 50–55 m band arrives with its physics callback already **off** — `_tick_remote` would never run, and the body would jump 8 m at a time, never animate, and never reach `move_and_slide`/`_handle_collisions`, i.e. be neither solid nor able to bite, which breaks the "bitten peer detects its own bite locally" rule the whole phase is specified against. `clear_remote_drive()` hands the body back to its own AI from wherever it currently stands (the sync timeout, and promotion to master) and hands the physics switch back with it (`set_physics_process(lod_active)`) — leaving it on for a croc the manager believes is asleep would silently un-sleep it forever, since `set_lod_active()` no-ops when the state already matches. `_tick_remote(delta)` runs from a branch at the **very top** of `_physics_process`, above the `lod_active` backstop: it eases `rotation.y` with `lerp_angle`, drives `velocity` toward the sample at `CROC_REMOTE_INTERP_RATE` (10/s — **the SAMPLE rate, never the frame delta**: dividing the gap by `delta` asks for a velocity that lands exactly on the sample *this* frame, so the body arrives in one frame and sits at velocity ~0 for the other five, and since `_animate_body` derives its stride from `velocity` those five take the `move_factor < 0.05` branch — a croc visibly flipping between sprinting and idle breathing ten times a second on every peer that is not the master), clamped to `CROC_REMOTE_MAX_SPEED` (40) so a bad sample cannot launch the body, then calls **`move_and_slide()`** — deliberately, not incidentally, because that is what keeps a synced croc *solid* to the player and what makes the **bitten peer detect its own bite locally**, which is the bite rule the whole phase is specified against — followed by `_handle_collisions()` and `_animate_body(delta)`. And `_ready()` asks the `"mp"` group `is_croc_dead(croc_id())` and frees itself if so — the same shape, in the same place, as `coin.gd`'s `is_coin_collected` check, one failed group lookup per croc at spawn and a no-op offline. `flee_from()` and `set_lod_active()` are **unchanged**: a remote-driven croc's flee state arrives in the flag byte and a local `flee_from` call on one is harmless, so don't "fix" it.

**The croc-sync packet, and the fourth trust boundary.** Wire format is `var_to_bytes({"t": "croc", "i": PackedInt32Array (one id per entry), "x": PackedFloat32Array (4 per entry: px, py, pz, yaw), "f": PackedByteArray (one state byte per entry)})`, sent by the master only, over the mesh, **unreliable** at `CROC_SYNC_HZ` (10) — a dropped sample is replaced 100 ms later and re-sending a stale transform would be strictly worse, the same argument presence makes. The state byte is `CROC_FLAG_CHASING/FLEEING/PAUSED/BITING` (1/2/4/8), declared **once** in `mp_manager.gd` so the encoder (`_croc_flags`) and the decoder (`set_remote_state`) cannot drift. `_send_croc_sync()` makes **one pass over the `"crocodile"` group filling N per-peer buffers** — never one pass per peer; the group holds ~1000 nodes at 10 Hz, so loop order is the whole cost model — appending each awake, non-`remote_driven` croc to the buffer of every connected peer within `CROC_SYNC_RADIUS` (55 m) of that peer's last known position. **55 must stay above the LOD manager's sleep radius** (`SIM_RADIUS + HYSTERESIS_MARGIN` = 50), or a croc could be awake-for-a-peer yet outside its sync window. Per-peer filtering is what makes it affordable: ~25 crocs × 21 bytes × 10 Hz ≈ **5 KB/s per peer**, against ~100 KB/s for an unfiltered broadcast of the room-wide awake set. Sleeping crocs cost **zero** network — their pose is the deterministic spawn state every peer already computes identically. The receive side is the **fourth trust boundary**, built like the other three: `static func decode_croc_sync(state) -> Dictionary`, `_rtc`-free so the selfcheck can beat on it, validating **whole or nothing** — every field present and of exactly the right packed type, `i.size() == f.size()`, `x.size() == i.size() * 4`, `i.size() <= MAX_CROC_SYNC` (192, there to reject hostile garbage rather than to police the pack), and every float finite **before any cast** and within `MAX_PRESENCE_COORD`; yaw is wrapped with `fposmod(yaw, TAU)` rather than dropped, for the same reason presence wraps `y`. A packet is **dropped unless it came from the master** (and dropped outright if *we* are the master), for exactly the reason only the master's `seed` is accepted. Lookup is a `_synced_crocs` id → node cache filled lazily — at most **one** group scan per packet, never one per entry — purged of freed instances on each sync tick.

**The `"t"` discriminator is what makes all of this backward compatible.** `_receive_mesh_packets()` does `bytes_to_var` **once** (never `bytes_to_var_with_objects` — the sharpest rule in the file) and then branches: no `"t"` key → the phase-3/4 presence path, `"t"` present → `_receive_mesh_verb()`'s `match` over `croc` / `clm` / `cnf` / `flee` / `kill` / `dead`. An unknown verb returns **silently, without a warning** — the same forward-compatibility rule `_on_lobby_relay` states — so a phase-5 packet reaching an older peer falls through its presence validation and is dropped, and a later build's packet kinds never spam this one. `static func decode_presence(bytes)` is kept **exactly as it was** (the selfcheck pins its signature); its body was factored into `_decode_presence_dict(state)` so both paths share one validator rather than growing a second. The discriminator itself lives in `static func packet_kind(packet)` (`""` = presence, else the verb) rather than inline, because that is the only form the selfcheck can pin: driving `_receive_mesh_verb()` directly asserts nothing at all, since that function has no presence branch to leak through and passes however the dispatch is written.

**The three state-mutating verbs are rate-limited per peer, and bounding their fields was not enough.** `VERB_BUDGET_PER_SEC` (`clm` 30, `kill` 10, `flee` 4, `croc` 40, `cnf` 150, `dead` 60) is checked in `_receive_mesh_verb` before the `match` — **including the master-only verbs, because a master-only authority check is not a rate bound**: "master" is only the oldest member, anyone may host a room, and every room is listed publicly over `/rooms`, so a hostile master is an ordinary peer with a title. Unmetered, its `dead` wrote an unbounded `_dead_crocs` entry and rescanned the ~1000-node group per packet, its `cnf` wrote an unbounded `_collected_ids` entry and swept the whole `"coin"` group per packet, and its `croc` carried up to `MAX_CROC_SYNC` entries per packet — all at the bounded drain's ~1440 packets/s. The bounded drain already passes up to `MAX_PRESENCE_PACKETS_PER_PEER × peers` (24) packets per **frame**, and these three are expensive out of all proportion to their 20-odd bytes: `flee` walks the whole `"crocodile"` group (~1000 nodes) per packet — ~1.4 M `flee_from` calls/s at the drain rate, a hard frame stall on `gl_compatibility`, and `MAX_FLEE_DURATION` does nothing about it because re-sending every frame keeps the pack harmless just as well as one long duration; `kill` writes an unbounded `_dead_crocs` entry and provokes a full group rescan on the master *and*, via the `dead` broadcast, on every peer; `clm` writes an unbounded `_collected_ids` entry (the set replayed to every future joiner), broadcasts a reliable confirm, and makes every peer sweep the whole `"coin"` group. Room codes are public over `/rooms`, so "a peer in the room" means *anyone* — the same premise the bounded drain is written against. The budgets sit far above honest play (Phoboman's ability cools down for seconds, a crush needs a body under your feet and `piglet_crocodile_ai` stamps `_kill_requested_msec` so the round trip is asked for once per `KILL_RETRY_MSEC` (1 s) — **it expires rather than latching forever, because nothing acknowledges the request**: `request_croc_kill()` reports only that the packet left, and this very budget drops the excess *silently*, so a permanent latch left a giant Teibi's eleventh victim in a dense pack unable to be crushed **and** unable to bite (the early return sits above the bite path), i.e. an immortal harmless obstacle for the rest of the run, a running player crosses a coin every few hundred ms). **`ponytail:`** a whole-second window rather than a token bucket, so a peer can spend its budget in one frame and wait; a dropped claim is re-driven by `_tick_claims` 0.5 s later.

**Promotion adopts this peer's own pending claims.** `_on_lobby_master_changed`'s `_master == _you` branch resolves every entry in `_pending_claims` through `_resolve_claim` before anything else. A claim waiting on the *old* master's confirm can never get one — `_send_reliable_to_master` refuses to send to ourselves, so `_tick_claims` would count `tries` up and then resolve the pickup **locally**, banking it with the local multiplier and recording the id in nobody's set but ours. The coin would still be standing on every other screen, and the next peer to walk over it would claim it to us, be refused by `_collected_ids` *silently and with no confirm*, time out, and bank it a second time.

**Pickup claims: claim → confirm → broadcast, first claim wins, and the master owns the room's streak.** Through phase 4 two peers walking over one deterministic coin each banked it into the shared bank — the room paid twice, and a treasure chest (~12 pickups) paid twice for twelve. The protocol is over the mesh and **reliable** (a lost claim pays nothing, a lost confirm pays twice — neither is droppable): `claim  peer → master  {"t":"clm","id","n","v"}` and `confirm  master → everyone  {"t":"cnf","id","by","a","m"}`, where `n` is how many *pickups* (1 for a coin, the whole burst for a chest), `v` the base value each (1 or `Coin.GEM_VALUE`), `by` the winner's `peer_int_id`, `a` the total awarded **after** the room's multiplier and `m` the multiplier afterwards for the HUD. **The pre-multiplier base total that meta-progression takes is NOT on the wire, and that is a security decision rather than a saving.** A confirm names its own winner, so a hostile master can address one to any member — `a` has always been forgeable that way and inflates a *run-scoped* bank, but lifetime coins are monotone and **persisted**, so a forgeable base value would outlive the room. Every peer derives it locally instead: the master from the claim it is resolving, and a non-master from its **own `_pending_claims` entry**, which still holds `n`/`v` when the confirm lands (`_apply_confirm` erases it further down). No matching claim means 0, which is correct in all three cases it happens — the confirm is for somebody else, it is a duplicate whose entry we already consumed, or `_tick_claims` gave up and `_resolve_claim_locally` already paid the progression through `collect_coin`. It is a **separate figure rather than "divide `a` by `m`"** because the award loop steps the multiplier *per pickup*, so a chest crossing a streak threshold mid-burst has no single multiplier that divides `a` back into a base. **The set that arbitrates is `_collected_ids` — the very set phase 4 already keeps and already replays to joiners**, not a second one; a claim for an id already in it is refused with no confirm at all, because the loser has nothing to do with one. The master advances **one room streak** (`room_multiplier_from(streak, per_step, max_bonus)`, a pure static pinned by the selfcheck against `player_controller`'s own `STREAK_COINS_PER_STEP` / `STREAK_MAX_BONUS`, with the window read from `STREAK_WINDOW` — referenced, never re-typed) and prices the whole claim itself, which is why `player_controller.bank_awarded(amount, base_total)` exists next to `collect_coin()`: **the multiplier is already in `amount`** and applying it again would pay the square of it, while `base_total` is the untouched figure meta-progression takes. `get_streak_multiplier()` defers to `room_multiplier()` when it is not null, so `coin_hud.gd` shows the room's `(xN)` with **no HUD change** — the same trick phase 4 used for the bank and the hearts. Confirm handling on every peer records the id, **reuses `_absorb_collected([id])`** to sweep the live world (so arrival order is irrelevant, exactly as at join), drops any pending claim and — only when `by` is us — calls `bank_awarded(a, base_total)`, the base total having been read off that pending claim first. **`_resolve_claim` must NOT record the id itself, and the master is the only peer that could notice:** `_absorb_collected` skips ids already in the set and returns early when nothing was fresh, so an up-front write turned the master's own sweep into a no-op, and `coin.gd` deliberately does not `queue_free()` on the claimed path — every coin the *host* took stayed in the tree, invisible and still in the `"coin"` group, until its chunk unloaded. The refusal guard (`_collected_ids.has(id)`) is unaffected, because `_broadcast_reliable` cannot re-enter. `_resolve_kill` / `_apply_dead` already had the right shape. `coin.gd` on a taken claim hides the coin (`visible = false` + a **deferred** `monitoring = false`) and plays the pop and blip so the pickup still *feels* instant, but does **not** `collect_coin` and does **not** `queue_free` — the confirm's sweep owns both — and `report_coin_collected` is left **only** on the offline path so `_resolve_claim` is the single writer of the collected set. `treasure_chest.gd` uses the **same** machinery: `Coin.id_at(global_position)` latched in `setup()`, the same `is_coin_collected` check at spawn, and one claim for the **whole burst**, after which the burst runs purely as animation with no `collect_coin` calls at all. **`ponytail:`** an unconfirmed claim is retried every `CLAIM_RETRY_SEC` (0.5) up to `CLAIM_MAX_TRIES` (4) and then **resolved locally** — banked with the local multiplier and the id recorded — rather than eaten; the ceiling is a rare double-count when the confirm was merely 2 s slow, which beats a coin that visibly vanished and paid nothing, and the upgrade path is the master ACKing the claim itself. **A chest another peer emptied IS swept, by the same `_absorb_collected` pass, and the fix is a second group rather than a second id list.** A chest's id *is* a coin id (`treasure_chest.setup()` latches `Coin.id_at(global_position)`), so it already rode both the snapshot's `ids` and every `cnf` confirm — the only thing missing was that the sweep walked the `"coin"` group and a chest is not in it. Chests now join `"chest"` and `_absorb_collected` walks it too, calling `treasure_chest.consume_silently()`; that fixes the live case as well as the join one (a teammate emptying a chest spends our copy the moment the confirm lands). **A chest is deliberately NOT in the `"coin"` group** — the LOD manager gates that group's `set_process` on distance and a chest's `_process` *is* its payout burst, so a chest opened 31 m from the local player would freeze mid-shower and never free itself — and `consume_silently()` **leaves a chest mid-burst alone** (`_opened`), because that burst is paying out an award the master already priced.

**`peer_markers()` exists BESIDE `peer_positions()`, and the duplication is load-bearing.** The HUD surfaces that draw teammates (the minimap dots and the locator bar) need three things `peer_positions()` cannot give: it is deliberately **master-only** (waking crocodiles for the whole room is a cost only the master gets anything back for — see its comment), so a locator on a non-master would show nothing at all; it hands out **bare positions with no ids**, so nothing could be coloured stably; and it is written to allocate nothing because a crocodile asks per physics frame. `peer_markers()` answers for **every** member of the room as `{"id", "pos", "color"}`, **`null` offline** (the project's standard one-`== null`-test shape), and **it allocates** — which is why it is documented for HUD tick rates, the two callers ask at 5 Hz, and `nearest_member_position()` still exists for the per-frame crocodile query. Both skip `stale` peers for the reason their siblings do: a marker on a frozen coordinate points at empty ground. The colour is `static func peer_color(id)` — a pure function of the lobby id, so two surfaces agree on a teammate's colour with **no shared state and no lookup table to keep in step**, and the colour survives a master migration, a rejoin and a hero swap because none of those change the id. A hash collision means two teammates share a hue, i.e. a legibility annoyance rather than a correctness bug, so unlike `croc_id_for()` it needs no sign extension.

**A crocodile's quarry is the nearest ROOM MEMBER, not the nearest node in group `"player"`.** The master simulates every awake croc for everybody, and by the isolation contract a remote peer is a `RemoteAvatar` in **no group** — so `_update_chase_state()`'s `get_nodes_in_group("player")` lookup only ever finds whoever happens to be master, and phase 5 would have left the other one-to-three peers walking through the pack untouched **on every screen** (a regression from phase 4, where each peer's own local crocs chased that peer). `piglet_crocodile_ai.gd` therefore caches the `"mp"` group node in `_find_player()` and asks `MpManager.nearest_member_position(from)` — the nearest *other* member's last known position, or **`null` offline**, the same one-`== null`-test shape `peer_positions()` and `shared_bank()` use, and returning the nearest one rather than an array so the per-frame test allocates nothing. The winner is stored in `chase_target`, which `_chase_player()` reads; solo that is exactly `player_node.global_position`, so single-player is byte-for-byte unchanged. **The two candidates are judged INDEPENDENTLY**, which is what "nearest *smellable* quarry" means: the local player enters the running only while `is_on_floor()` (its distance is otherwise `INF`), and **`nearest_member_position()` applies the same rule to remote members by honouring the on-floor bit (`g`) presence has always carried** — `_peer_state` keeps it as `floor`, and an airborne peer is simply not offered, so the "jumping breaks the scent" hatch works for teammates too. Letting the nearest candidate's groundedness stand for both — the shape the naive version takes — means one airborne peer vetoes the scent of a grounded teammate standing beside it, and on the master, which simulates the pack for everybody, that is one player bunny-hopping to call every croc in range off their friend. The **bite still needs no protocol**: the croc is remote-driven on the quarry's own machine, where `_tick_remote()` runs `move_and_slide()` + `_handle_collisions()` against a real local body. **A peer whose pose is unknown counts as GROUNDED**: the join snapshot carries no `g`, and defaulting the other way would leave every incumbent unsmellable for the 66 ms until its first presence packet — a stealth window rather than a conservative default. `peer_positions()` deliberately does **not** take the same test: that one is the LOD manager's awake set, and the crocodiles a teammate is jumping over must stay simulated for them to land among.

**Bites needed no protocol at all — phase 4's shared-lives sum already was one.** The bite is decided by the bitten peer's own local collision (`piglet_crocodile_ai._handle_collisions()` runs on that peer's machine and calls `player.hit_by_crocodile()`), `own_lives_spent += 1`, and the next presence packet 66 ms later carries that **absolute** number to everyone, where `shared_lives_from()` debits the pool. **Do not add a bite message.** The only piece that was missing is that the run did not end for the peers who were *not* bitten: `player_controller._check_shared_game_over()`, called from `_physics_process` immediately after `_refresh_shared_totals()`, fires `_trigger_game_over()` when the room's hearts are 0 and we are neither already `is_game_over` nor mid-`is_caught`. It is guarded on `shared_lives_spent(...) != null` so it can **only** fire in a room — solo, `lives` reaches 0 only inside `_on_caught_finished()`, which already ends the run there, and firing here too would play the sting twice.

**Abilities that touch crocodiles go through the master; the ones that don't are untouched.** Phoboman's Stink Wave keeps its existing local loop **exactly as it was** (correct for every croc this peer still simulates, harmless on remote-driven ones) and adds one call to `request_croc_flee(origin, duration, radius = 0.0) -> bool` — a no-op returning false offline; in a room the local group loop runs on **every** caller, master or not (correct for the crocs this peer still drives, harmless on remote-driven ones, and on the master it *is* the authoritative application), and a non-master additionally relays `{"t":"flee","x","y","z","d","r"}` (every field validated finite and bounded, like all peer input). The `r` radius is what lets `clear_nearby_crocodiles()` reuse this as a **bounded** sweep: an unbounded flee disarmed every awake crocodile in the room, on every screen, once per death by any peer. **No flee broadcast is needed**: `is_fleeing` is a bit in the next sync packet, so the master's copy of the flight reaches every screen for free. Giant Teibi's crush is the one place a croc is *destroyed*, so it asks first: `request_croc_kill(id)` returns false offline (and whenever the request could not leave), letting the existing squash run **byte-for-byte unchanged**; in a room it returns true and the caller must **not** squash — the master records the id in `_dead_crocs`, broadcasts `{"t":"dead","id"}` reliably, and every peer runs the **ordinary** `squash_and_die()` visual so a crush still *reads* as a crush everywhere. `is_croc_dead(id)` is what `piglet_crocodile_ai._ready()` asks, so a chunk reload does not walk a dead croc back in. Windman and Primm are self-only and were not touched. **The dead set IS replayed in the join snapshot** (`_recent_dead_ids()` → the snapshot's `dead` array → `_absorb_dead()`), so a peer joining after a crush does not see the crocodile alive again — see the join-snapshot paragraph above for the bound and its ceiling.

**The heartbeat rides the LOBBY RELAY, not the mesh, and that is a deliberate deviation with three reasons.** (1) The thing being detected is a **throttled tab**, and a throttled tab stops polling the socket and the mesh alike, so either transport detects it equally. (2) `--lobby-only` has no mesh, so a mesh heartbeat would make the entire migration path untestable headless — and `scripts/mp_e2e.sh` is where this phase's automated evidence lives. (3) It is 1 Hz to at most 3 peers, i.e. nothing, on a socket that already carries a 20 s ping. The master broadcasts `{"mp": "hb"}` through `send_signal_to("")` every `HEARTBEAT_INTERVAL` (1 s), gated on `@export var heartbeat_enabled` — a **test affordance** for simulating a throttled tab, exposed nowhere in the UI. Peers accept `hb` **only from the master** (the `seed` rule) and stamp `_last_hb_msec`; the verb *is* the whole message, so there is nothing to validate. `_tick_stall_watch()` runs **before** the `_rtc` guard in `_process`, for the same reason `_tick_seed_request` does — it must work with no mesh — and past `HEARTBEAT_TIMEOUT` (4 s) it calls `LobbyClient.send_stalled(_master)` at most once per `STALL_REPORT_INTERVAL` (2 s), emitting the status line "Host not responding — voting to migrate…" once so a stalled host is visible in the panel with **no UI change**, exactly as the seed retry is. **A vote is not a request**: `server/room.go`'s `ReportStalled` drops it unless the subject really is the master, and answers with a `master` broadcast **only** once strictly more than half the non-master members agree — nothing at all otherwise — so the client keeps voting on its own timer instead of waiting for a reply, and one peer whose own connection is the broken one cannot depose a healthy host. **`_last_hb_msec` is stamped fresh in `_on_lobby_joined` AND `_on_lobby_master_changed`**: without that a joiner votes to depose a perfectly healthy master four seconds after arriving, and a fresh master is deposed by the clock that was running against the old one. On becoming master, `_on_lobby_master_changed` additionally runs the promotion — `clear_remote_drive()` on every synced croc, `_synced_crocs` / `_croc_seen` emptied — and starts heartbeating; the seed re-broadcast behaviour is unchanged. **No server code was added in this phase**; the lobby has implemented `stalled` since phase 2.

**Lobby URL precedence** (`LobbyClient.resolve_lobby_url`), most specific first: `--lobby=<url>` in the user command line (after a bare `--`) → `?lobby=<url>` in `location.search` (web only, behind the usual `OS.has_feature("web")` gate) → the `@export var lobby_url` on the manager → `DEFAULT_LOBBY_URL` (the deployed `wss://ck.wandergeek.org`). `/ice` failing is not fatal either — `FALLBACK_ICE` degrades to STUN-only rather than failing the join, and the request carries `ICE_TIMEOUT_SEC` (5) because `HTTPRequest`'s default timeout is *wait forever* and this one request is the only path to `_setup_mesh()`: a lobby whose `/ws` upgrades but whose `/ice` blackholes would otherwise leave the mesh unbuilt for the session while the UI reported a room, and the stuck request makes every later `fetch_ice` return `ERR_BUSY` (i.e. no TURN again for that session). The mesh's ICE config is fixed for the room's life — `_on_ice_ready` returns before assigning `_ice` when `_rtc` already exists, so a stale reply landing after a FALLBACK_ICE mesh was built can't leave early peers STUN-only and later peers on TURN.

**Desktop needs the `webrtc-native` addon; the web build needs nothing.** Browsers ship WebRTC; desktop Godot 4.5 has the *classes* but no implementation, so `MpManager.webrtc_available()` probes for `res://addons/webrtc/webrtc.gdextension` and the UI says so instead of failing mysteriously. `addons/` is gitignored — the addon is fetched, never vendored. See README's "Multiplayer (dev setup)" for the download plus the two local-lobby recipes (`cd server && go run .`, then either two desktop instances with `--lobby=ws://localhost:8080` or two browser tabs with `?lobby=ws://localhost:8080`). **`--lobby-only` is the escape hatch for having neither:** set once in `_init()` from the user command line (the same precedence shape as `--lobby=`), it skips the `webrtc_available()` refusal in `join()` and returns from `_on_lobby_joined` before the `/ice` fetch, so the room, the seed, the snapshot and the hero pool all work over the relay with no mesh at all. **ponytail:** a **test/dev** mode — used by `mp_e2e.sh` and by a desktop developer with no addon — not a shipped degraded mode. Its ceiling is that with no mesh there is no presence and no avatars: you share the room's world, but nobody moves. Nothing in the UI exposes it and the web build never sets it.

**One terrain entry point, with one parameter added in phase 4:** `endless_terrain.new_run(forced_seed = null, around: Vector2i = Vector2i.ZERO)`. `set_run_seed(value)` is **the only place `run_seed` is written**, because the biome domain offset is derived from it and an assignment that skipped `_roll_biome_offset()` would leave the ground shader drawing the old run's rivers while `is_river_at()` reports the new run's; both `_roll_run_seed()` (the ordinary random path) and `new_run()` converge on it. `forced_seed` is deliberately **untyped with a `null` default** rather than an int sentinel — 0 is a legitimate seed, so no int could mean "none given". `around` is the chunk the rebuild centres on: `new_run`'s step 4 builds that chunk **plus `SYNC_RING` ring 1 synchronously** and queues the rest for progressive fill, which is the load-bearing guarantee that a player teleported there the same frame lands on solid ground instead of falling through a hole. A mid-run joiner passes `world_to_chunk(anchor)` so that guarantee applies kilometres from the origin; both existing call sites (`restart_game()` and `_receive_seed()`) omit it and stay byte-identical to before the parameter existed. Note that `_receive_seed`'s "rebuild at (0,0) + `reset_position()`" is now only the **host / no-snapshot-yet** path — when a snapshot is already in hand it hands straight over to `_apply_join_placement()`, or the joiner would be yanked to the origin first.

**Deliberately not built, and still not:** **no croc creation over the network** — the sync layer never spawns, re-parents or frees a crocodile except through the explicit kill broadcast, and every croc still comes from the deterministic terrain spawn; **no bite protocol** (the shared-lives sum already is one); and **no `multiplayer.multiplayer_peer` assignment**, still forbidden. The terrain *is* now touched, by exactly one hook — `set_focus_points()`, which decides only which chunks stay loaded and never what one contains. Weather and fauna remain local and non-deterministic by design.

### Multiplayer discoverability: start overlay + the public room list
Two changes to how a player *finds* multiplayer, on top of the phase 3–4 machinery above. Both came from one owner playtest of the deployed build: *"opened the URL, game just starts, no idea multiplayer exists"* and *"copy code not convenient, show a list of opened lobbies."*

**`scripts/start_overlay.gd` (the `StartOverlay` `Control`, the LAST `HUD` child in `main.tscn`) — the game no longer starts on its own.** It opens on one code-built card offering **PLAY SOLO** and **MULTIPLAYER**. Solo stays **one action deep** (one press, or Enter/Space through `_unhandled_input` — never by focusing a button, which is the FOCUS_NONE/Space-is-jump bug `mp_ui._make_button` documents). It **pauses the tree** while up, with the same `_paused_by_us` guard `pause_controller.gd` / `mobile_input.gd` / `mp_ui.gd` carry on each other, for the same two reasons the MP panel does: the world must not run behind a menu, and `player_controller` reads gameplay through the *global* polled `Input` and `_input()`, which a `Control` on top does not suppress. **`player_controller.gd` needed no edit**: `Player` is an earlier child of `Main` than `HUD`, so its `_ready()` mouse capture happens first and this overlay simply releases the cursor while the menu is up and re-captures on dismiss — which is *better* than the old boot capture on desktop web, where pointer lock is refused outside a user gesture and the button press **is** the gesture. It also calls `sound_manager.unlock_audio()` on dismiss, because the manager's own `_input()` unlock does not run under a pause. On a phone it **hides itself and drops its pause while `touch_controls.has_modal()`** — the same three lines `mp_ui.gd` and `mobile_settings_panel.gd` run, and for the same non-negotiable reason: the enable-motion tap is the ONE gesture iOS grants `DeviceMotionEvent.requestPermission()` and the browser grants WebAudio. `_dismissed` is one-way; there is no route back to this screen (Play Again restarts in place, the MP panel is the way into a room). The title is read from `application/config/name`, so a rename never leaves it stale.

**ALL open rooms are public and listed — there is no opt-in flag, and this deliberately supersedes the epic's invite-code-only framing** (owner override, 2026-08-25). `Hub.ListRooms()` in `server/room.go` returns every room with 1..`MaxMembers`−1 members as `{code, members, heroes[]}`, sorted by code (and heroes sorted within a row) so a refresh does not reshuffle an unchanged list; `server/main.go`'s `roomsHandler` serves it at **`GET /rooms`** with the same CORS allowlist as `/ice` and `Cache-Control: no-store`. **It is HTTP, not a websocket message, because `/ws` *joins* on connect and an unknown well-formed code CREATES a room** — asking over the socket would mean making a junk room to ask from, which would then appear in its own answer. Full rooms and member-less (mid-teardown) rooms are withheld: a row you cannot join is worse than no row. **Adding a lobby route means editing the Traefik rule in `server/docker-compose.yml`** — the game client's catch-all owns `/`, so a route missing from the lobby's narrow rule silently serves `index.html` in production.

Client side: `LobbyClient.fetch_rooms()` uses a **second `HTTPRequest` (`_rooms_http`), never `_http`** — one node answers ERR_BUSY while a request is in flight, and `/rooms` is fetched from the panel while `/ice` is fetched *during* a join, so sharing one node would silently degrade a fast player's session to STUN-only. Every failure hands back an **empty array**, never an error, so an old or unreachable lobby reads as "no rooms right now" with the code field still there. `MpManager.list_rooms()` is the passthrough (`mp_ui.gd` only ever knows the `"mp"` group), and it works **while OFFLINE** — that is the point, since the list is browsed before joining; `_ensure_lobby()` creates the `LobbyClient` without opening a socket or touching `_state`. `mp_ui.gd` leads the panel with the room rows (one press joins; the row list is rebuilt wholesale and every entry is type-checked where it is rendered, like the member list) and demotes the invite-code `LineEdit` to "…or join by invite code". The list is pulled **on panel open and on Refresh, never polled**. The section hides in a room. The **`"mp_ui"` group** exists so the start overlay can call `open_panel()` — which takes the panel's pause synchronously, so the tree is never unpaused for a frame between the two. **The persistent room indicator is the MP button itself**: while online it relabels to `"ABC234  2/4"` (wider, smaller font) instead of "MP" — the one control already always on screen, no extra node.

`scripts/mp_e2e.sh` now also curls `/rooms` against the live local lobby and fails unless the room the host instance actually created is listed — the Go tests cover the logic, this covers the route being reachable.

## Localization (en / de)
The game ships in English and German. **Almost none of it is this codebase's code** — it is Godot's built-in `Control` auto-translation, and the two rules below are the whole feature.

**RULE 1 — the translation KEY is the ENGLISH SOURCE STRING, and a plain literal assigned to `.text` needs NO `tr()` call.** `assets/translations/ui.csv` is a `keys,en,de` table imported by Godot's CSV importer (listed in `project.godot`'s `[internationalization]` `locale/translations`). Every `Control` runs its own `text` / `placeholder_text` through the `TranslationServer` at draw time and **re-runs it on `NOTIFICATION_TRANSLATION_CHANGED`**, which `TranslationServer.set_locale()` broadcasts to the whole tree — so `title.text = "GAME OVER"` is already localized, and already live-switching, with no edit at the call site. That is why this landed as a CSV plus ~15 lines of GDScript instead of a `tr()` at 60 call sites, and why **no screen needs a rebuild or a re-apply hook** when the language changes. Keying by the English text also makes English the automatic fallback: a string somebody forgets to add to the CSV renders as readable English, never as a raw `HUD_DISTANCE_LABEL` identifier. **Adding a user-facing string therefore means adding a CSV row and nothing else.**

**RULE 2 — `tr()` explicitly, on the FORMAT STRING, wherever the displayed text is composed at runtime.** Auto-translation would only ever see the *formatted result* (`"Distance: 240m   Coins: 87"`), which is a key in no table. So `tr("Distance: %dm   Coins: %d") % [...]`, never `tr("Distance: 240m…")`. The same applies to text that is **painted rather than assigned** — `minimap_hud.gd` draws its caption with `draw_multiline_string`, so its biome names and river marker are `tr()`d individually. Every such site re-runs on its own (`_process`, an event handler, or the minimap's 0.2 s tick), which is what keeps a mid-run language switch correct for them too. The five sites are `coin_hud.gd`, `game_over_ui.gd`, `minimap_hud.gd`, and two in `mp_ui.gd`.

**The default language is auto-detected and costs nothing:** Godot seeds `TranslationServer` from `OS.get_locale()`, so a German browser starts in German before any of this code runs, and a regional code (`de_DE`) resolves through to the `de` table by Godot's own locale matching. `start_overlay.gd` — the one screen every player passes through, with the cursor free and the tree already paused — carries the EN/DE pills and the `user://locale.cfg` persistence (`apply_saved_locale()` / `save_locale()`, static so the selfcheck drives the real functions). That config is only an **override** of the auto-detection, which is why an unreadable file is silently ignored rather than reported: `user://` is IndexedDB-backed on web and known to be flaky there, and auto-detection is the load-bearing half. The pill labels "EN"/"DE" are deliberately **not** translated — a player who cannot read the current language must still be able to find their way out of it.

**Deliberately NOT localized, and marked as such in each file:** the F3 perf overlay, the F4 motion read-out, the ⚙ panel's raw sensor telemetry block (`accel now` / `peak` / `energy` / `tilt`), and the selfcheck output. These are debug surfaces read against English documentation.

**German is ~30% longer and this UI is full of hard-sized controls, so the fit is MEASURED, not eyeballed.** `scripts/locale_selfcheck.gd`'s `WIDTH_BUDGETS` measures every German string in the real font at the real size against the real control width, and it **caught four genuine overflows on its first run**: `WECHSEL` (118 px in a 120 px circle whose curve eats the corners) → `TAUSCH`, `Lenkung: Neigen`/`Lenkung: Drehen` (243/248 px in a 200 px pill) → `Neigen`/`Drehen` — the mode name alone, which is the information the button actually carries — and `⚙ Regler` (102 px against 110 px minus 8 px of theme padding) → `⚙ Setup`. **Re-run it after any layout constant or CSV change.** Two layouts are exempt by construction rather than by measurement: the MP room rows set `clip_text = true` (they clip, and the room code is at the front where clipping cannot reach it), and the start-overlay / game-over labels autowrap inside a `CenterContainer` that grows to fit.

**CI gotcha — `*.translation` and `*.import` are gitignored, so the CSV is the only committed artifact and CI must regenerate the rest.** `.github/workflows/build.yml` therefore runs an explicit `godot --headless --path . --import` step **before** the export and *asserts both `.translation` files exist*. That assertion is the point: a missing translation resource does **not** fail a Godot export — it ships a build that is silently English in every locale, with nothing in the log. The same trap bites a human in a fresh clone (see the `--import` note at the top of Commands).

**Known gaps, all in files a parallel branch owned during this work, and every one of them a CSV row plus a `tr()` on a format string — no structural change.** (1) ~~The respawn countdown~~ — **done**: `_show_respawn_countdown()` now does `tr("Caught! Back in %.1f...") % …` (RULE 2: `tr()` on the format string, never the formatted result) with the `de` row in the CSV. (2) The multiplayer **status** strings (`"Waiting for the shared world…"`, `"In room %s (%d/4)"`, the lobby/WebRTC errors) in `mp_manager.gd` and `lobby_client.gd`; they render into the MP panel's already-translated status `Label`, so only the `status.emit()` sites need touching. (3) `player_controller.get_ability_name()`, which supplies the ability names `AbilityHUD` draws. Note the sibling `print("Caught! Lives remaining: %d")` at `player_controller.gd:1775` is console output and stays English by the debug-surface rule.

## CI/CD
`.github/workflows/build.yml` builds the web export on every push. Deploy to GitHub Pages happens **only on push to `master`**; `claude/*` branches build (and upload a downloadable `web-build` artifact) but do not deploy. So merging to `master` is what publishes the playable build.

The same master push also runs **`deploy-stack`, the single owner of the `deploy` branch** that Portainer reads. It builds *both* production images — `godot-test1-lobby` from `server/` and `godot-test1-web` (nginx + the web export, with the COOP/COEP headers Godot's `SharedArrayBuffer` needs) from `web/` — pushes them tagged with the commit SHA (**never `:latest`** in production), rewrites both `LOBBY_IMAGE` and `WEB_IMAGE` in `server/docker-compose.yml` in one commit, force-pushes `deploy`, and pokes `PORTAINER_REDEPLOY_HOOK`. **Both images must stay in this one job:** the branch is maintained by force-push, so a second workflow writing it would reset it to its own checkout and clobber the other's pin. The accepted cost is that the lobby image rebuilds on every master push, not just on `server/**` changes. On the deployed host the client owns `/` and the lobby keeps `/ws`, `/ice` and `/healthz` via Traefik router priorities — so the lobby's embedded test page is shadowed in production (`server/README.md` has the table).

## Conventions
- GDScript with explicit type hints throughout; constants for tunable values (`WALK_SPEED`, `DETECTION_RADIUS`, etc.) declared at the top of each script.
- Gravity is per-script and intentionally non-physical: the player uses `gravity = 14.4` with `JUMP_VELOCITY = 10.2` — an arcade-snappy arc whose apex (`v²/2g = 3.6125 m`) is byte-identical to the old floaty 5.1 / 3.6 tuning, so 2.5 m blocks stay jumpable while airtime halves (~1.42 s); Windman's glide gravity is likewise preserved exactly (`14.4 × WINDMAN_GRAVITY_FACTOR 0.1125 = 1.62`, the old `3.6 × 0.45`). Jumps get `COYOTE_TIME` / `JUMP_BUFFER_TIME` (0.12 s each) forgiveness, and horizontal velocity approaches its target via `move_toward` at `MOVE_ACCELERATION` (40 m/s²) instead of snapping. The one thing that scales `JUMP_VELOCITY` is `WADE_JUMP_FACTOR` (0.75, a jump pushed off from inside a river) — which drops the apex to 2.03 m and therefore **deliberately** puts a 2.5 m block out of reach from the water; see the biome section's wading rules. Crocodiles use `GRAVITY = 9.8`.
- Input actions are defined in `project.godot` (`move_forward`/`move_backward`, `turn_left`/`turn_right`, `step_left`/`step_right`, `jump`, `run`, `duck`, `switch_character`, `special_ability`, `toggle_camera`) — reference these action names, don't hardcode keycodes. **The line that convention draws is *gameplay* input**: meta/UI keys that only open or toggle a panel live OUTSIDE the input map as raw keycodes, because there is nothing to rebind them against — P (pause), M (minimap), +/− (minimap zoom), K (skill tree) and F3–F7 (debug) are all of that kind.
